# 退役记录：旧 dev 实例（2026-10-13）

> 用户指示：「旧的归档之后就可以撤了」。本文记录撤了什么、归档在哪、怎么恢复、以及为什么一般不该恢复。

## 1. 撤了什么

| 项 | 处置 |
|---|---|
| `sc2clud-dev.service`（旧 Rust 实例，127.0.0.1:8081，nginx `/dev/` 原来指着它） | 停 + 禁用 + **删除 unit** |
| `/srv/sc2clud-dev/bin/forum`（6.8MB） | 归档后删除 |
| `/srv/sc2clud-dev/dist/{index.html,art/,assets/}` | 归档后删除 |
| `sc2clud-featured-dev.service`（残骸） | 归档 unit 原文后删除 |
| `sc2clud-visual-dev.service`（残骸） | 归档 unit 原文后删除 |

**没有撤、也不该撤的**：

- `/srv/sc2clud-dev/dist/devroom/` —— DevRoom 设计房间，**仍在使用**（nginx `location /dev/devroom/` 静态直出它）；
- `/srv/sc2clud-dev/dist/devroom.legacy-bak-20261013` —— DevRoom 的上一版备份；
- `sc2clud-placeholder.service`（8080）—— 它现在就是生产 `/` 的对外门面（维护页），**上线前才停**；
- `sc2clud@dev.service`（8082）—— 新站，正在跑。

## 2. 归档在哪

```
/srv/archive/sc2clud-old-dev-20261013-1915.tar.gz      3,285,466 字节
/srv/archive/sc2clud-old-dev-20261013-1915/           解开的副本 + 两份 README
├── README.md                                        这一份的详细说明与恢复步骤
├── legacy-units/README.md                           两个残骸变体是什么
├── legacy-units/sc2clud-featured-dev.service
└── legacy-units/sc2clud-visual-dev.service
```

**归档经过校验**：解包后比对二进制的 sha256，与原件**逐字节一致**（`9b5be421…f646`）。
删除原件发生在校验通过**之后**。

**归档不含数据库**：旧实例退役时**没有任何到 PostgreSQL 的连接**，unit 里也没有 `EnvironmentFile` ——
它不依赖库。服务器上那两个库（`forum` 7.5MB / `forum_dev` 11MB）**一个都没动**：
`forum_dev` 是新 dev 在用的；`forum` 既可能是将来的生产库也可能是遗留数据，**没有确证就不碰**。

## 3. 怎么恢复（一般不需要）

```bash
tar -xzf /srv/archive/sc2clud-old-dev-20261013-1915.tar.gz -C /
systemctl daemon-reload && systemctl enable --now sc2clud-dev.service
# 再把 nginx 的 upstream sc2clud_dev 指回 127.0.0.1:8081 并 nginx -s reload
```

**但不建议**：它的前端产物是旧的、没有库、而且与新实例抢同一个路径前缀。
要回退应该用 `deploy.ps1 rollback`（回到上一个 release）—— 那才是这套工具正确的回退方式。

## 5. 一条值得记的教训

`sc2clud-featured-dev.service` 与 `sc2clud-visual-dev.service` 的 `ExecStart` 指向的二进制**早就没了**，
工作目录也删了 —— 它们 disabled，所以从不报错，就这么留了好几天。

**指向已删除文件的 unit 是陷阱**：它不报错、不告警，直到有人 `systemctl start` 它才失败，
而那时你已经在别处查问题了。（退役时**删 unit**，不只是停服务。）
