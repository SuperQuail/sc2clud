# 数据迁移审计（老 Rust/SQLite → 新 Go/PostgreSQL）

> 范围：`backups/old-prod-2026-10-12/sc2clud.sqlite3`（老生产库）+ `prod-files.tgz`（文件）+ 服务器 dev 库 `forum_dev`。
> 本次只动 **dev 库**；prod 要跑的 SQL 在 §4，由 Lead 串行执行。
>
> 一句话结论：**已迁的那批（boards 6 / users 16 / topics 4 / posts 6 / likes 3 / titles 2 / user_titles 2 / images 8 / 3 个头像）逐列核对全对得上；漏了 9 项（候选清单里的 4 项 + 逐列核对时又挖出 5 项），本次全部补进 dev 并逐项留了证据；剩下放不下的一些写在 §3.4 与 §5。**

## 0. 口径（这份审计是怎么做出来的）

| 事实来源 | 用途 |
|---|---|
| 逐表读老 sqlite（`pragma table_info` + `count(*)`） | 老库 **54 张表、每一列**与每张表的行数 |
| 读 `forum_dev` 的 `information_schema.columns` | 新库 49 张表的每一列 |
| 读老站 Rust 源码 `site/crates/**`（`migrations/*.sql`、`repo.rs`、`templates/*.html`） | 老列的**语义**（不猜：老站内容寻址是 blake3、默认头像是模板里的站点资源、分区门槛是角色门槛） |
| 读 `deploy/legacy-migration.sql`（v2，真正跑过的那份） | 已经迁过什么、按什么规则迁的 |
| 真跑 dev 库 + 真打 `/api/v1/**` | 每一项的验收证据（字段值，不是状态码） |

老库 53 张业务表 + `sqlite_sequence` + `_sqlx_migrations`；新库 49 张表，其中 10 张老库没有（`jobs`、`roles`、`permissions`、`role_permissions`、`user_permissions`、`user_donation_settings`、`user_notice_settings`、`mail_logs`、`mail_quota`、`topic_search`）。

## 5. 风险与遗留

### 5.1 已迁的 8 行 `images.hash` 是老站的 **blake3**，不是 sha256

新站 `images` 的键是 sha256（`localstore` 边收边算 sha256，路径 `<root>/<ab>/<cd>/<sha256>`），老站是 blake3（`site/crates/sc2clud-storage/src/local.rs` 的布局注释、`core/hash.rs`）。实测：把备份里 8 个 blob 的字节逐个算 sha256，**8/8 都不等于它的文件名 hash**；新 store 上的文件与 `images.hash` 一一对应、mime 与魔数一致（8 个文件逐一验过头字节，PNG/WEBP 都对）。

- **不影响功能**：`/img/<hash>` 按路径取文件，可见性查 `images.visibility`，都不校验摘要（真取字节：`200 image/webp 5868`）。
- **损失**：跨库去重失效 —— 用户再上传同一张图，sha256 与老 hash 不同 → 多一行 `images` + 多一份盘上字节。
- **建议**：接受，别再动。改键要连带改 `users.avatar_hash`/`avatar_small_hash`/`default_avatar_hash`、`topic_images.image_hash`、`boards.cover_hash`、`default_avatars.hash` 与盘上文件名，收益只有 8 行的去重。
- 顺带：本次播种的默认头像用的就是老 hash `8bec38b0…`，与新站自己上传的图片 hash 不同源，同属这一类。

### 5.2 老 `developer` 组的 2 个人降成了普通用户

老 `users.role` 有 4 个值：`super`(3) / `admin`(4) / `member`(7) / `developer`(2)，v2 把 `developer` 折进了 `role_id=1 (user)`，涉及 `Alenger`(5) 与 `576530175`(15)。老 `developer` 的用处只有 tool_player / tool_dev 的**角色门槛**（在新站已经是 `min_post_level=0`，人人可发）。要把「认证创作者」这个语义补回来是**权限决定**、不是数据迁移，SQL 一行：

```sql
update users set role_id = (select id from roles where key = 'creator') where id in (5, 15);
```

### 5.3 「公告区只有管理员能发帖」还没补

老站靠 `sections.post_min_role = admin`。新站的 `min_post_level` 是等级门槛，**不能替代**（对齐文档第三节已记账）。要表达它只能用 `board_acls`；本次只迁了老库真实存在的那 1 行（emperor/creator），**没有**替公告区造新行 —— 那是规则设计，得用户拍板。SQL 形态：

```sql
update boards set acl_enabled = true where slug = 'announcement';
insert into board_acls (board_id, role_id, can_post, can_reply)
select b.id, r.id, true, true from boards b join roles r on r.key in ('admin','superadmin') where b.slug = 'announcement'
on conflict (board_id, role_id) do nothing;
```

⚠️ `acl_enabled = true` 之后是**白名单**制：没列到的角色连回复都不行。这个口子要不要开得用户拍板，我没有动。

### 5.4 老用户组 → `creator` 是**语义变化**，不是等价

老 `user_groups.huangdi`（皇帝）那 1 行没有迁（新站没有自定义组），它唯一的作用（emperor 分区的规则）挂到了 `creator`。当时该组成员是 0 人，所以没有用户的权限被改变；但「皇帝」这个身份在新站**没了**（要恢复只能新建角色，那会动 RBAC 种子）。

### 5.6 论坛列表里的头像不走默认头像（数据之外的契约问题）

`TopicCardDTO.Author` / `TopicDetailDTO.Author` 回的是**裸 `avatar_hash`**（`forum/dto.go:12`），前端自己拼 `/img/<hash>`（`web/src/routes/_parts/mappers.ts:40`）。所以 §2.6 分派的默认头像**资料页可见、论坛列表不可见**（列表回退首字占位）。这是新站既有的 DTO 形状问题，不是迁移问题：要修得让 forum DTO 也走 `media.Avatar()`，动的是后端契约 + 前端映射（前端还要过 DevRoom 验收）—— **不在本次数据迁移范围**，写在这里备案。

### 5.7 门禁状态（诚实说明）

- `cd web && pnpm check` **当前是红的，但红在别人的在途改动上**：`web/src/routes/topic.tsx` 有 13 条 TS 错误（`wire`、`toDesignAuthor`、`toReview`、`toDesignTopic` 未定义 + import 未使用）。`git status` 里 `web/src/routes/topic.tsx`、`web/src/devroom/pages/12-topic/**` 等 30+ 个文件都是 modified —— 别人没提交的工作，我没有碰。

### 5.8 两处「不确定要不要补」
