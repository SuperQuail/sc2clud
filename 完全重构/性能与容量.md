# 性能与容量（约束：2 核 / 2 GB / 10 Mbps，dev 与 prod **同机**）

> 前提变了：**没有多余域名 → dev 只能挂在同域 /dev/ 前缀下**，而且只有一台机器 → **两个实例要一起塞进 2GB**。
> 所以性能问题**在代码里解决**，不靠加内存、不靠拆机器、不靠加组件。
> 本文档取代后端方案 §9.6 的内存预算表；搜索方案取代 §7.6 与数据库文档 §5 的 gse 实现。

---

## 1. 修正后的真实账（盲审核实过）

| 项 | 原文档 | 实测 / 修正 | 差 |
|---|---|---|---|
| gse 词典 | ≤ 80 MB | **仅 Tokens 切片就 49 MiB**（Token=88B × 589,035 词条），加索引结构更大 | **被推翻** |
| autovacuum_work_mem | 未计入 | 默认取 maintenance_work_mem(64MB) × 3 worker → **最多 192 MB** | 漏 |
| PostgreSQL 后端进程 | 未计入 | ~20 个 × 5–10 MB → **100–200 MB** | 漏 |
| work_mem | 当作「每连接」 | **是每排序/哈希节点**，一个复杂查询可用掉多份 | 口径错 |
| 单实例合计 | 纸面 ≈400 MB | **推算 1.0–1.6 GB / 2 GB** | 无余量 |

结论：**两个实例按现状必然 OOM**。必须从代码里把预算砍下来。

## 2. 代码级优化（按收益排序）

### 2.1 删掉 gse 词典，搜索改 **bigram（二元切分）** —— 省 80–100 MB/实例

现做法：启动时加载中文词典，写入与查询都用它分词。代价是常驻近百 MB，而本站的搜索需求只是「按词找回帖子」。

改成：**不加载任何词典**，写入与查询都把文本切成 **2-gram**，用空格连接后交给 PostgreSQL 的 simple 配置：

    写入： "中文搜索" → "中文 文搜 搜索"   → to_tsvector('simple', …)
    查询： 同样的切分                       → plainto_tsquery('simple', …)

- **收益**：词典内存归零、启动不再等词典、`go-ego/gse` 依赖整个删掉（少一个第三方库）。
- **代价**：索引略大（2-gram 数量 ≈ 2× 字符数）；多字词靠 GIN 的 AND 语义匹配，会有少量误召回——**论坛搜索可以接受**。
- **plan B**（实测召回不可接受时）：把 gse 改成**懒加载 + 空闲卸载**（首次搜索时加载，30 分钟无查询释放），代码里留开关但不进默认依赖。

    shortcut: bigram 会带来少量误召回；若用户明确抱怨搜索质量，再切回 gse 懒加载方案。

### 2.2 进程被 cgroup 硬顶，代码不再「假设自己独占内存」

    systemd:  sc2clud-prod  MemoryMax=900M     sc2clud-dev  MemoryMax=350M
    Go:       GOMEMLIMIT 略低于上限（prod 800MiB / dev 300MiB）

Go 1.25+ 会读 cgroup 决定 GOMAXPROCS，但**不会**自动设 GOMEMLIMIT —— 必须显式给。给早了 GC 频繁，给晚了被 OOM kill：**宁早勿晚**。

### 2.3 dev 实例**按需启动**（省常驻，不省峰值）

dev 只在有人验证时跑：`deploy.ps1 dev` 启动它，空闲 30 分钟由 systemd timer 停掉。dev 不对外服务，停掉不影响任何人。

### 2.4 连接池按实例给（不是一刀切 16）

| 实例 | MaxConns | MinConns | 理由 |
|---|---|---|---|
| prod | 12 | 2 | 2 核机器上再高的并发也只是排队，多连接只多内存 |
| dev | 4 | 1 | 单人使用 |

### 2.5 PostgreSQL 参数（一个实例两个库，按共享 2GB 调）

    shared_buffers = 192MB          # 两库共用；不按 25% 的教条给 512MB
    effective_cache_size = 512MB
    work_mem = 2MB                  # 每排序节点；宁小，慢查询再单独调
    maintenance_work_mem = 64MB
    autovacuum_work_mem = 32MB      # 显式指定，否则默认跟 maintenance_work_mem 走
    max_connections = 40            # prod 12 + dev 4 + psql/备份余量
    wal_compression = on

### 2.6 HOT 更新与膨胀（写热点表）

「reply_count / view_count / last_seen_at / download_count」都是**高频小更新**，必须让他们走 HOT：

    ALTER TABLE topics    SET (fillfactor = 85);
    ALTER TABLE sessions  SET (fillfactor = 80);
    ALTER TABLE posts     SET (fillfactor = 90);

配套：计数器已经是「内存缓冲 + 15 秒批量写回」，last_seen_at 已经是「10 分钟节流 + 批量 UPDATE」——**继续保持，禁止改成每请求 UPDATE**。

### 2.7 图片与静态产物（已定，不再讨论）

上传流式、不转码、不生成缩略图；图片字节不进应用进程；前端路由级懒加载 + 体积门禁。

## 3. 启动自检（把纸面总账变成运行时事实）

`forum run` 启动时：

1. 读 cgroup 内存上限（Linux：`/sys/fs/cgroup/memory.max`，读不到就跳过）；
2. 与配置里的内存预算（是否加载词典、缓存上限、连接池大小）比对；
3. **超过上限 80% → 记 Warn 并在 `/readyz` 暴露**；**超过 100% → 拒绝启动**并打印建议（例如「dev 实例请把 pool 降到 4」）。

这样「内存够不够」不再靠人在文档里算，而是**起不来就是起不来**。

## 4. 怎么证明优化有效（验收）

| 项 | 判据 |
|---|---|
| 内存 | 两实例同时在跑时 cgroup 显示 prod < 700MB、dev < 300MB；机器 free 余量 > 200MB |
| 依赖 | `go list -deps ./...` 里不再出现 gse |
| 搜索 | 给定 10 个两字/三字中文词，全部能搜到对应帖子；结果里没有 hidden/deleted |
| 列表页 | 50 并发请求分区列表，P95 < 200ms，跑完 RSS 不增长 |
| 队列 | 积压 1000 个任务时 worker 内存不随积压线性增长 |
| 膨胀 | 连续 24 小时写入后，pg_stat_user_tables 里 topics/sessions 的 n_dead_tup 不持续增长 |

## 5. 明确不做（为性能而做的反优化）

- 不引 Redis / Meilisearch / 只读副本 / 拆服务：单机 2C2G 下这些只会更慢、更复杂。
- 不用 CGO 换性能（省下的部署复杂度比那点性能值钱）。
- 不为「以后可能扩」预留连接池与缓存容量。
