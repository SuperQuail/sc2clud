# 性能与容量（目标：4 GB 服务器，**保证体验**）

> 现状 2 核 / 2 GB，**之后升级到 2 核 / 4 GB**。本文档按 4 GB 重新设计，并保证**同一份制品在 2 GB 上今天也能跑**——靠**档位**，不靠改代码、不靠重建制品。
> 方向从「省到能跑」改为「**把多出来的 2GB 花在体验上**」。本文档取代上一版按 2GB 极限压缩的方案。

---

## 1. 先认清瓶颈在哪

| 资源 | 现状 | 结论 |
|---|---|---|
| 带宽 | **10 Mbps ≈ 1.25 MB/s 全站共享** | **唯一瓶颈**。省带宽 = 直接提升体验 |
| CPU | 2 核，长期空闲 | 可以**用 CPU 换带宽**（旧站自己写下的原则） |
| 内存 | 2GB → 4GB | 升级后约 2GB 可支配 |

优化顺序：**① 省带宽 → ② 降延迟 → ③ 才是省内存**。

---

## 2. 两个档位（同一份代码）

| 档位 | 触发条件 | 场景 |
|---|---|---|
| **small** | 主机 / cgroup 上限 < 3GB | 今天：2GB 机器；dev 按需启动 |
| **standard** | ≥ 3GB | 升级后：4GB 机器；dev 常驻 |

    capacity:
      profile: auto        # auto | small | standard（auto = 按启动时读到的内存上限判定）

档位影响的项：**连接池大小、进程内缓存容量、worker 并发、私信实时通道、列表页缩略图、dev 是否常驻**。
**切换只改配置**（或什么都不改，auto 自己认）。

---

> **swap（2026-10-12 配置为 8GB）**：单个 `/swapfile`（已进 fstab），`vm.swappiness=10`，`vm.overcommit_memory=1`（Redis 要求）。
> **它是兜底不是容量**：用来吸收突发（pg_dump/恢复、图片批处理、Go GC 尖峰），目标仍是「常驻不换出」。`MemoryMax` 与 `GOMEMLIMIT` 该设还得设——靠 swap 撑住的进程会让整机变慢，那是体验的反面。

## 3. 4GB 怎么分（standard 档）

| 用途 | 预算 | 说明 |
|---|---|---|
| 操作系统 + nginx | 400 MB | page cache 算体验的一部分（图片与 PG 都吃它） |
| PostgreSQL | 1400 MB | shared_buffers 1GB + 约 20 个后端进程 + WAL（**实际参数已按此配置上线**） |
| Redis | 320 MB | `maxmemory 256mb` + 进程自身约 10–30MB + 客户端缓冲；不落盘所以没有 fork 尖峰 |
| Go prod | 900 MB | GOMEMLIMIT 800MiB |
| Go dev | 400 MB | GOMEMLIMIT 350MiB；standard 档下**常驻**（验证不用等启动） |
| 余量 | ~900 MB | 备份、pg_dump、缩略图任务、突发 |

PostgreSQL（standard）：

    shared_buffers = 1GB
    effective_cache_size = 2560MB
    work_mem = 8MB                  # 每排序节点，不是每连接
    maintenance_work_mem = 128MB
    autovacuum_work_mem = 64MB      # 必须显式给
    max_connections = 60
    wal_compression = on
    random_page_cost = 1.1          # SSD

small 档沿用上一版：shared_buffers 192MB、work_mem 2MB、autovacuum_work_mem 32MB、max_connections 40。

## 4. 体验优先的六项（多出来的 2GB 花在这里）

按**感知收益**排序：

1. **列表页缩略图** —— 收益最大，因为省的是唯一瓶颈。
   上传时同步生成一张 ≤ 60KB 的缩略图（2 核 CPU 长期空闲），列表页只加载缩略图，详情页才加载原图。
   预期：帖子列表首屏字节数降约 10 倍。生成失败回落原图，**不阻塞上传**。
2. **私信改 SSE（standard 档）** —— 端到端延迟从「最多 5 秒」降到 **< 1 秒**。
   每连接内存极小；保留 30 秒轮询兜底（断线、代理缓冲、老浏览器）。small 档仍用 5 秒轮询。
3. **PostgreSQL 缓冲与连接** —— shared_buffers 1GB、prod 连接池 20。目标：列表页 P95 < 150ms。
4. **进程内缓存放宽** —— 权限、版块、主题详情缓存容量与 TTL 上调（**仍然有硬上限**，不许无界）。
5. **worker 并发 4 → 8** —— 通知、邮件、搜索索引不再排队。
6. **nginx：HTTP/2 + brotli_static + 静态 immutable** —— 首屏字节数直接下降；图片仍走 sendfile 直出。

**已经上线的**：Redis（2026-10-12，仅回环，`maxmemory 256mb` + `allkeys-lru` + 不落盘）。**明确不做**（即使有 4GB）：Meilisearch（tsvector 够用）、对象存储（单机 10Mbps 下没意义）、视频 / 大文件（产品边界）。

## 5. 搜索分词：**保持 bigram，不把 gse 加回来**

这是本次重新设计里唯一「有钱也不花」的项：

- bigram 是**零内存、零启动开销、零依赖**的一条实现；换回 gse 只换来有限的精度提升，却要 **100MB 常驻 + 1–2 秒启动 + 多一个第三方库**；
- 更要紧的是：**可切换的双实现必然漂移**（写入侧与查询侧切法不一致 = 搜不到，且很难查）。宁要一条够用的实现。

若你更在意搜索精度，这是唯一值得重新评估的项（代价 ~100MB + 启动时间，收益是词级切分）——**其余预算一律花在带宽与延迟上**。

## 6. 启动自检与档位（代码级护栏）

    forum run 启动时：
    1. 读内存上限（/sys/fs/cgroup/memory.max，读不到就用 /proc/meminfo）
    2. 选档（配置显式指定则优先）
    3. 打印「档位 + 各项预算 + 实际可用」一行
    4. 超上限 80% → Warn 并在 /readyz 暴露；超 100% → 拒绝启动

GOMEMLIMIT **必须在 systemd 里给**（运行时改不了）：

    # standard
    MemoryMax=900M
    Environment=GOMEMLIMIT=800MiB
    # small
    MemoryMax=450M
    Environment=GOMEMLIMIT=400MiB

## 7. 验收：**体验指标**，不是内存指标

| 指标 | small（2GB 今天） | standard（4GB 升级后） |
|---|---|---|
| 列表页首屏字节（含缩略图） | ≤ 400 KB | **≤ 150 KB** |
| 列表页 P95 响应 | < 300 ms | **< 150 ms** |
| 私信端到端延迟 | ≤ 5 s（轮询） | **< 1 s（SSE）** |
| 内存余量（两实例同跑） | > 150 MB | **> 400 MB** |
| 50 并发列表页后 RSS 增长 | 0（无泄漏） | 0 |
| 搜索 | 10 个中文词全部能搜到，且不含 hidden / deleted | 同左 |

---

## 8. 升级动作（当天就能切完）

1. 加内存（**不改代码、不重建制品**）；
2. 改 systemd：MemoryMax / GOMEMLIMIT / PG 参数 / nginx 打开 http2 + brotli；
3. 配置里把 capacity.profile 改成 standard（或保留 auto）；
4. 重启 → 看启动自检打印的新档位 → 跑 §7 的验收表；
5. **回滚**：把 profile 改回 small 重启即可，**不动数据、不动制品**。
