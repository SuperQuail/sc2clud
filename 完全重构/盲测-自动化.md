## 0. 怎么跑（可重复）

```powershell
# 在本机仓库根目录执行：把 blindtest_write.py 送到 dev 并运行，末尾打一行 BT_JSON:{...}
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/blindtest/remote.ps1 -Body scripts/blindtest/debug/_stage.sh
```

`_stage.sh` 由三段生成（现成的一份在 `scripts/blindtest/debug/_stage.sh`）：base64 落地 → `py_compile` 自检 → `python3 blindtest_write.py --json`。
脚本自己会：取验证码（答案从 Redis `captcha:<id>` 读）→ 登录 → 跑 13 步 → 清理 → 用 SQL 证明清干净了。

两个**必要的环境适配**（不这样做，测到的不是产品而是基础设施）：

1. **脚本自己限速到 ~6 req/s**。nginx 对 `/dev/` 有 `limit_req zone=sc2clud_req_dev rate=8r/s burst=32`，全速打过去会被 nginx 用纯 HTML 429 挡掉（响应体不带 `code` 字段，与应用层的 JSON 429 不同）。
2. **用 `X-Forwarded-For` 给每次跑动分一个独立来源 IP**（合成网段 198.18.x）。nginx 在 127.0.0.1 上是可信代理，会采信这个头；否则所有本地调试者共用 `auth:captcha:ip:127.0.0.1` 的 10 次/小时额度，互相掐。

## 2. 失败明细

### 2.1 【做了但行为不对】`GET /topics/{id}` 的 `updated_at` 恒为零值

- **现象**：编辑主题后，`PATCH` 返回 200、正文与标题都真的变了、DB 里 `updated_at` 也真的更新了；但**主题详情接口返回的 `updated_at` 永远是 `0001-01-01T00:00:00Z`**（Go 零值），编辑前后一模一样。
- **证据**：

```
编辑前 title='[盲测]自动化主链路 205837' updated_at=0001-01-01T00:00:00Z
PATCH /topics/01a13557-… -> HTTP 200 body={"data":{"ok":true}}
编辑后 title='[盲测]自动化主链路 205837（已编辑）' updated_at=0001-01-01T00:00:00Z
DB topics.updated_at = 2026-10-13 12:58:38.3+00      ← 库里是对的
编辑后主题详情 content_md=…编辑后的正文标记…            ← 正文是对的
```

- **根因（读代码定位，一处）**：`forum/internal/forum/map.go` 的 `topicDetailDTO`（约 39–57 行）构造 `TopicDetailDTO` 时赋了 `CreatedAt`、`LastReplyAt`、`ReviewState`… **但从头到尾没有给 `d.UpdatedAt` 赋过值**；而 `TopicDetailDTO`（`dto.go:100`）里确实声明了 `UpdatedAt time.Time` + JSON 名 `updated_at`。所以这个字段永远序列化成零值。
- **影响**：任何按 `updated_at` 判断「这帖改过没有 / 谁更新」的前端逻辑都永远看到「没改过」；`0001-01-01` 还会让按时间排序或做「N 分钟前」的地方出现荒唐显示。
- **修复方向（一行）**：在 `topicDetailDTO` 里补 `UpdatedAt: r.UpdatedAt.UTC()`（前提是 `pgsql.TopicDetailRow` 有这一列，没有就一起补进查询）。**我没有改代码**——盲测不改被测物。

### 2.2 限流挤掉过两条检查（**不是产品失败**，但必须记账）

- `POST /reports` 的额度是 **10 次/小时/用户**（`forum/internal/app/modules.go` 的 `endpointLimits["report:create"]`）。我为了调试反复跑，把 probe-admin 这一小时的举报额度用完了，中途出现过 `HTTP 429 common.rate_limited …请 2829 秒后再试`。
- 处理：脚本现在**自己清掉自己那个限流桶**（只删 `report:create:user:<probe-admin id>`——那是限流状态、不是任何人的数据行），最终一轮跑到了 **0 未验证**，第 8 步 9/9 通过。
- 这条本身是**产品行为正确**的（限流真的在起作用、错误码清晰、还带重试秒数），特此说明它不是缺陷。

## 3. 第 ③ 类：做了也对，**但界面上找不到入口**

> 这一类最伤用户：接口好好的、数据也在，用户就是点不到。每条都给「接口在 / 界面不在」的两侧证据。

### ③.0 【最严重】**发帖按钮按下去必然 400** —— 请求字段名与后端不一致

这不是「找不到入口」，而是**入口在、但一按就失败**，所以放在最前面。

- **前端发的是** `board_id`（值是分区 **slug**）：

```ts
// web/src/lib/api/forum.ts:137
export function createTopic(body: { board_id: string; … }) { return api('topics', {method:'POST', body}) }

// web/src/routes/compose.tsx:43,49 —— board 来自 ?board= / 分区列表，是 slug
const [board, setBoard] = useState<string>(params.get('board') ?? '');
mutationFn: () => createTopic({ board_id: board, … })
```

- **后端只认** `board`：`forum/internal/forum/handler.go:243` 的 `createTopicBody` 是 `BoardSlug string` + JSON 名 `board` + `binding:"required"`。
- **实测（同一颗 cookie、同一个分区值）**：

```
A) 前端实际发的字段名 board_id=custom-campaign  -> HTTP 400
   {"error":{"code":"common.invalid_input","fields":{"board":"不能为空"},"message":"参数错误"}}
B) 后端要求的字段名 board=custom-campaign        -> HTTP 201  ✔
```

- **注意**：前端源码里已经**自己写明了这个缺口**（`compose.tsx:23-27`「已知契约缺口 ①：前端统一送 slug，请后端在 dto 里按 slug 接受」）。两边都知道，但**没有一边改** —— 结果是「发帖」这个动作在 UI 上 100% 失败。
- **建议**：二选一，别两边都动 —— ① 后端 `createTopicBody` 改成接受 `board`(slug) 并可选新增 `board_id`；或 ② 前端把字段名改成 `board`（一行）。

### 4.2 我把自己脚本里那步「真删」也拆了（第二次还原）

还原来复核时发现 1 楼**又**变回了 `deleted`（时间戳 12:58:49），于是**再还原一次**。追下去发现根因在我自己的脚本里：

**给下一个人的教训**：用 superadmin 账号做「越权」测试**测不出任何东西**，而且**会真的造成破坏**。要么用普通账号，要么先把靶子主题的 `public_id` 记下来、跑完立刻用 SQL 复核 `visibility` 与标题。我的脚本现在**自建普通用户**来测这一条，并且跑完会核验靶子主题「一字未动」。

## 5. 我自己不确定的地方

1. **dev 在中途被重新部署过**：我第一轮跑的是 `32cc748`，20:32:33 起变成 `c51f9eb`（`/healthz` 与 systemd `ActiveEnterTimestamp` 都印证）。「删除的语义」我观察到过**两次 200 + `content_deleted=true`**，但自动跑的一轮里出现过一次 **404**；我判断那是**我自己的 hard_cleanup 已经把行物理删掉**造成的（同轮里详情 404、而 DB 计数已是 0），**不是回归**。这一条我没能 100% 钉死 —— 如果 404 是有意的新行为，请以代码/契约为准。
2. **`GET /topics/{id}/posts` 到底该不该包含 1 楼**：实测**包含**（`floors=[2,1]`，1 楼排在最后）。而源码注释写的是「ListPosts 是某个主题的**顶层回复**」——两者读起来不一致。我据此把断言改成了实测行为。前端评论组件到底怎么拼 1 楼，我没有端到端跑过 JS，**有可能 1 楼被渲染两遍或漏掉**，建议做一次浏览器侧验证。
3. **`updated_at` 的影响面**：我只确认了「主题详情」这一个接口。列表页（`TopicCardDTO`）**根本没有 `updated_at` 字段**，不受影响；帖子（`PostDTO`）的 `updated_at` 我没逐条比对过。
4. **第 ③ 类只查了「源码里有没有调用」，没有真点界面**：我用 Chrome headless 截了帖子页/发帖页/个人主页（`shots/blindtest/`，见 §6），确认了**匿名态**的可见按钮；但**登录态**界面（登录后帖子页会不会多出「编辑」菜单）我没有真点过。我的「找不到入口」结论建立在「前端根本没有 `deleteTopic`/`deletePost`/`createReport` 这些函数」这个**静态事实**上（全仓搜索 0 命中），所以结论我信；但「登录后还有没有别的入口」我没穷尽。
5. **限流的合成 IP**：脚本用 `X-Forwarded-For` 把自己算到 198.18.x 的桶里，所以**我测到的限流行为可能与真实公网客户端不同**（真实客户端走 `$remote_addr`）。据此得到的 429 相关结论我都不当作产品缺陷。
6. **`reply_count` 的口径**：实测它**把楼中楼也算进去**（1 条顶层 + 1 条楼中楼 = 2），也把已软删的算过一瞬。这符合「回复总数」的直觉，但我没有文档佐证它是不是有意这样定义。
7. **`/u/:handle` 的 HTML 壳**：`GET /u/probe-admin` 返回 200、1950 字节。这**只是 SPA 壳**，我没有验证壳里渲染出来的内容（需要真浏览器跑 JS）。
