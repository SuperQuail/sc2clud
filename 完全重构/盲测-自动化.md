## 二、失败明细（按三类分）

**结论一句话：dev 的核心可用性有一个致命缺口 —— 用浏览器登录不进去**（表单字段名与后端契约不一致 + 验证码永不出现）。其余页面/接口大体都在，
问题集中在「登录」与「权限点两套命名」上。

### ① 功能没做（界面已如实说「还没接」）

| 项 | 证据 | 说明 |
|----|------|------|
| 搜索 `GET /api/v1/search` | 404 `common.route_not_found`；`/dev/search` 页写「搜索还没接后端」 | 前端没假装能用，是诚实的占位 |
| 私信界面 | `/dev/messages` 与 `/dev/messages/{handle}` 同一屏占位，明说「私信还没接后端」 | 但接口那侧已经冒头（见 ③ 的表），两边口径要统一 |
| 启动器下载 `GET /api/v1/launcher/*` | 404 `common.not_found`；`/dev/download` 占位 | 同上 |
| 找回密码 / 头像上传 / 设备会话列表 | 登录页与设置页脚注逐条写明「还没接，见回报的端点清单」 | 同上 |
| 后台 12 屏的数据 | `/dev/admin/*` 顶部常驻横幅「管理后台的界面已上线，数据还没接」 | 同上；屏内是 DevRoom mock |

### ② 做了但行为不对（本节是重点）

#### ②-1 【致命】登录表单字段名与后端契约不一致 → 谁都登不进去

- 实测：在 `/dev/login` 填 `probe-admin / Probe-Dev-2026!` 提交，浏览器实际发出：
  `{"username":"probe-admin","password":"Probe-Dev-2026!"}`（CDP 抓到的真实请求体）
- 服务端回：`{"error":{"code":"common.invalid_input","fields":{"login":"不能为空"},"message":"参数错误","request_id":"1d71d310a010020b"}}`
- 后端 DTO 要的是 `login`（forum/internal/auth/handler.go:82 `Login string json:"login" binding:"required"`），
  而前端 `web/src/lib/api/auth.ts` 的 `login(body: { username; password })` 原样把 `username` 发出去（只改写了 captcha 字段）。
- 对照：同样参数改用 `login` 字段直连接口 → **200 登录成功**（`{"data":{"expires_at":"2026-11-12T13:09:10.16371936Z"}}`）。
- 后端逻辑本身是对的：不带验证码时它确实回 `{"error":{"code":"auth.captcha_required","message":"请先填写验证码"`（前端就是靠这个 code 画验证码）。

**为什么这是致命的**：

1. 后端回的 code 是 `common.invalid_input`，而前端只在 `auth.captcha_required / auth.captcha_wrong` 时才画验证码
   （`web/src/routes/login.tsx:42-47、110`）→ **验证码输入框永远不会出现**，用户卡在第一屏无路可走；
2. 错误文案只有「参数错误」，用户不知道要做什么；
3. 影响面：**在 dev 上用浏览器登录 = 不可能**，它同时挡住所有已登录能力（发帖、设置、通知、后台 12 屏）。
   本地开发是接口直连 + 手工种 cookie，所以一直没被发现。

#### ②-2 【严重】权限点两套命名：超级管理员也发不了帖 / 回不了帖

- 前端判据是 `post.create`：`compose.tsx:70 / topic.tsx:167,184 / profile.tsx:187`；
- 后端 `/me` 的 perms 里根本没有这个键，只有 `topic.create`（实测 24 个权限点，全是 topic.* / user.* / role.* / site.*）。
- 实测页面：`/dev/new` 顶部黄条「账号没有发帖权限 · 当前角色没有 post.create 权限」，**发布按钮置灰**；

## 三、我不确定 / 可能是我这边的假阳性

1. **`/dev/devroom/` 的 404 截图是工具假象**：`full/41-devroom.png` 是 404 页 —— 我的本地反代剥掉 `/dev/` 后直连 Go 进程，而设计房间是 **nginx alias** 服务的（Go 的 dist 里没有 devroom/）。经真实公网入口复测为 200 + DevRoom，真图是 `41b-devroom-via-domain.png`。**不要按 41-devroom.png 下结论。**
2. **`首页(游客,首帧白屏测量)` 那条 FAIL 是刻意留的**：它记录「加载完成」之前的第一帧（4.3 s 内 #root 无子节点），用来量化 ②-5；它不是坏页面（`01-home-guest.png` 同一 URL 正常）。
3. `GET /topics/{id}/posts` 最后一次跑返回 0 条（前一次同端点 1 条）。可能是帖子真的没回复，也可能是服务端在 20:31 前后重启过（版本号与 X-Request-Id 都变过）。我没做写操作去验证，故标存疑。
4. 限流：dev 上按 X-Forwarded-For 分的桶里有前一位施工者的残留，我的扫描每页换一个 XFF 绕开，因此**没测出真实用户视角的限流阈值**（captcha 端点曾被 429 挡 284–1155 秒，那是别人的桶）。
5. 我的探针按 `main` 的 innerText 取文本、按 `.animate-pulse` 认骨架屏；若存在「不用这两个类也不写正在加载」的骨架屏，我的等待判据会提前认为渲染完成（本轮未遇到）。
6. 我没有测任何写操作（发帖/回复/点赞/上传/举报/后台动作），也没测移动端宽度、深色模式、i18n。登录是唯一一次写（POST /auth/login），只用了我自己建的 probe-admin。
