# 缺陷处理总纲（管所有 bug，不只是这一次）

> 用户 2026-10-13 定，**这条优先于其它一切**：
> 「即使是新发现的偶发性错误，也不能修掉了事，要从根源上杜绝，持久化/写文档，**除非只是单纯的误操作**。」

## 1. 规则本身

发现一个缺陷时，按顺序做三件事，缺一件不算处理完：

1. **修掉它**（让当前现象消失）；
2. **问「为什么它会存在」**——找到让它可以被写出来的那个东西（缺检查？缺类型？缺文档？缺一条能红的测试？）；
3. **把那个东西堵上**：加检查、加测试、改文档、改约定——**堵法必须能被机器验证，或在文档里有一条能被逐条核对的位置**。

**唯一例外**：**单纯的误操作**（打错字、路径拼错、把参数写反了一次）。误操作不追根因，但**要在提交信息里说明它是误操作**，避免下一个人把它当设计缺陷去分析。

## 2. 为什么这条这么重（不是洁癖）

旧站 12 条根因里，**根因 12 就是这条的反面**：

> 「反馈回路失效的代价被『就地打补丁』吸收，缺陷因此常驻」

旧站的每一个缺陷单独看都不难修，问题是**每次只修现象、不堵来源**，于是同一类缺陷换个地方再出现一次。
本项目的 11 条最小验收线（复盘 §5）就是为这件事写的：**每条根因都对应一条能红的检查**。

## 3. 今天已经按这条处理过的例子（作为样板）

| 发现的缺陷 | 只修现象的做法（❌） | 我们实际做的（✅） |
|---|---|---|
| 退避 SQL 报「表达式类型为 interval」 | 把 SQL 改到不报错为止 | 查清是 **DescribeExec 下 PG 对 `$4` 的类型推断**导致的，改用**参数处显式转型**，并把这个理由写进 SQL 注释（下一个人改这条 SQL 时不会再踩） |
| `TestValidateRejectsDeadValues` 自己断言写错 | 把断言改绿 | 改成复用加载器的 `__`→`.` 映射，**同时钉住「env 名 → 配置键不漂移」**，于是新加的 5 个 case 的真实失败被暴露出来 |
| 档位 bug：日志打 8、实际跑 4 | 把日志改成 4 | 抽出 `resolveQueue` 让**生产路径与用例共用同一份代码**，并**变异验证**（退回去会红、还原才绿）——不加这一步，「测试通过」与「测试什么都没测」长得一模一样 |
| 我给 16 张表补 id 却没同步迁移 | 只把报错的那张表补上 | 用真库跑一遍迁移，**把 17 张「有 ent 实体但迁移没建 id」的表一次找齐**，并留 `.tools/migcheck` 作为可复跑的探针 |
| 有 agent 把 `$env:TEMP` 当相对路径，工作区里出现 `undefined/` | 删掉了事 | 删目录 + **在 .gitignore 加 `/undefined/`**，下次不会再入库 |

## 4. 落地方式：每个缺陷在回报里要回答四问

施工者的回报里，每条缺陷必须写：

1. **现象**（怎么复现、影响谁）；
2. **根因**（为什么它能被写出来）；
3. **堵法**（哪条检查/哪条测试/哪份文档不会再让它出现）；
4. **如果只是误操作**，写明它是误操作。

Lead 合并时逐条核对这四问——**缺第 3 问的退回重做**。

## 5. 与「不要防御性石山」的边界（两条不冲突）

这两条看起来矛盾，实际是分工：

| 场景 | 该怎么做 |
|---|---|
| **一次性的、不可能再发生的输入** | 不为它加代码（那是防御性石山）——例如「正文最多一万字」这种入口约束，就不该在 AI 审核里再截断一次 |
| **一类会反复出现的缺陷来源** | 必须堵（那是根因）——例如「配置键名漂移」会反复出现，所以要有检查 |

判断标准：**问「这个保护将来会不会用到」**。只为当下这一个不可能的输入写的分支 = 石山；为一类已经出现过两次的缺陷写的检查 = 根因堵法。

## 6. 检查（这条本身也要有落点）

- [ ] 每个提交里如果修了缺陷，提交信息必须含「根因」与「堵法」两行（找不到堵法就写「堵法：待定 + 原因」）；
- [ ] 缺陷复审（Lead 合并时）逐条核对 §4 的四问；
- [ ] 每堵一次根因，检查它是否已经被 `完全重构/原项目失败复盘.md` 的 12 条根因覆盖；**没覆盖的，补进那份文档**（那才是这类知识的归处）。

## 7. 通用铁律：**验收要看产物，不看命令的退出码**（2026-10-13 补）

今天出现了**三次同型的坑**，共同点是「**工具报告成功，产物没变**」：

| 工具 | 现象 | 发现方式 |
|---|---|---|
| `write` 写大文件 | 返回成功，落盘被**静默截断**（`read` 还返回带旧内容的过期快照） | 核对字节数才发现 |
| `grep` / `read` | 返回**过期快照**（文件正在被别的 agent 写） | 与 `pwsh` 读原始字节对比才发现 |
| Chrome 无头出图 | 服务已停时**静默不覆盖旧 PNG**，退出码仍是 0 | 看文件大小与 hash 没变才发现 |

**铁律：任何「生成产物」的操作，验收必须看产物的属性 —— 时间戳 / 大小 / 内容 / hash —— 不看命令的退出码。**

适用范围（不只截图）：

- **出图**：出完看时间戳与内容（不是「命令没报错」）；**停掉服务之后不许再出图**；
- **写文档/代码**：写完核对字节数或行数（大文件必做）；
- **ent 生成 / 构建**：看生成物的 mtime 与关键内容（例如 `boardacl/boardacl.go` 里的 `Table` 常量），不是看 `go generate` 的退出码；
- **跑迁移**：看真库里的表与列（`information_schema`），不是看执行退出码；
- **跑测试**：看有没有真的断言到东西（**变异验证**：把修复退回去，确认会红）。

### 7.1 这条与「堵根因」的关系

它不是根因堵法，它是**让根因能被看见的前提**：
如果验收只看退出码，那么「产物没变」与「产物正确」长得一模一样 —— 后面所有的检查都会变成假绿。
所以这条排在前面：**先保证你看到的确实是产物本身，再谈产物对不对。**
