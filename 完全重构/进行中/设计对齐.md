## 1. 结论

**三页已经同源（12-topic / 14-home 的卡片族 / 11-profile 的 hero），其余全部有偏差。**
偏差分三类，其中第 ① 类最致命 —— 它不是「不好看」，是「点了没反应 / 数据永远是空的」：

1. **契约字段名错，功能静默失效**（第 3 节，本轮修了 4 条）；
2. **产品页手写了 DevRoom 已有的件**（第 2 节 B）；
3. **DevRoom 整页/整块没被用上**（第 2 节 A）。

## 4. 本轮（2026-10-14）做了什么

**后端新增契约（先定契约再补功能）**

    GET  /api/v1/notifications/settings       -> { alert, reply_scope, mention_scope, like_alert }
    PUT  /api/v1/notifications/settings       -> 同上（全量四字段；值域只有 all | none）

- 存储层 `user_notice_settings`（迁移 0018）**早就在**，缺的只是一个写入口和两个 HTTP 端点；
  `notify` 域的 `NoticeSetting` 端口原先只有 `Get`，本轮补 `Set` + `UpsertNoticeSetting`（一人一行）。

## 5. 后端契约待定（要人拍板，不是「顺手做」）

1. **消息屏蔽词**（DevRoom 10-messages 的设置项）：后端没有表、没有端点。已按规矩先从稿里撤掉 ——
   要放回来得先定：屏蔽词命中的是「通知正文」还是「私信正文」、以及命中后是丢弃还是折叠。
2. **重发激活码**：现在必须已登录（`RequireLogin`）。而「刚注册完没收到码」是它最主要的场景，
   那时没有会话。两条路：给 `/auth/email/resend` 也收 `{username|email}`（要有 IP 限流，`ResendVerify` 已带 IP），
   或者注册即建会话（改注册的副作用面更大）。**本轮没动这块**——它是认证边界，不该顺手改。
3. **通知 `kind` 多值**：信息中心要把「系统通知」做成 `system + review + sanction + reward` 一档，
   而现在 `?kind=` 只收单值。要么后端收逗号分隔，要么前端分四次请求（不推荐）。
4. **首页搜索的用户档**：`GET /search?type=users` 后端**已实现**（`app/search_endpoint.go:109`），
   前端只是没有函数。接上就能同时补齐「搜人」与 `PeerPicker`。
