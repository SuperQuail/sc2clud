## 3. 本轮补的契约：人工审核队列

### 为什么非补不可

AI 判定只有「明确合规」才写 `approved`（d7 §1 的实现口径）；拿不准的一律留在 `pending`。
而公开流的可见性谓词只有一条：`visibility='normal' AND review_state='approved'`
（`forum/internal/forum/pgsql/topics.go` 的四条列表 SQL 全用它）。
于是 **「AI 拿不准」= 帖子从首页 / 分区页 / 搜索 / 个人主页同时消失**，作者只看到审核横幅，
**而在补这两条端点之前，没有任何方式能把 `pending` 变成 `approved`** ——
队列索引 `idx_topics_review_queue`（0004）从建库起就一直是空的。

### 契约

    GET /api/v1/admin/topics?state=pending|rejected|all&board=<slug>&q=&limit=&cursor=
        perm: post.review
        → { data: ReviewQueueItem[], next_cursor }

    POST /api/v1/admin/topics/{id}/review
        perm: post.review
        body { action: "approve" | "reject", note }
        → 200 ReviewQueueItem（更新后的那一条）
        副作用（与判定**同一个事务**）：topics 三列 + audit_logs 一行 + notify:review 一条

    ReviewQueueItem:
      id, board{slug,name}, author{handle,nickname,avatar_hash,avatar_small_hash},
      kind, title, excerpt, review_state, review_note, review_source, created_at

### 几个刻意的取舍（写下来，免得下次再讨论一遍）

1. **没有 `request_revision`**：`topics.review_state` 只有三值（0004 的 `ck_topics_review_state`），
   而「请求修改」在作者那一侧与 `rejected` **完全同形**（同一张横幅 + 同一条 `review_note`）。
   加第四态是 schema 变更而没有用户可感知的差别。作者改完 1 楼正文会自动回到 `pending`（见下）。
2. **`state` 没有 `approved`**：部分索引的谓词是 `review_state <> 'approved'`，查它用不上索引；
   而「看已通过的」不是队列要做的事。
3. **拒绝必须给理由**：作者在帖子页看到的就是这条 `review_note`；允许空理由等于让人收到
   「未通过」而不知道为什么。
4. **判定落 `review_source='manual'`**：AI 任务见到 manual 直接返回（d7 §1 铁律：AI 绝不覆盖人工判定）。
5. **`approve` 清空 `review_note`**：上一版的拒绝理由不该挂在一条已通过的主题上。
6. **没有「AI 说了什么」这一列**：`topics` 表**从来就没有** `ai_review_note`，AI 的理由本来就写在
   `review_note` 里，谁写的看 `review_source`（ai / manual）。不要再造第三列。

## 4. 顺带修掉的两个后端 bug（都在本轮验证路径上撞出来的）

### 4.1 `PATCH /topics/{id}` 带 `content_md` **必然 500**

`forum/internal/forum/pgsql/topics.go` 的 `ResetTopicReview` 写的是
`SET review_state='pending', ai_reviewed=false, ai_review_note=NULL`，
而 `topics` 表**没有 `ai_reviewed` / `ai_review_note` 这两列**（任何迁移里都没有）。
后果：**「编辑帖子正文」100% 失败**（整个事务回滚），而只改标题没事 ——
所以它不会被「随便点一下」发现。已改为清真实存在的四列
（`review_state='pending', review_source=NULL, review_note=NULL, reviewed_by=NULL, reviewed_at=NULL`），
语义仍是「这份内容还没有任何判定」，并补了用例 `TestEditBodyResetsReview`。

### 4.2 消息设置的四个字段**没有端点**（本轮补上）

存储层 `user_notice_settings`（迁移 0018）早就在、领域端口 `NoticeSetting` 也早就读得到，
缺的只是写入口与两个 HTTP 端点。本轮补 `GET/PUT /api/v1/notifications/settings`
（值域只有 `all | none` —— 拍板 §8.3 说本产品没有关注用户，0018 把 `followed` 删了）。

## 6. 本轮已知的测试缺口（诚实记下，别当成已覆盖）

- 审核队列的 4 条用例走的是 **service 层**；HTTP 层的绑定 / 中间件 / 响应包络**没有用例**。
  仓库里有现成的 HTTP 台（`forum/internal/forum/handler_test.go` 的 `TestRoutesEndToEnd`），
  照着补两条即可（列表的包络是 `{data,next_cursor}`，判定是单对象 `{data}`）。
  注意那个台注入的 `perm` 中间件是**空实现**：它证明不了「路由级权限被挂上」，
  只能证明 service 里的 `requirePerm`。真实权限点由 `app` 层的 `svc.Perm(...)` 挂，
  那一条要到 `internal/app` 的端到端用例里验。
- `?kind=` 多值（第 5 节第 6 条）**没做**：`notify/pgsql` 的 `listSQL` 仍是单值等值比较。
