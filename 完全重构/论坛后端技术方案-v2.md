> 本文档用于指导开发，执行者可能是其他 AI 或开发者。部署与 dev/prod 流程见 `完全重构/部署与开发流程.md`。
> 文档里的“必须 / 禁止”是硬性要求，不允许自行替换成别的库或别的写法。
> 遇到文档没有覆盖的情况，先按“第 14 章 开发规范”的原则处理，处理不了就停下来提问，不要猜。

## 1. 背景与约束

### 1.1 项目

论坛网站后端，包含：用户、认证、版块、主题帖、回复、点赞、收藏、拉黑、举报、**站内私信**、**头衔与等级**、通知、站内搜索、**资源帖的问题与建议（issue）**、赞赏（打赏，站点不经手资金）、邮件发送、**图片上传**、**外链下载（启动器 / 资源包）**。

**明确不做**：网盘、文件托管、对象存储、转码与缩略图。服务器进程**不承载任何文件字节**；安装包与资源文件一律以外部直链形式存放，只做 302 转链与计数（见第 11 章）。

### 1.2 服务器

2 核 CPU、2 GB 内存。因此：

- 数据库用 **PostgreSQL**（原方案的 SQLite 已作废；完整表结构见 `完全重构/数据库设计-postgresql.md`）。
- **Redis 现在就部署**（2026-10-12 已在服务器上线，仅回环 127.0.0.1:6379，纯缓存不落盘）：缓存、限流、锁、热点计数走 Redis。任务队列**仍在 PostgreSQL**（jobs 表 + SKIP LOCKED），理由见 §7.4——`EnqueueTx` 的「与业务数据同事务入队」是核心性质，挪到 Redis 就破了。
- 只运行一个业务进程（HTTP、后台任务、定时任务都在同一个进程里）。**除 PostgreSQL 之外不引入外部常驻组件**（没有 Meilisearch、没有独立 worker、没有 pgbouncer）。
- 前端**不引入 Node 运行时**（SPA + Go 注入 meta 壳，见前端方案 §2）。
- 缓存 / 限流 / 队列 / 搜索仍按接口编写，为以后换 Redis 与多实例留切换点。

### 1.3 存量数据

**已定案（Q0）**：只导入旧站的**用户**——帖子、回复、图片、文件、通知、打赏记录一律不迁；而且新 users 表是**全新设计**，导入是一次语义映射而不是列复制。实现为独立子命令 `forum import-users`，完整映射规则与冲突处理见 **`完全重构/数据库设计-postgresql.md` 第 10 章**。M0–M8 的验收标准都不含它。

## 4. 分层与依赖规则

### 4.1 调用方向

    handler  →  service  →  ent client / platform 接口
                        ↘  其他业务模块（只能通过本模块 deps.go 中定义的小接口）

### 4.2 import 规则（违反任何一条都要改）

1. platform 下的包禁止 import 任何业务模块（user、auth、forum、media、release、notify、reward）。
2. platform 可以 import internal/ent（生成代码）和 internal/config 的子配置类型。
3. 业务模块之间禁止直接 import 对方包。需要对方能力时，在自己的 deps.go 里定义接口，由 app 层把对方的 *Service 传进来。
4. 只有 internal/app 可以 import 所有包。
5. handler 只能调用本模块的 service，不能直接用 ent client。
6. service 不能出现 gin 的任何类型（*gin.Context 等），只接收 context.Context。

deps.go 的形状：在**使用方**的 `deps.go` 里定义它真正用到的方法的小接口（例如 reward 只需要 `GetBasic(ctx, userID) (UserBasic, error)`），由 app 层把 `*user.Service` 传进来。Go 的隐式接口让 user 包完全不需要知道 reward 的存在。

### 4.3 跨模块有副作用的联动

例如“打赏到账后通知作者”：reward 不直接调用 notify，而是在同一个数据库事务里投递一个后台任务（queue.EnqueueTx），由 notify 的任务处理函数处理。这样两个模块解耦，失败可以重试。

## 5. 组装层（internal/app）

### 5.1 原则

- 每个组件通过构造函数拿依赖。禁止全局变量，禁止在 init() 里初始化任何东西。
- 构造函数接收接口、返回具体类型（*Service）。
- 只传子配置：auth.NewService(cfg.Auth, ...)，禁止把整个 *config.Config 传进业务模块。
- 资源创建时记录关闭函数，关闭时倒序执行。
- 启动时尽早失败：数据库打不开、迁移版本不对、图片目录不可写、**发信凭据主密钥缺失**，直接返回错误退出。（发信账号本身允许为空 —— 它是后台配置的，见 8.2）

### 5.2 Infra

    // internal/app/infra.go
    type Infra struct {
        DB      *ent.Client          // 写库（也用于事务）
        DBRead  *ent.Client          // 只读库
        Cache   kv.Cache
        Limiter ratelimit.RateLimiter
            Queue   queue.Queue
        Worker  queue.Worker
        Mail    mail.Sender          // 实际是 *mail.Router
        Pay     payment.Gateway
        Search  search.Searcher
        Images  image.Store
        Captcha captcha.Verifier
        Counter *counter.Buffer
        MD      *markdown.Renderer
        Clock   clock.Clock
        Log     *slog.Logger

        closers []func() error
    }

    func NewInfra(ctx context.Context, cfg *config.Config) (*Infra, error) {
        in := &Infra{Clock: clock.Real{}, Log: newLogger(cfg.Log)}

        w, r, closeDB, err := db.Open(cfg.DB)
        if err != nil {
            return nil, fmt.Errorf("open db: %w", err)
        }
        in.DB, in.DBRead = w, r
        in.closers = append(in.closers, closeDB)

        switch cfg.KV.Driver {
        case "memory":
            in.Cache = memkv.New(cfg.KV.Memory)
            in.Limiter = memlimit.New(cfg.KV.Memory.LimiterKeys)
            default:
            in.Close()
            return nil, fmt.Errorf("unknown kv driver %q", cfg.KV.Driver)
        }

        switch cfg.Queue.Driver {
        case "postgres":
            q := pgqueue.New(in.DB, in.Clock, in.Log, cfg.Queue.PG)
            in.Queue, in.Worker = q, q
        default:
            in.Close()
            return nil, fmt.Errorf("unknown queue driver %q", cfg.Queue.Driver)
        }

        // 邮件：账号在数据库里（管理员后台配置）。这里只装配加密器与 Router。
        crypter, err := mail.NewCrypter(cfg.Mail.KeyHex, cfg.Mail.OldKeyHex)
        if err != nil {
            in.Close()
            return nil, fmt.Errorf("mail crypter: %w", err)
        }
        in.Mail = mail.NewRouter(in.DB, crypter, in.Clock, in.Log) // 账号按需从库读，带 30s 缓存

        img, err := localstore.New(cfg.Image)
        if err != nil {
            in.Close()
            return nil, fmt.Errorf("open image store: %w", err)
        }
        in.Images = img

        in.Captcha = imagecaptcha.New(cfg.Captcha, in.Cache, in.Clock)

        // ……其余组件同理
        return in, nil
    }

    func (in *Infra) Close() error {
        var errs []error
        for i := len(in.closers) - 1; i >= 0; i-- {
            errs = append(errs, in.closers[i]())
        }
        return errors.Join(errs...)
    }

### 5.3 Modules

    // internal/app/modules.go
    type Modules struct {
        User    *user.Service
        Auth    *auth.Service
        Forum   *forum.Service
        Media   *media.Service
        Release *release.Service
        Notify  *notify.Service
        Reward  *reward.Service
    }

    func NewModules(cfg *config.Config, in *Infra) *Modules {
        m := &Modules{}
        // 顺序：被依赖的先创建
        m.User = user.NewService(cfg.User, in.DB, in.DBRead, in.Images, in.Clock)
        m.Auth = auth.NewService(cfg.Auth, in.DB, in.Limiter, in.Queue, in.Captcha, m.User, in.Clock)
        m.Media = media.NewService(cfg.Image, in.DB, in.DBRead, in.Images, in.Clock)
        m.Forum = forum.NewService(cfg.Forum, in.DB, in.DBRead, in.Cache, in.Queue, in.Search, in.Counter, in.MD, m.Media, in.Clock)
        m.Release = release.NewService(in.DB, in.DBRead, in.Counter, in.Clock)

### 5.4 运行与优雅关闭（forum run）

    func Run(ctx context.Context, cfg *config.Config) error {
        ctx, stop := signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)
        defer stop()

        in, err := NewInfra(ctx, cfg)
        if err != nil {
            return err
        }
        defer in.Close() // 第 5 步：倒序关闭数据库等资源

        if err := checkMigrated(ctx, in); err != nil { // 迁移版本不对就拒绝启动
            return err
        }

        m := NewModules(cfg, in)
        registerTasks(in.Worker, m, in)
        srv := newHTTPServer(cfg.HTTP, in, m)

        g, gctx := errgroup.WithContext(ctx)
        g.Go(func() error { return in.Worker.Run(gctx) })
        g.Go(func() error { return runCron(gctx, in, m) })
        g.Go(func() error { return in.Counter.Run(gctx) })
        g.Go(func() error {
            if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
                return err
            }
            return nil
        })
        g.Go(func() error {
            <-gctx.Done()
            shutdownCtx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
            defer cancel()
            return srv.Shutdown(shutdownCtx) // 第 1 步：停止接收新请求，等进行中的请求结束
        })
        // 第 2 步：Worker.Run 收到取消后等进行中的任务结束再返回
        // 第 3 步：cron 收到取消后等本轮任务结束（备份的临时文件要清掉）
        // 第 4 步：Counter.Run 收到取消后把内存里的计数写回数据库再返回
        return g.Wait()
    }

关闭顺序必须是：HTTP 停止 → worker 停止 → cron 停止 → 计数写回 → 关闭数据库。

## 7. 抽象层（Redis 为主，内存实现只留给派生数据）

原则：按用途定义小接口，不做“通用 KV / 模拟 Redis”的大接口。**接口保留，实现以 Redis 为主**；内存实现只用于「丢了能重建、且不值得进网络」的数据（例如分词表缓存、静态派生量）。**Redis 不可用时的行为必须明确写出来**：缓存类降级为直查库，限流类**拒绝放行**（宁可 429 也不放行），见 §7.5。

### 7.1 职责划分

| 用途 | 现在的实现 | 以后的实现 | 备注 |
|---|---|---|---|
| Session | PostgreSQL 表 | 可以一直用 PG | 封号时按 user_id 删除全部 Session |
| 缓存 kv.Cache | **Redis** | 保持 Redis | 丢了没关系（验证码、热点缓存、权限集合用它） |
| 限流 ratelimit.RateLimiter | **Redis** | 保持 Redis | 重启不再清零；Redis 故障时**拒绝放行**（安全优先） |
| 热点计数 counter | **Redis 计数 + 定时批量写回库** | 保持 | 写回逻辑与内存版一致 |
| 邮件额度 | PG 表 mail_quota | 继续用数据库 | 必须持久化，禁止放内存 |
| 任务队列 queue | 自写 PG 队列（jobs 表） | asynq 或 river | 见 7.4 |
| 搜索 search | tsvector + bigram | Meilisearch | 见 7.6 |
| 图片 image.Store | 本地内容寻址目录 | 对象存储 | 见第 10 章 |

### 7.4 任务队列

接口：

    // internal/platform/queue/queue.go
    type Task struct {
        Type      string        // 使用 types.go 中的常量
        Payload   []byte        // JSON
        UniqueKey string        // 可选，相同 key 的未完成任务只保留一个
        RunAt     time.Time     // 零值表示立即执行
        MaxRetry  int           // 0 表示使用默认值 5
        Priority  int           // 越大越优先：验证码邮件 10，通知邮件 0
    }

    type Queue interface {
        Enqueue(ctx context.Context, t Task) error
        // 和业务数据在同一个事务里提交：事务回滚，任务也不会存在
        EnqueueTx(ctx context.Context, tx *ent.Tx, t Task) error
    }

    type Handler func(ctx context.Context, payload []byte) error

    type Worker interface {
        Handle(taskType string, h Handler)
        // ctx 取消后等待进行中的任务结束再返回
        Run(ctx context.Context) error
    }

    // 处理函数返回这个错误表示不要重试，直接进入 dead
    var ErrSkipRetry = errors.New("queue: skip retry")

任务类型常量：

    // internal/platform/queue/types.go
    const (
        TypeMailSend        = "mail:send"
        TypeNotifyReply     = "notify:reply"
        TypeNotifyReward    = "notify:reward"
        TypeRewardReconcile = "reward:reconcile"
        TypeSearchIndex     = "search:index"
        TypeImageGC         = "image:gc"
        TypeJobCleanup      = "queue:cleanup"

**unique_key 必须是部分唯一索引**，普通唯一索引会让任务 done 之后永远无法再次入队：

    // internal/ent/schema/job.go
    func (Job) Indexes() []ent.Index {
        return []ent.Index{
            index.Fields("unique_key").
                Unique().
                Annotations(entsql.IndexWhere("unique_key <> '' AND status IN ('pending','running')")),
            index.Fields("status", "run_at"),
        }
    }

实现要点（PostgreSQL 版；DDL 见 `数据库设计-postgresql.md` §4.10）：

1. 领取任务：`UPDATE jobs SET status='running', locked_until=now()+interval '5 min', attempts=attempts+1 WHERE id = (SELECT id FROM jobs WHERE status='pending' AND run_at<=now() ORDER BY priority DESC, run_at LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *`。**不再需要 SQLite 时代的「先查再条件更新」两步**。（ent 需开 `sql/lock` 特性。）
2. 轮询每 1 秒；Enqueue 成功后向带缓冲 channel 发信号立即唤醒。空轮询只记 Debug。
3. 并发按档位：**small 4 / standard 8**（见 `性能与容量.md` §2）；PG 下不再受单写者限制，但仍受 CPU 与连接池约束。
4. 成功 status=done。
5. 失败：attempts < max_retry 时 pending，run_at = now + 退避（10s × 2^attempts，上限 1 小时），记 last_error；否则 dead。返回 ErrSkipRetry 直接 dead。
6. 崩溃恢复：定时把 status=running 且 locked_until < now() 的改回 pending。
7. 清理：done 保留 7 天；dead 保留 30 天。
8. 处理函数 panic 必须 recover，按失败处理；处理函数必须幂等。

**关于 river（Q5）**：river 支持 PostgreSQL，所以“river 不存在”从来不是理由。本方案仍然选择自写队列，理由是：① 本方案的核心设计是“任务与业务数据同库同事务入队”，自写能让 Job 和业务表共用一份 schema、一套 ent 生成代码，而 river 会带进它自己的一整套表；② 自写只有约 200 行 + 契约测试，行为完全可控；③ 少一个重量级依赖。M1 做完后回头评估一次：若自写在崩溃恢复/退避上反复出问题，就换 river —— 换的时候 `EnqueueTx` 的调用点不需要改。

### 7.5 热点计数（浏览量等）

- counter.Buffer 在内存里用 map + 互斥锁累加，例如 view:topic:<id> += 1。
- 每 15 秒把累计值批量写回数据库（ent 的 AddViewCount），写回后清空。
- 进程关闭时必须先写回一次再退出（见 5.4）。
- 点赞数不走这里：点赞要写 Like 表保证唯一，计数在同一事务里 AddLikeCount(1)。

### 7.6 全文搜索

接口不变（`search.Searcher`：Index / Delete / Search），**实现换成 PostgreSQL**：

- 索引表 `topic_search` + `tsvector` 生成列 + GIN；写入与查询都切 **bigram**（同一套切法，两边不一致就是「搜不到」）。
- **查询必须 JOIN topics 过滤 status**：`pending`/`rejected`/`hidden`/`deleted` 不许被游客搜到（盲审安全项 D2）。
- 完整 DDL、查询写法、扩展依赖与刷新策略见 `数据库设计-postgresql.md` 第 5 章。
- 索引更新走后台任务 `search:index`，不在发帖请求里同步执行。

|---|---|

### 8.3 Router 发送流程

0. **占额度的粒度是“一次投递（MailLog）”，不是“一次尝试”**。Router 收到请求时先看 `m.QuotaProvider` / `m.QuotaDay`：
   - 都为空：这是第一次尝试 → 走第 2 步占额度，并把结果回写给 MailLog。
   - 已有值：这是重试 → 直接沿用该账号（前提：该账号当天仍有余量），**不再 AddCount**；该账号已满则换账号，并更新 MailLog。

1. 按 priority 从高到低排序候选账号（同一家提供商的多个账号各自独立参与排序）。
2. 占额度：在写库事务里查 MailQuota(account, day)，count >= daily_limit 则跳过该账号；否则 upsert AddCount(1)。
3. 调用 Provider.Send：
   - 成功：返回。
   - ErrQuotaExceeded：把该账号当天的 count 设为 daily_limit，并熔断（内存记录，key 为账号名 + 当天日期），然后尝试下一个账号。
   - ErrTemporary：尝试下一个账号；所有账号都失败时，把 ErrTemporary 返回给任务队列，由队列退避重试（重试不会重复占额度，见第 0 步）。
   - ErrPermanent：不换账号，直接返回（任务处理函数会把它转成 ErrSkipRetry）。
4. 所有账号都没有额度：返回 ErrNoProvider，任务延迟到下一个重置时间之后重试。

**为什么不“先占后不退还”**：额度账是用来做账号轮换的，不是计费账。真正的浪费来自“一次投递重试 5 次占 5 次额度”，那个必须掐掉；至于“发出去了但对方没收到”这种一次性损耗，接受。

### 8.4 业务侧如何发邮件

- 业务代码禁止直接调用 mail.Sender。一律投递 mail:send 任务。
- 投递前（或在同一事务中）创建一条 MailLog（status=pending，idempotency_key 唯一，格式如 verify:<user_id>:<token_id>）。
- mail:send 任务的 payload 只放 MailLog 的 id。
- 任务处理函数：读取 MailLog；如果 status=sent 直接返回成功（幂等）；否则渲染模板 → Router.Send（带上 MailLog 的 quota_provider / quota_day）→ 更新 MailLog（含新的额度占用与 attempts）。
- 优先级：验证码、找回密码 Priority=10；通知类 Priority=0，并且可以合并成摘要邮件。
- 【待确认 Q8】resend-go 是否支持传 Idempotency-Key 请求头，支持就传 MailLog.idempotency_key。

## 9. 认证与安全

### 9.1 注册与登录

- 密码用 argon2id 哈希：**time=2, memory=32MB, threads=2, keyLen=32**，盐 16 字节随机。存储格式：$argon2id$v=19$m=32768,t=2,p=2$<salt>$<hash>。
- **必须限制并发哈希数**：进程内信号量，最多 2 个并发（make(chan struct{}, 2)）。理由是哈希一次要 32MB，2 核 2GB 的机器上并发 10 个登录就是 320MB 的瞬时分配，GC 压不住。取不到信号量时等待，超过 3 秒返回 503（并记 Warn 日志）。
- 校验密码时用 crypto/subtle.ConstantTimeCompare。
- 登录失败不要提示“用户不存在”还是“密码错误”，统一返回“账号或密码错误”。
- 注册必须完成邮箱验证才能登录（EmailToken，purpose=verify）。

### 9.2 会话与认证中间件

#### 会话本身

- 登录成功生成 32 字节随机 token（crypto/rand），base64url 编码后放 Cookie，**数据库只存它的 SHA-256**。
- Cookie 属性：HttpOnly、Secure（https 时）、SameSite=Lax、Path=/、有效期 30 天。
- **Cookie 名必须可配**（`server.cookie_name`，默认 `forum_session`）：生产 `/` 与测试 `/dev/` 同域部署时，两个实例必须用不同的名字，否则两边会话互相顶掉。
- 封号、改密码、管理员强制下线时，删除该用户的全部 Session。

#### 中间件只做认证，不做授权

它只干一件事：**把请求里的凭证变成上下文里的 Principal**。

- 不判权限（那是 `Perm(...)` 中间件与 service 的事）
- **不因为没登录就报错**（公开页面游客也要走这条路）
- 不读 body、不写响应体（除了清掉失效 Cookie）

一次请求的路径：

    有 Cookie？
    ├─ 没有 ─────────────────────► 放行（游客），什么都不塞
    └─ 有 ──► sha256(token)
               ├─ 缓存命中（key = token 摘要，TTL 60s）──► 直接得到 Principal
               │    ⚠ 缓存条目**必须同时带 status**，否则封号在 60 秒内不生效（盲审 B1：
               │      这一条与 M2 验收「封号后立刻 401（不能等 60 秒）」直接冲突）
               └─ 未命中 ──► 一次 JOIN 查 sessions ⋈ users（读库）
                             ├─ 无行 / 已过期 ──► 清 Cookie，当游客放行
                             └─ 有行 ──► 组装 Principal ──► 回填缓存

> 缓存 key 用 **token 摘要**而不是 userID：同一用户多设备登录时各自独立；封号时按 userID 批量失效也做得到（维护 userID → 摘要集合的二级索引，或直接清整张缓存）。

#### 放什么进 context

    // internal/auth/principal.go
    package auth

    // 私有类型做 key：防止别的包用字符串 key 撞车
    type ctxKey struct{}

    type Principal struct {
        UserID    int64
        PublicID  string
        Nickname  string
        SessionID string    // token 的 sha256，用于「登出当前设备」/ 踢下线
        CSRF      string    // 会话里的 csrf_token
        EmailVerified bool  // 对应 users.email_verified_at（原写 Activated，与 6.6 的列名不一致）
        Perms     authz.Set // 已展开的全局权限点集合
        BoardIDs  []int64   // 他是版主的版块（作用域判定用）
        IsSuper   bool
    }

    func PrincipalFrom(c *gin.Context) (*Principal, bool)

**传参约定**：service 方法接收 `*auth.Principal`（或 `authz.Actor`），**不从 context 里取**。这样 service 既能做 `authz.Require`，又不必再查一次库。

#### 代码骨架

    // internal/auth/middleware.go
    func LoadPrincipal(svc *Service) gin.HandlerFunc {
        return func(c *gin.Context) {
            token, err := c.Cookie(svc.cookieName())
            if err != nil || token == "" {
                c.Next()                        // 游客，不是错误
                return
            }
            p, err := svc.Resolve(c.Request.Context(), token)
            switch {
            case errors.Is(err, ErrSessionInvalid):
                svc.ClearCookie(c)              // 过期/伪造：清掉，当游客
                c.Next()
            case err != nil:
                httpx.Fail(c, err)              // 真故障（库挂了）才中断
                c.Abort()
            default:
                c.Set(ctxKey{}, p)
                svc.TouchAsync(p.SessionID)     // last_seen_at，见下
                c.Next()
            }
        }
    }

    func RequireLogin() gin.HandlerFunc {
        return func(c *gin.Context) {
            if _, ok := PrincipalFrom(c); !ok {
                httpx.Fail(c, apperr.ErrUnauthorized)   // 401
                c.Abort()
                return
            }
            c.Next()
        }
    }

    // 路由层权限点（与 9.8 配套）
    func Perm(perms ...string) gin.HandlerFunc {
        return func(c *gin.Context) {
            p, ok := PrincipalFrom(c)
            if !ok {
                httpx.Fail(c, apperr.ErrUnauthorized)   // 401
                c.Abort()
                return
            }
            if !p.IsSuper && !p.Perms.HasAll(perms...) {
                httpx.Fail(c, apperr.ErrForbidden)      // 403
                c.Abort()
                return
            }
            c.Next()
        }
    }

#### 五个必须定死的决策

1. **token 无效 = 游客，不是 401**。公开页面游客也要过这个中间件；坏 token 直接清 Cookie 放行，让 `RequireLogin()` 去出 401。否则首页挂着过期 Cookie 的人会看到 401。
2. **`status` 每请求校验，不进权限缓存**。封号必须立刻生效：`Resolve` 每次都看 `users.status`（反正已经在 JOIN 结果里，零额外成本），banned 一律按 `ErrSessionInvalid` 处理。权限集合照旧缓存 60 秒。
3. **`last_seen_at` 要节流 + 异步**。写库只有 1 个连接，不能每请求都写：

       func (s *Service) TouchAsync(sessionID string) {
           now := s.clock.Now().Unix()
           if last, ok := s.touched.Get(sessionID); ok && now-last < 600 {
               return                         // 10 分钟内不再写
           }
           s.touched.Add(sessionID, now)
           select {
           case s.touchCh <- sessionID:       // 有缓冲的 channel
           default:                           // 满了就丢：丢掉的只是「在线时间不准」，不影响正确性
           }
       }

   后台一个 goroutine 收 channel，按 500ms 或攒够 100 条**批量 UPDATE**。请求路径上零写库。
4. **会话续期用滑动式**：批量刷 `last_seen_at` 时顺带把 `expires_at` 续到 `now + 30d`，但**每 24 小时才真的改一次** `expires_at`，别把它变成新的写热点。（不做续期也行，但活跃用户会齐刷刷掉线。）
5. **401 与 403 的分界**：未登录 → 401（`common.unauthorized`），已登录但缺权限 → 403（`common.forbidden`）。两者都在中间件里统一出，service 层复用同一个函数。

#### 中间件顺序

    requestid → access log → recover → LoadPrincipal → 限流 → Perm(...) → handler

- `LoadPrincipal` 必须在限流前：限流要按 userID 计数。
- `Perm` 放在限流后：未授权流量不该反复触发权限判定。
- `/static`、`/healthz` 这类**不要挂 `LoadPrincipal`**（白查一次库）。

#### SQL 与索引

    -- 一次拿全，不要查两次
    SELECT s.token_hash, s.csrf_token, s.expires_at,
           u.id, u.public_id, u.nickname, u.status, u.email_verified_at
      FROM sessions s JOIN users u ON u.id = s.user_id
     WHERE s.token_hash = ?;

    CREATE UNIQUE INDEX idx_sessions_token ON sessions(token_hash);
    CREATE INDEX idx_sessions_expires ON sessions(expires_at);   -- 过期清理用

权限集合（`users.role_id ⋈ role_permissions`）走 60 秒缓存，**不要每请求 join**。

#### 必须写的测试

| 用例 | 断言 |
|---|---|
| 无 Cookie 访问公开页 | 200，`PrincipalFrom` 返回 false |
| 伪造 token | 200（当游客）+ 响应里带清除 Cookie 的 `Set-Cookie` |
| 过期会话 | 同上 |
| 正常登录后访问需登录接口 | 200，Principal 的 UserID / Perms 正确 |
| **封号后立刻请求** | 写接口 401（**不能等 60 秒**） |
| 改密码后用旧 Cookie | 立刻失效（该用户全部 session 被删） |
| 连续 1000 次请求 | `last_seen_at` 的 UPDATE **不超过 1 次** |
| 权限缓存 | 60 秒内不查库；后台改权限后立刻失效 |


### 9.3 CSRF

使用 Cookie 鉴权，所以必须防 CSRF：

- 默认部署（前端与后端同域）：SameSite=Lax + Origin 校验即可。
- 对 POST、PUT、PATCH、DELETE 请求，检查 Origin 头（没有 Origin 就检查 Referer），必须在配置的允许列表中，否则返回 403。
- **若开启跨站部署**（http.cors.enabled=true）：Cookie 必须同时切成 SameSite=None; Secure，CORS 必须带 credentials 且 origin 白名单精确匹配。这两处是一个开关的两个半边，禁止只改一半 —— 只改 CORS 不改 Cookie，浏览器不会带 Cookie，登录态直接失效。
- 跨站部署是**可选配置**，默认关闭。

### 9.5 人机验证（自建，不依赖外部服务）

    // internal/platform/captcha/captcha.go
    type Verifier interface {
        // 下发一道题，返回 id 与图片字节（PNG）
        Issue(ctx context.Context, ip string) (id string, png []byte, err error)
        // 校验答案；一次性消费，无论对错都作废
        Verify(ctx context.Context, id, answer string) error
    }

imagecaptcha 实现要点：

- 纯标准库：image + image/png + crypto/rand。生成 4 位字符或简单算术题，加噪点与轻微扭曲。
- 答案存 kv.Cache，key = captcha:<id>，TTL 5 分钟；**校验后立即 Del（无论对错）**，防爆破。
- 端点：GET /api/v1/captcha 返回 { id, image_base64 }。
- **默认策略（auth.captcha.mode=off）**：不要求验证码。注册有邮箱验证兜底，登录有 §9.4 的限流兜底。
- **风险模式（mode=on_failure）**：同一 IP 在 10 分钟内登录/注册失败 ≥5 次后，后续请求必须带验证码；计数放 kv.Cache，TTL 10 分钟。这是默认建议值。
- **强制模式（mode=always）**：注册、登录、发帖全部要求验证码，用于被刷时应急（改配置即可，不改代码）。
- 禁止在服务端保存验证码明文超过 TTL，禁止把答案回传给前端。

### 9.7 内容安全

- 用户提交 Markdown，后端在写入时渲染：goldmark → bluemonday.UGCPolicy() → 存入 content_html。原文存 content_md。

**@提及的存储与渲染（契约，2026-10-12 定；用户正文一律适用）**

| 项 | 约定 |
|---|---|
| 存储格式 | **标准 Markdown 链接**：`[@<昵称>](mention:<user_id>)`，例如 `[@唐天](mention:123)`。它是合法 Markdown（别的渲染器不认识 `mention:` 协议时会退化成普通链接），比自定义 token 更好互操作 |
| 真源 | **`user_id` 是唯一真源**——跳转、通知、拉黑判定、权限都用它；昵称只是**写入时的快照** |
| 渲染 | 服务端把 `mention:<id>` 的链接改写为 `<a href="/u/<id>" data-mention="<id>">@<当前昵称></a>`；**显示用 users 当前昵称**（渲染时 join），链接里的昵称快照仅在用户被删除时兜底 |
| 写入校验 | `mention:<id>` 里的 id 必须存在且未被封禁；否则 400 `content.bad_mention`；单条正文最多 20 个提及 |
| 通知 | 每个被提及者收到 `kind='mention'` 通知；**自己提及自己不通知** |
| 限流 | 与回复同一档（见 §8 限流表） |
| 前端 | 编辑器 `web/src/ui/rich/markdown-editor.tsx`（**Lexical 内核，所见即所得**），渲染 `web/src/ui/rich/markdown.ts`（marked + DOMPurify）；选人用 `GET /api/v1/users/search?q=`（按昵称前缀 + username，**重名要标记**） |

**为什么链接里也要带昵称**：链接文本能让人看懂；昵称可改、可重名（`users.nickname` 非唯一）——只存昵称会导致改名后指向错人、同名时无法消歧。
**为什么不能只存 id**：渲染与通知都需要一个可读名字；且用户被删除时要有东西可显示。

**评论区界面约定（同批定下）**：

1. **回复不带图片**——图片只有三个端点（头像、帖子配图、收款码），回复不在其中；
2. **楼中楼只允许一级**（`posts.parent_id` 的父必须是普通回复，service 层校验）；
3. **主楼与楼中楼必须看得出层级**：主楼正文 15px、楼中楼 13px，头像 md/sm，不靠缩进竖线；
4. 排序「最热 / 最新」进 URL 查询串（可分享、可后退）。
- 前端只展示 content_html，禁止展示未清洗的内容。
- 标题、昵称等纯文本字段由前端转义显示，后端限制长度并去除控制字符。
- 图片一律不接受 SVG（可内嵌脚本），只接受 PNG / JPEG / GIF / WebP。

### 9.8 授权：RBAC

**角色可以在后台配，权限点必须在代码里。** 这一节的其余内容都是这句话的推论。

#### 表

| 表 | 说明 |
|---|---|
| roles | 内置角色 `is_system=1`，不可删、key 不可改；自定义角色可增删 |
| permissions | 权限点由**迁移文件**写入，与 Go 常量一一对应。**不允许后台新增权限点** |
| role_permissions | 角色 × 权限点的勾选结果 |
| users.role_id | 用户的角色（**一个用户只有一个**，权限树是层级） |
| board_moderators | 分区版主。把「作用域」做进 RBAC，而不是另搞一套角色系统 |

**角色在 `users.role_id` 上**（单一）；权限集合 = 该角色 ⋈ `role_permissions`。

#### 内置角色（迁移里幂等插入）

| key | 说明 |
|---|---|
| user | 默认角色，注册时自动授予 |
| moderator | 版主：删帖 / 锁帖 / 禁言；是否只管某个版块由 board_moderators 决定 |
| admin | 管理员：用户、内容、站点设置、发信配置 |
| superadmin | 最高权限，**不可被降权**（防止有人把自己锁在门外）；**只能由 `forum create-admin` 授予**；系统里必须始终至少保留一个 |

#### 权限点（代码里的常量，初版清单）

    // internal/authz/permissions.go
    const (
        // 内容
        PermPostCreate    = "post.create"
        PermPostUpdateOwn = "post.update_own"
        PermPostDeleteOwn = "post.delete_own"
        PermPostDeleteAny = "post.delete_any"
        PermPostLock      = "post.lock"
        PermPostPin       = "post.pin"
        // 用户

        PermRoleAssign     = "role.assign"    // 给用户分配角色
        // 站点
        PermBoardManage = "board.manage"
        PermRewardVerify = "reward.verify"   // 人工核验 / 结算赞赏订单（12.1 的“收款码 + 人工核验”路线必需）

        PermAuditView   = "audit.view"

新增权限点 = 在常量里加一个 + 加一条迁移往 permissions 表插一行，两处必须同名。

#### 判定：路由层声明 + service 层兜底

两层都要有，不是二选一。

**路由层声明（第一道闸门）**：

    rg.POST("/topics", auth.RequireLogin(), auth.Perm(authz.PermPostCreate), h.createTopic)

    // 整组一次声明，省掉逐条重复
    admin := rg.Group("/admin", auth.RequireLogin(), auth.Perm(authz.PermSiteSetting))

好处有两个：路由表本身就是一份**权限清单**，可以直接导出成「接口 × 所需权限」对照表给管理员看；而且能写一个**遍历 gin 路由表的测试**——「非公开接口没有声明权限点就失败」，这条能永久防住新接口忘了加权限，比任何规范条文都管用。

**service 层兜底（最终保证）**：

    authz.Require(actor, authz.PermPostDeleteAny)

理由：队列任务、cron、CLI、模块间调用**都不走路由**，只靠中间件等于这些入口完全没有授权。**危险写操作（删帖、封号、改角色、改发信账号）在 service 里必须再 Require 一次。**

约定：

- 中间件 `Perm(a, b)` 默认 **AND**；需要任一满足时用 `PermAny(a, b)`。
- 401 / 403 的分界与 9.2 一致（未登录 401、缺权限 403），两处复用同一个函数。
- **作用域权限不能放在中间件里**：路由参数里只有 topic id、没有 board id，中间件要判 `board_moderators` 就得先查库。所以中间件只判全局权限点，带版块语义的判定留在 service。
- **资源归属也不能放在中间件里**：`PermPostDeleteOwn` 只回答「这类动作允不允许」，回答不了「这条是不是我的」。顺序是：先 `authz.Require(PermPostDeleteOwn)`，再判 `post.AuthorID == actor.UserID`，两者 AND；只有持有 `PermPostDeleteAny` 才跳过归属判定。
- 每请求的权限集合 = `users.role_id ⋈ role_permissions`，**缓存条目里必须同时带上 BoardIDs 与 status**（见 9.2 的决策 2）；TTL 60 秒；后台改角色、改授权、封号、任免版主时都主动失效。
- 超级管理员在 `authz.Require` 与中间件里**都短路**（`if actor.IsSuper { return nil }`），否则以后新增权限点时超管会被自己拦住。
- 缓存条目数要有上限（例如 1 万条），超了按 LRU 淘汰、回落查库（两表 join，PG 很快）。

#### 审计、一致性与边界

- **审计**：角色创建/删除、权限矩阵变更、用户角色分配、分区版主任免，全部写 `audit_log`（谁、何时、把什么权限给了谁）。提权是攻击者的第一目标，没有审计等于事后无从追查。
- **权限点一致性自检**：启动时把代码常量集合与 `permissions` 表对比 —— 代码有、表里没有 → **启动失败**；表里有、代码没有 → Warn（提示这是可以删的死权限点）。只靠「两处必须同名」的约定，人一定会忘。
- **新增权限点不会自动授予已有自定义角色**：这是 RBAC 的固有行为。约定：新权限点默认只授予内置角色（迁移里同时写 `role_permissions`），后台在角色页提示「该角色缺少最近新增的权限」。
- **删除自定义角色**：`role_permissions` 用 `ON DELETE CASCADE`；`users.role_id` 用 `RESTRICT`（有用户在用就不许删）；`is_system=1` 的角色禁止删除，**在 service 层挡**，不能只靠后台界面不显示按钮。
- **最后一个 superadmin 不可移除**：service 层守卫 + CLI 兜底，否则真的会把自己锁在门外。

#### 后台界面（属于管理后台范围）

- 角色列表：内置角色只读，自定义角色可增删改名
- 角色 × 权限勾选矩阵：按 grp 分组显示，改完即时生效
- 用户角色分配：在用户详情页
- 分区版主任免：在版块设置页
- 审计日志查询：按操作者 / 目标 / 时间过滤，至少能看到全部提权类操作

#### 禁止

- 禁止在 handler、service、模板里比较角色字符串（`if user.Role == "admin"`）—— 一律走权限点。
- 禁止把权限点做成可后台新增的数据：代码不认识它，只会变成一个永远不生效的勾。
- 禁止用「角色优先级 ≥ X」代替权限点判断（那样自定义角色永远不会生效）。
- **禁止只在路由层声明权限**：队列、cron、CLI 都不走路由，危险写操作必须在 service 里再 Require 一次。
- **禁止把「改角色」与「分配角色」合成一个权限点**：能把权限勾给角色的人，就能给自己提权。`role.edit`（改矩阵）与 `role.assign`（给人分配）是两个权限点，单持其一都不足以完成提权。

## 10. 图片上传与分发（本站唯一的字节入口）

### 10.1 范围

只处理**图片**：头像、帖子配图、（可选）赞赏收款码。**不做文件上传、不做网盘、不做转码与缩略图。**

### 10.2 端点与限额

| 端点 | 用途 | 单张上限 | 张数限制 |
|---|---|---|---|
| POST /api/v1/me/avatar | 头像 | 64KB | 1（替换） |
| POST /api/v1/posts/{id}/images | 帖子配图 | 2MB | 每帖 ≤ 9 |
| POST /api/v1/me/payment-channels | 收款码 | 512KB | 每用户 ≤ 5 |

- 请求体上限按上表 + 一点余量设置（例如帖子配图路由设 3MB），**不要**用全局 1MB。
- 头像在前端压到 ≤64KB 再上传（浏览器 canvas），服务端**再校验一次**实际大小 —— 不信任客户端。
- 图片可以整块读进内存（因为上限已经卡死在 2MB）；**文件不行，所以本站不托管文件**。这条是设计边界，不是妥协。

### 10.3 存储

    // internal/platform/image/image.go
    type Store interface {
        // 边读边算 sha256，返回内容摘要与真实大小；已存在则直接返回（去重）
        Put(ctx context.Context, r io.Reader, maxBytes int64) (hash string, size int64, err error)
        Open(ctx context.Context, hash string) (io.ReadCloser, error)
        Stat(ctx context.Context, hash string) (size int64, err error)
        Delete(ctx context.Context, hash string) error
    }

localstore 实现：

- 路径 `<root>/<ab>/<cd>/<sha256>`（ab/cd 是摘要前 4 位，避免单目录堆几万个文件）。
- 写入：先写 `<root>/tmp/<random>.part` → 算摘要 → fsync → 同盘 rename 到最终路径（原子，读者永远看不到半成品）。
- 同摘要已存在：删掉临时文件，直接返回（天然去重）。
- 摘要用标准库 crypto/sha256（不加依赖）。

### 10.4 入库与回收

- 落盘成功后写 `images` 表（hash 主键、size、mime、refcount、visibility、owner_id），refcount 初始为 1。
- 引用关系由业务表体现：`users.avatar_hash`、`topic_images`、`payment_channels.image_hash`。
- 解引用时 refcount -= 1，**归零才删盘**（删盘失败只记 Warn，由 image:gc 任务兜底重试）。
- `image:gc` 任务：每天扫一次 refcount=0 但文件仍在的记录，补删。

### 10.5 可见性

| level | 含义 | 谁可见 |
|---|---|---|
| 0 | 公开 | 所有人 |
| 1 | 登录可见 | 已登录用户 |
| 2 | 私有 | 本人与管理员 |

- 头像与公开配图 = 0；收款码 = 1；其他按业务定。
- **权限不足时不要返回 404**：返回一张带说明文字的占位图（服务端生成的小 PNG），并带 `Cache-Control: no-store`。理由是 `<img>` 拿到 404 只会画成裂图，用户不知道发生了什么；no-store 保证登录后刷新能拿到真图。

### 10.6 分发

- 图片 URL 形如 `/img/<hash>`，由应用返回 **X-Accel-Redirect** 指到 nginx 的 internal 目录：

      location /_img/ { internal; alias /srv/forum/data/images/; }

- 应用侧响应只带路径，不带字节；nginx 直出磁盘（sendfile），并配 `Cache-Control: public, max-age=31536000, immutable`（内容寻址，URL 即版本）。
- 按 MIME 分目录（`/_img/png/...`、`/_img/webp/...`）是可选的优化；若不做，就必须确保 nginx 的 `default_type` 不至于把图片发成 octet-stream —— 建议做。
- 开发环境（没有 nginx）允许应用直接回字节：由 `image.serve_locally=true` 控制，**只用于本地开发与测试**。

### 10.7 魔数校验

- 只认 PNG / JPEG / GIF / WebP 的文件头；其余一律 400。
- 不要只看 Content-Type，也不要只看扩展名。
- 不接受的格式（含 SVG）明确写进错误信息，便于前端提示。

## 11. 外链下载（启动器 / 资源包）

本站**不承载这些文件的字节**。

- `releases` 表存版本、更新说明、发布状态；`release_assets` 存平台、架构、**外部直链 URL**、大小、sha256、下载计数。
- 下载端点：GET /api/v1/launcher/assets/{id}/go → 302 到外部 URL，同时把下载计数加进 counter.Buffer（内存缓冲 + 每 15 秒批量写回 release_assets.download_count，见 7.5）。**禁止每请求 UPDATE**；也禁止说“不落库”——6.6 有 download_count 列、M8 验收要求计数增加。
- 转链的意义：以后换镜像只改数据库，不用改已发布的客户端。
- 禁止在本站做代理转发（那就是让字节过应用进程）；禁止把外链做成需要鉴权的形式（会与转链冲突）。
- 外链的 sha256 由管理员在录入时核对，站内不做下载后校验。

## 12. 赞赏模块（老设计：收款码 + 用户自报 + 管理员人工核验）

> 用户已定：**收款按老设计**。站点**不经手资金**，所以下面这些**全部不需要，不要再实现**：
> Gateway 接口、支付回调与签名校验、主动查单、对账任务、Wallet、LedgerEntry、余额。
> 这条路线的代码量比支付通道小一个数量级，而且没有商户资质门槛。表结构见 `数据库设计-postgresql.md` §4.6。

### 12.1 流程

    作者在设置页挂收款码（≤5 张，内容寻址图片，visibility=1）
      └─ 开关 show_channels 决定帖子页/主页是否展示

    访客在帖子页点「打赏」→ 弹窗展示作者的收款码 + 提示文案（作者自定义；空则用渠道默认）
      └─ 扫码支付（微信 / 支付宝 / …，与本站无关）

    访客回来后填「打赏了多少 + 单号或备注」→ donation_records(state=pending)

    管理员在后台核验 → approved / rejected（改判必须写 audit_logs，action=reward.verify）

    统计只认 approved，且只累加作者同意公开（records_public）的记录

### 12.2 端点

| 方法 | 路径 | 登录 | 权限点 | 说明 |
|---|---|---|---|---|
| GET | /api/v1/users/{handle}/channels | — | — | 作者的收款码；show_channels=false 时返回空数组 |
| POST | /api/v1/rewards | ✔ | — | { to_handle, post_id?, amount_cents, txn_id, note? } → pending |
| GET | /api/v1/me/rewards | ✔ | — | 我发出的申报（含状态） |
| GET | /api/v1/users/{handle}/rewards | — | — | 只返回 approved 且作者同意公开的 |
| DELETE | /api/v1/rewards/{id} | ✔ | — | 撤回自己 pending 的申报（置 withdrawn，不物理删） |
| GET / PATCH | /api/v1/me/donation-settings | ✔ | — | 三个开关（show_channels / records_public / notice_visible）+ notice_text |
| GET | /api/v1/admin/rewards?state=pending | ✔ | reward.verify | 核验队列 |
| POST | /api/v1/admin/rewards/{id}/verify | ✔ | reward.verify | { state: approved \| rejected, note? }；已核验过返回 409 reward.already_handled |
| GET / PATCH | /api/v1/admin/donation-notice-defaults | ✔ | site.setting | 按渠道配默认提示文案 |

### 12.3 规则与边界

- **金额只用于展示与统计**，站点不校验支付真实性——核验靠人（管理员看对方贴的单号或截图）。这条必须显示在后台核验页上，避免以后有人以为它是自动的。
- 申报必须 `donor ≠ recipient`（数据库 CHECK 兜底）。
- `txn_id` **不加唯一约束**：假单号与重复申报会很常见，唯一约束只会挡住正常申报；重复由管理员在核验时合并或拒绝。
- 统计口径：收入侧 / 支出侧 / 按帖 / 排行榜只算 `approved` 且作者 `records_public`；管理员看得到全部。
- **状态机只有一条**：`pending → approved | rejected`，以及用户自己 `pending → withdrawn`。没有「已支付/已结算/已退款」——本站没有资金流，不要发明这些状态。
- **禁止**引入任何支付 SDK 与支付密钥配置（第 13.2 章不再有 `FORUM_SECRET_PAYMENT_KEY`）。

## 13. 配置

### 13.1 加载顺序

默认值（代码里） → 配置文件（configs/config.yaml） → 环境变量。后者覆盖前者。

环境变量规则：前缀 FORUM_，层级用双下划线，例如 FORUM_DB__PATH 对应 db.path。列表类配置不通过环境变量覆盖，密钥类字段单独处理（见 13.2）。

### 13.2 密钥

- **发信凭据不在配置里**：它们在数据库里、由管理员后台配置、加密存储（见 8.2 与 8.7）。配置文件里只有一把主密钥。
- 配置文件/环境变量里出现的密钥**只有一把**：`FORUM_SECRET_MAIL_KEY`（发信凭据主密钥，见 8.7）。
- **没有支付密钥**：赞赏走「收款码 + 人工核验」，站点不经手资金（第 12 章）。
- 主密钥只从环境变量注入，**禁止写进 configs/config.yaml**，也禁止提交进仓库。
- 日志里禁止打印任何密钥、密码、token、Cookie、凭据明文。

## 14. 开发规范

### 14.1 通用

- 代码必须通过 gofmt 和 golangci-lint。
- 每个导出的类型、函数写注释，注释用中文或英文均可，但同一个文件内统一。
- 函数超过 80 行就拆分。
- 不写没有用到的代码、不预留“以后可能用”的参数（第 7 章规定的接口除外）。
- 所有可能阻塞的函数第一个参数是 ctx context.Context，并且要把 ctx 传下去，禁止在业务代码里用 context.Background()（main、Run、关闭流程除外）。

### 14.2 命名

| 对象 | 规则 | 例子 |
|---|---|---|
| 包名 | 小写单词，不用下划线和复数 | reward、memkv |
| 构造函数 | NewXxx | NewService、NewHandler |
| 接口 | 名词或 -er 结尾 | Sender、Searcher、UserLookup |
| 错误变量 | ErrXxx | ErrTopicLocked |
| 任务类型 | 模块:动作 | mail:send |
| 缓存 / 限流 key | 模块:用途:标识 | forum:topic:<id> |
| JSON 字段 | snake_case | created_at |
| URL | 小写，复数名词，kebab-case | /api/v1/topics/:id/posts |

### 14.3 错误处理

统一错误类型：

    // internal/platform/apperr/errors.go
    type Error struct {
        Code   string // 机器可读，例如 "topic.locked"
        Status int    // HTTP 状态码
        Msg    string // 给用户看的提示
    }

    func (e *Error) Error() string { return e.Code }

    func New(status int, code, msg string) *Error {
        return &Error{Code: code, Status: status, Msg: msg}
    }

    var (
        ErrInvalidInput = New(400, "common.invalid_input", "参数错误")
        ErrUnauthorized = New(401, "common.unauthorized", "请先登录")
        ErrForbidden    = New(403, "common.forbidden", "没有权限")
        ErrNotFound     = New(404, "common.not_found", "内容不存在")
        ErrConflict     = New(409, "common.conflict", "数据冲突")
        ErrRateLimited  = New(429, "common.rate_limited", "操作太频繁，请稍后再试")
        ErrInternal     = New(500, "common.internal", "服务器错误")
    )

规则：

1. 每个模块在自己的 errors.go 定义业务错误，例如 var ErrTopicLocked = apperr.New(403, "topic.locked", "主题已锁定")。
2. service 返回业务错误时直接返回这些变量；返回底层错误时用 fmt.Errorf("动作: %w", err) 包装，说明在做什么。
3. ent 的 NotFound 在 service 层转换成本模块的业务错误（ent.IsNotFound(err)），不要让 ent 的错误类型到达 handler。唯一约束冲突用 ent.IsConstraintError(err) 转换成 409。
4. handler 统一调用 httpx.Fail(c, err)：用 errors.As 取出 *apperr.Error 就按它返回；否则记录完整错误日志，对外只返回 ErrInternal，禁止把内部错误信息返回给前端。
5. 禁止忽略错误（除了明确不需要处理的 Close 等，要写 _ = 并加注释说明）。
6. 禁止在业务代码里 panic。

### 14.4 HTTP API

- 前缀 /api/v1。
- 成功：HTTP 200/201，响应体直接是数据：

      { "data": { ... } }
      { "data": [ ... ], "next_cursor": "..." }

- 失败：

      { "error": { "code": "topic.locked", "message": "主题已锁定", "request_id": "..." } }

- 参数校验失败返回 400，code=common.invalid_input，可以附带 fields 字段说明哪个字段错了。
- 时间字段统一 RFC3339 格式 UTC。
- 金额字段统一 *_cents 整数。
- ID 字段只返回 public_id，字段名就叫 id。

handler 写法模板：

    type Handler struct {
        svc *Service
    }

    func NewHandler(svc *Service) *Handler { return &Handler{svc: svc} }

    func (h *Handler) Register(rg *gin.RouterGroup, requireLogin gin.HandlerFunc) {
        rg.GET("/topics/:id", h.getTopic)
        rg.POST("/topics", requireLogin, h.createTopic)
    }

    func (h *Handler) createTopic(c *gin.Context) {
        var req CreateTopicReq
        if !httpx.Bind(c, &req) { // 绑定失败时 Bind 已经写好 400 响应
            return
        }
        uid := auth.UserID(c)
        out, err := h.svc.CreateTopic(c.Request.Context(), uid, req.toInput())
        if err != nil {
            httpx.Fail(c, err)
            return
        }
        httpx.Created(c, toTopicResp(out))
    }

规则：handler 只做三件事：解析参数、调 service、写响应。业务判断全部放 service。

### 14.5 service

- service 结构体通过字段持有依赖，构造函数是唯一的创建方式。
- 方法参数用明确的输入结构体（例如 CreateTopicInput），不要用 handler 的 DTO。
- 权限检查在 service 里做（例如“只有作者或版主可以编辑”）。
- 需要多表写入的操作必须放进 db.WithTx。

### 14.6 事务

1. 事务里禁止：发 HTTP 请求、发邮件、调用支付接口、调用 Queue.Enqueue（应使用 EnqueueTx）、耗时计算、图片落盘。
2. 事务要尽量短：长事务会挡住 autovacuum、放大队列锁冲突、占满连接池。PG 没有 SQLite 的单写者限制，但连接池只有 16 条，事务同样必须短。
3. 事务里所有数据库操作都用 tx（或 tx.Client()），禁止混用 s.db。

### 14.7 时间与金额

- 获取当前时间一律通过注入的 clock.Clock（s.clock.Now()），禁止在业务代码里直接调用 time.Now()（ent mixin 默认值除外）。
- 时间存储和计算用 UTC，只在展示层（前端）转本地时区。
- 金额 int64，单位分，禁止 float32/float64。

### 14.8 日志

- 使用注入的 *slog.Logger，禁止 fmt.Println、log.Printf。
- 每条请求日志带 request_id、method、path、status、latency、user_id（有的话）。
- 日志级别：Debug 开发细节；Info 正常业务事件；Warn 可恢复的异常（例如邮件账号熔断）；Error 需要人处理的错误。
- 空轮询、缓存未命中等正常路径禁止记 Error（否则真实故障会被噪声淹没）。
- 禁止打印密码、token、Cookie、密钥、完整邮件正文。

### 14.9 测试

- 每个 service 方法至少有正常路径和主要错误路径的测试。

## 15. 禁止事项（汇总）

1. 禁止替换第 2 章已定的库，禁止引入功能重复的库。
2. 禁止使用全局变量保存依赖，禁止在 init() 中初始化资源。
3. 禁止业务模块之间直接 import。
4. 禁止 handler 直接访问 ent client，禁止 service 依赖 gin。
5. 禁止在生产代码里调用 client.Schema.Create。
6. 禁止修改已提交的迁移文件，禁止手改 ent 生成代码。
7. 禁止使用数据库私有语法；`tsvector` 相关的原生 SQL 只允许出现在 `platform/search/pgsql` 包与手写迁移里。
8. 禁止字符串拼接 SQL。
9. 禁止在事务中执行外部调用、图片落盘或 Queue.Enqueue。
10. 禁止业务代码直接发送邮件，必须走 mail:send 任务。
11. 禁止把邮件额度计数放在内存。
12. 禁止用 float 表示金额。**本站没有余额与流水**（赞赏不经手资金，第 12 章）；任何「站内钱包 / 余额」需求都必须先改第 12 章，不许顺手加张表。
13. 禁止对外暴露自增 id。
14. 禁止把未经 bluemonday 清洗的 HTML 存库或返回。
15. 禁止把内部错误信息返回给前端。
16. 禁止在日志、配置文件、代码仓库中出现密钥。
17. 禁止在业务代码中直接调用 time.Now() 和 context.Background()。
18. 禁止启动多个 forum run 进程（当前所有进程内组件都只在单进程下正确）。
19. **禁止上传或托管文件**：本站只接受图片（PNG/JPEG/GIF/WebP），且只接受 10.2 列的三个端点。文件与安装包一律外部直链。
20. **禁止接受 SVG**；禁止只按 Content-Type 或扩展名判断图片类型（必须嗅探魔数）。
21. 禁止在应用里转发下载字节（外链只做 302）。
22. 禁止在图片权限不足时返回 404（会变成裂图），必须返回占位图 + no-store。
23. 禁止在 handler / service / 模板里比较角色字符串；授权只走 `authz.Require` + `internal/authz/permissions.go` 里的权限点常量。
24. 禁止把权限点做成可后台新增的数据；禁止用「角色优先级 ≥ X」代替权限点判断。
25. 禁止把发信 / 支付凭据写进配置文件或环境变量（环境变量里只放主密钥）；禁止把主密钥提交进仓库或存进数据库。
26. 禁止在 service 里从 gin.Context 取身份：**身份一律作为参数传入**（见 9.2 的传参约定）。
27. 禁止只在路由层声明权限、不在 service 兜底：队列 / cron / CLI 都不走路由（见 9.8）。

## 16. 备份与恢复

> SQLite 时代的 `VACUUM INTO` 方案作废。现在的做法（`pg_dump -Fc` + `pg_restore`、保留策略、磁盘闸门、恢复流程）见 **`数据库设计-postgresql.md` 第 8 章**。

要点：进程内 cron 每小时一次；保留「最近 24 份 + 每天 1 份 × 7 天」；磁盘余量不足时跳过并记 Warn；图片目录不进 dump，单独 rsync；快照里没有凭据主密钥（它在环境变量里，这是有意的）。

## 17. 开发顺序（里程碑）

> **排期、顺序、并行、上线一律以 `完全重构/施工计划.md` 为准**；本章只保留每个里程碑的验收细节。

每个里程碑完成后必须通过 14.11 的检查清单和对应验收标准，再进入下一个。

### M0 项目骨架

- 内容：go.mod、目录结构、config 加载与校验、slog、db.Open（pgx 连接池）、WithTx、apperr、httpx、requestid / 日志 / recover 中间件、clock、idgen、forum migrate、forum run、GET /healthz（探针不带 /api/v1 前缀，见 21.1）、优雅关闭。
- 验收：forum migrate 能在空库上执行成功；forum run 启动后 healthz 返回 200；Ctrl+C 能正常退出且日志显示按顺序关闭；未执行迁移时 forum run 拒绝启动；**pg_trgm 扩展能装、tsvector 生成列能建能查**（数据库文档 §5 的测试）；**外键索引自检 SQL 在空库上跑通**（数据库文档 §12 第 1 条）。

### M1 抽象层

- 内容：kv/memkv、ratelimit/memlimit、queue/pgqueue 及契约测试（入队、领取、重试、dead、崩溃恢复、EnqueueTx 随事务回滚、unique_key 在 done 之后可再次入队）。
- 验收：所有契约测试通过。

### M2 用户与认证

- 内容：User、Session、EmailToken；注册、登录、登出、当前用户、修改密码；**RBAC：roles / permissions / role_permissions / users.role_id / board_moderators 五张表 + authz.Require + 四个内置角色 + 后台角色权限矩阵（见 9.8）**；**认证中间件（LoadPrincipal / RequireLogin / Perm，见 9.2）与 `forum create-admin`**；图形验证码（默认 off，可切 on_failure）；CSRF Origin 检查；限流；鉴权中间件；argon2 并发信号量。
- 验收：密码以 argon2id 存储；数据库中只有 token 哈希；登录失败超过限制返回 429；跨域 POST 被拒绝；**越权用例：普通用户调管理端点返回 403；新建一个自定义角色并只勾一个权限，该角色用户只能做那一件事；给角色加权限后 60 秒内生效**；**未登录访问需登录接口 401、已登录缺权限 403**；**最后一名 superadmin 不可被移除**；**封号后立刻失效（不等 60 秒）**；**连续 1000 次请求时 last_seen_at 的 UPDATE 不超过 1 次**；**并发 10 个登录请求时不会出现 10×32MB 的瞬时分配**（用运行时读数或 pprof 验证）。

### M3 邮件

- 内容：mail_accounts 表 + 凭据加密（8.7）、**后台账号 CRUD 与测试发信（8.2）**、Router（多账号轮换，账号从库读 + 30 秒缓存）、mail_quota、MailLog（含 quota_provider / quota_day）、mail:send 任务、模板；接入注册验证邮件和找回密码。
- 验收：用 fake provider 测试：额度用完自动落到下一个账号；ErrQuotaExceeded 熔断；ErrPermanent 不重试；**同一个 MailLog 重试 3 次只占 1 次额度**；重复执行同一任务只发一次；重启后额度计数不丢失；**后台改完账号立即生效（缓存失效）；接口与页面都不回显凭据；主密钥不对时启动直接失败**。

### M4 图片

- 内容：image.Store（内容寻址、去重、refcount）、魔数校验、三个上传端点、可见性三档与占位图、X-Accel-Redirect 分发、image:gc 任务。
- 验收：同一张图上传两次只落一份盘；超过上限被拒；伪造扩展名的非图片被拒；SVG 被拒；level=2 的图对他人返回占位图且带 no-store；删掉最后一个引用后盘上文件被回收。

### M5 论坛核心

- 内容：Board、Topic、Post、Like；发帖、回复、编辑、删除（状态改为 deleted，不物理删除）、点赞、列表游标分页；markdown 渲染与清洗；版主权限；帖子配图关联。
- 验收：XSS 测试用例（script 标签、onerror 属性、javascript: 链接）都被清洗；点赞重复提交只计一次；锁定主题无法回复。

### M6 通知

- 内容：Notification；回复提醒、被点赞提醒（任务驱动）；未读数；标记已读；通知邮件（低优先级，可合并）。
- 验收：回复后作者收到站内通知；通知任务失败可重试且不重复生成通知。

### M7 赞赏

- 内容：**收款码 + 用户自报 + 管理员人工核验（老设计，站点不经手资金，第 12 章）**；`donation_records` 表、申报/撤回端点、管理核验队列（`reward.verify`）、统计（收入/支出/按帖/排行榜，只算 approved 且公开的）、`notify:reward` 任务、按渠道的默认提示文案。
- **不做**：Gateway、支付回调、签名校验、主动查单、对账任务、Wallet、LedgerEntry、余额（盲审 C2：这些在 §12 与数据库 §4.6 已删除，M7 不许再要求）。
- 验收：只有 `pending → approved|rejected` 与 `pending → withdrawn` 三条转换（非法转换被拒）；改判写 `audit_logs`；统计只含 approved 且 `records_public`；同一申报重复核验返回 409。

### M8 搜索、外链、计数、备份

- 内容：tsvector + bigram 搜索、search:index 任务；release 模块与外链转链；浏览量 counter；image:gc 与 job 清理；backup:snapshot 定时任务与 forum backup。
- 验收：中文两字词能搜到；转链返回 302 且计数增加；关闭进程后浏览量不丢失；能从一份快照恢复出可用的数据库。

#### D6 的具体设计（把旧站两套正交限制收敛到一套）

旧站有两条互不相同的限制，RBAC 原来都表达不了：

1. **用户组 × 分区的允许/禁止矩阵**（禁止优先）；
2. **分区级最低角色**（发帖 / 回帖各一个）。

收敛方式：**不再引入「用户组」这第二个主体**，自定义角色就是原来的用户组；作用域规则落在新表上：

    BoardACL
      board_id      → boards.id
      role_id       → roles.id
      can_post      bool
      can_reply     bool
      deny_post     bool
      deny_reply    bool
      (board_id, role_id) 唯一

    boards.acl_enabled  bool   -- 关闭时该分区不查 ACL，回到「登录即可发帖」的默认

判定顺序（在 service 层，不在中间件）：

    1. actor.IsSuper                          → 放行
    2. 有 Sanction 命中（20.2 第 21 条）       → 拒绝
    3. boards.acl_enabled = false             → 放行
    4. 任一角色命中 deny_post                  → 拒绝   ← 禁止优先
    5. 任一角色命中 can_post                   → 放行
    6. 都没命中                                → 拒绝（该分区是白名单制）

这样做的三个好处：**不需要「角色优先级比大小」**（9.8 明令禁止用优先级代替权限点）；「最低角色」被更高的「允许哪几个角色」替代，语义更准；用户组与角色不再并存，避免第三套主体。

## 21. 前后端接口契约（API v1）

> 这一章是**前端唯一的依据**，也是重写时最容易走形的地方（旧站根因 6：契约手写双份）。
> 规则：**后端 handler 的 dto.go 是契约的真源**；前端在 `web/src/lib/api/schema.ts` 用 zod 复述它；
> 两者是否一致**不靠人核对**，靠 21.6 的契约测试在 CI 里跑。

### 21.1 通用约定

| 项 | 规定 |
|---|---|
| 前缀 | 业务接口一律 `/api/v1`；探针 `/healthz`、`/readyz` **不带前缀** |
| 认证 | HttpOnly Cookie（9.2）。前端不做任何 token 存储 |
| CSRF | 写方法校验 Origin/Referer（9.3）。默认同域部署时前端无需附加令牌 |
| 成功响应 | `{ "data": … }`；列表 `{ "data": [...], "next_cursor": "..." }`；201 用于创建 |
| 失败响应 | `{ "error": { "code": "...", "message": "...", "request_id": "..." } }`；校验失败额外带 `fields` |
| 分页 | **游标分页**：请求 `?limit=20&cursor=<opaque>`，响应 `next_cursor`（为 null 表示到底）。**禁止 page/offset**。规格：`cursor = base64url(JSON{k:<排序键>,id:<该行 public 或内部 id>})`，查询条件恒为 `(<排序键>, id) < (k, id)` 的行序比较，**排序键永远带 id 兜底**（否则并列/NULL 会跨页重复或漏项）。`sort=latest` 用 `(last_reply_at DESC NULLS LAST, id DESC)`；**v1 不做 `sort=hot`**——它需要物化分数列才可能有稳定游标，现在没有（盲审 B4） |
| limit | 默认 20，上限 100；超出按 100 处理（不报错） |
| 排序 | `sort=latest`（按 last_reply_at 倒序，默认）/ `new`（按 created_at 倒序）/ `hot`（按 reply_count 与时间衰减，具体公式在 service 里写死并写测试） |
| ID | 响应里的 `id` 一律是 public_id（字符串）；**禁止出现自增整数** |
| 时间 | RFC3339 UTC 字符串，字段名以 `_at` 结尾 |
| 金额 | 整数分，字段名以 `_cents` 结尾 |
| 命名 | JSON 字段 snake_case |
| 幂等 | 点赞 / 收藏用 **PUT（选中）/ DELETE（取消）**，天然幂等；发帖与回复可选带 `client_token`（P2，防重复提交） |
| 状态码 | 400 参数错 / 401 未登录 / 403 无权限 / 404 不存在 / 409 冲突 / 429 限流（带 Retry-After）/ 507 磁盘满 |

                "wallet_cents": 0, "unread_count": 3 } }

### 21.5 契约的单一真源

| 侧 | 真源 | 生成/校验 |
|---|---|---|
| 后端 | 各模块 dto.go 的请求/响应结构体 | 结构体标签即契约；handler 必须走 httpx.Bind |
| 前端 | `web/src/lib/api/schema.ts` 的 zod schema | 类型由 schema 推导（z.infer），**不手写 interface** |
| 两侧一致 | 21.6 的契约测试 | 不一致时 CI 红 |

### 21.6 契约测试（把根因 6 变成会红的检查）

    1. CI 起一个真实后端（内存库 + 迁移 + seed 最小数据）。
    2. 跑 scripts/contract-test.ts：对每个端点发一次真实请求（覆盖成功 + 401 + 403 + 404 + 400 各一条）。
    3. 用前端 lib/api/schema.ts 的 schema 解析响应体：
       - 该解析成功 → 契约一致；
       - 解析失败 → 失败并打印 path（zod 会指出哪个字段）。
    4. 反向检查：gin 路由表里每个非公开接口都必须声明权限点（9.8 已有此测试）。
    5. 端点清单与本文档 21.2 表逐个比对：新增端点没写进文档也失败。

**这一条比任何规范条文都管用**：旧站的 422 类缺陷、字段名漂移、路径前缀散落，全部会在这里变成红灯。
