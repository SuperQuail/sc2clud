## 1. 「上线」的定义（这一节就是验收清单）

1. **后端跑得起来**：`forum migrate` 在空库跑通 → `forum run` 起来 → `/healthz` 200 → `forum check` 自检全过；
2. **主链路在真实路由上跑通**：注册 → 收验证码 → 激活 → 登录 → 发帖（带图）→ 列表看到 → 进详情 → 回复 → 点赞 → 举报 → 管理队列处理 → 作者看到结果；
3. **一条命令部署**：构建 → 上传 → 迁移 → 重启 → 健康检查 → **失败可回滚**；
4. **门禁在 CI 里跑**（不是靠人记得）；
5. **数据可回滚**：迁移 down 可执行、有备份、回滚演练过一次；
6. **不外泄**：无真实身份信息、无密钥入库、无 sourcemap 上线（后两条已有门禁）。

## 2. 分期（按依赖排序，每期都能独立验收）

### P1 · 后端接线（**最大缺口，阻塞其它一切**）

**做什么**：把六个域的 handler 挂进 `registerAPIRoutes`，并在 app 层写装配（各域 `deps.go` 声明的小接口由 app 提供实现）。

**设计决策（已定，施工照做）**：
1. **装配点只有一个**：`internal/app/modules.go`（新建）集中构造各域 Service 与适配器；`http.go` 只负责挂路由，**不写依赖细节**；
2. **跨域调用一律走接口**：各域 `deps.go` 里的小接口（如 forum 要的 `UserLookup`、notify 要的 `Renderer`）在 app 层用适配器实现，**禁止业务模块互相 import**；
3. **actor 从中间件取一次**：`auth.FromGin` 的产物传给各域 handler 的 `ActorFunc`，**service 层不再从 ctx 取值**；
4. **worker 与 cron 同批挂**：六个通知任务类型 + `mail:send` + `search:index` + `image:gc` 的 handler 必须都在启动时注册 —— **没注册的任务类型会被 worker 直接置 dead**；
5. **启动自检**：迁移版本 → `CheckPermissions` / `CheckEnums` / `CheckRoleSeeds` / 外键索引 → 才监听。**自检失败就拒绝启动**；
6. `mail` 的 `Store` 由 `internal/mail` 实现（`platform/mail` 只提供 provider 与轮换）。

**验收**：`go build ./...` = 0；`fm migrate` 后 `forum run` 起得来；`curl /healthz` 200；
**用 curl 真跑一遍** 注册 → 从 `mail` 的 log provider 里读 6 位码 → 激活 → 登录 → 发帖 → 读列表，**每一步存下请求与响应**。

**写作用域**：`forum/internal/app/**`（装配与路由）+ 必要时各域 `deps.go` 的适配器（**只加不改成型的 service**）。

### P2 · 前端产品壳（把 DevRoom 的页面搬进真实路由）

**做什么**：`src/routes/` 从 2 个页面扩到真实路由表；页面从 `devroom/pages/**` 提升为产品页面（或就地复用），接 `src/lib/api/client.ts`。

**设计决策**：
1. **路由表以 v2 §21.2 为准**（那是契约）：`/` 首页、`/b/:slug` 分区、`/t/:id` 帖子、`/new` 发帖、`/u/:handle` 个人主页、`/settings`、`/admin/*`、`/login`、`/register`、`/appeal`…；
2. **DevRoom 保留**：它是控件验证场所，**不删**；产品页与它共用 `src/ui/**` 的房子件（**同一份实现，不是两份**）；
3. **页面搬家的判定**：能被产品直接用的（首页信息流、帖子页、登录注册、管理后台）**先搬**；纯演示页（样板间、控件页）**留在房间**；
4. **API 接入顺序**：先接**只读**（列表、详情）再接**写**（发帖、回复、点赞）—— 这样前端能先对着真后端跑起来，而不必一次全接；
5. **错误与加载态**：每页三态（加载 / 空 / 错误）必须有，**不许白屏**（今天房间已经因为缺这个反复吃亏）。

**验收**：`pnpm build` 出产品产物；对着 P1 起来的后端跑通主链路前六步；每页三态都有出图。

### P3 · 部署交付物（让「上线」是一条命令）

**做什么**：`deploy.ps1`（build → pack → upload → migrate → restart → health → 失败回滚）、systemd 产品单元、nginx 站点、`/etc/sc2clud/prod.env`。

**设计决策**：
1. **一个产物**：`forum-<version>.tar.gz`（bin/forum + web/dist + VERSION）；
2. **目录约定**：`/srv/sc2clud/prod/releases/<version>` + `current` 软链 —— **与已存在的 `/srv/sc2clud-dev` 同一套**（旧站就是这么放的）；
3. **env 一律 `/etc/sc2clud/*.env`**，**密钥只从环境变量**，不进仓库（`secrets/env/production.env.example` 现在是**过时的旧 Rust 命名**，要改成 `FORUM_*`）；
4. **迁移在部署脚本里跑，但顺序是**：解包 → 校验 → **备份数据库** → 停服务 → 迁移 → 起服务 → 健康检查 → 失败则回滚到上一个 release；
5. **nginx**：复用服务器上已有的 `sc2clud.conf`（宝塔管），只加/改 `location /` 的 upstream 指向产品端口；**不改动 dev 与 `/devroom/`**。

**验收**：在服务器上跑一次完整部署（先 dev 实例演练，再 prod）；**故意让健康检查失败一次，验证回滚真的回到上一版**。

### P4 · 上线门禁（把「记得跑」换成「不跑过不去」）

1. **CI**：后端 `gofmt/vet/build/test`（embedded-postgres 在 CI 可用）+ 前端 `pnpm check`；**跑在所有会合入的分支上**（旧站 CI 只跑 main 而开发在 dev-side 领先 193 个提交 —— 等于没跑）；
2. **迁移一致性**：空库跑全部迁移 vs ent schema 的 diff（审计建议的 Atlas snapshot diff）；
3. **原生 SQL 进真库 PREPARE**（审计建议 —— 一次抓掉「列不存在」那一类）；
4. `CheckPermissions` / `CheckEnums` 接进 `forum check`（现在实现了但**全仓没有调用点**）；
5. **盲审复验**：把两名盲审员叫回来，用**同一份题面**跑（一号 17 页自由探索 + 二号 21 条主链路）—— 这样能看出这一轮到底补上了几条。

## 3. 已知的、必须在 P1/P2 里顺手做掉的小缺口

| # | 缺口 | 归期 |
|---|---|---|
| 1 | 服务端图片硬约束（头像 128KB）未实现 —— 现在只是前端闸门，绕过前端不受约束 | P1（media 域） |
| 2 | `14-home` 与 `12-topic` 的分区键空间没统一（`campaign/terrain/help` vs `custom-campaign/tool-dev`）—— 两套键表达同一个概念 | P2 |
| 3 | 删回复没有二次确认（单击即删），开发必读要求危险动作走 `ConfirmDialog` | P2 |
| 4 | `attachment-slot.tsx` 没有测试，而发帖页在用它 | P2 |
| 5 | `pnpm e2e`（12 组浏览器断言）一直没跑（要自起预览服务、端口冲突） | P4 |
| 6 | 事由值域无 DB 约束（`reports.reason` 是 `varchar(500)` 无 CHECK），五值枚举只活在管理队列的类型里 | P1（要么加 CHECK，要么写进契约） |

## 4. 顺序与并行

- **P1 必须先做**（它阻塞 P2 的联调与 P3 的健康检查）；
- **P2 与 P3 可并行**（前端接 API 与写部署脚本互不依赖）；
- **P4 在 P1/P2 之后**（CI 要跑得起来才有意义）；
- 每个 P 完成后都要**跑一次全仓门禁 + 出图/出证据**，并且**只有 Lead 提交**（今天的教训：并发提交会把别人的在途文件扫进去）。
