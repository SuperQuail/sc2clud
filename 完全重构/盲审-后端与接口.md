## B1 · blocker · v2 §9.2 第 686-691 行、第 775 行、第 823-824 行（测试表）；§9.8 第 976 行

**问题**：Principal 按 token 摘要缓存 60 秒且"缓存命中直接得到 Principal"，而"封号必须立刻生效"依赖的是"Resolve 每次都看 users.status"；同一节说 status 不进权限缓存，§9.8 却说缓存条目里必须同时带上 BoardIDs 与 status——两处对同一缓存的内容各说一套。

**为什么是问题**：缓存命中的路径根本没有 JOIN，status 无从校验；封号/改密码走的是"删除该用户全部 Session"，而缓存键是 token 摘要、失效键是 userID，两者不同源，删 session 不会让缓存条目失效。M2 验收又明确写"封号后立刻请求→写接口 401（不能等 60 秒）"：照 §9.2 骨架实现必然通不过自己的验收，照 §9.8 实现则要每请求查一次库（这正是缓存想省掉的 JOIN）。安全语义在文档层面就没有唯一解。

**最小修法**：定死一句——缓存只存 Perms/BoardIDs，status（含 email_verified_at、activated_at）每次 Resolve 单独读或另设 ≤5s 短缓存；同时删掉 §9.8 里"缓存条目必须带 status"，并把"删 session"与"清缓存"写成同一个失效函数。

**置信度**：高（两处原文逐行核对）

## B2 · blocker · v2 §8 全章（第 581-651 行只有 8.2–8.6）；引用点第 583、595、1143、1144、1422 行的"§8.7"；§8.3 第 619-628 行；M3 验收第 1423 行

**问题**：全篇 4-5 处引用"8.7 凭据加密/主密钥轮换"，第 8 章里既没有 §8.1 也没有 §8.7：chacha20poly1305 的密文格式、nonce 管理、**AAD 绑定什么**、`OldKeyHex` 的轮换与重加密流程全部没有规格；同时 M3 验收"重复执行同一任务只发一次"与 §8.4 的实现（MailLog 置 sent 才算发出）不兼容——"Provider.Send 成功但写库前崩溃/超时"这一窗口下重试会再发一封，SMTP 通道连幂等键都没有（Q8 只问 resend）。

**为什么是问题**：AAD 不绑定 account 主键时，密文可在账号之间挪用（同一主密钥下）；轮换路径未定义时，管理员改完账号即可能全线解密失败。幂等验收项与实现机制错位，要么假绿（测试只覆盖"重试前已置 sent"），要么上线后出现重复邮件，而"一次投递只占一次额度"正是靠 MailLog 状态实现的。

**置信度**：高（章节缺失为逐行核对；幂等窗口为逻辑推断）

## B4 · blocker · v2 §21.1 第 1603-1605 行、§21.3 第 1750-1761 行；DB §4.2 第 193-196 行、§12.11 第 613 行

**问题**：next_cursor 只有一个示例 `"eyJpZCI6…"`（疑似只装 id），而默认排序键是 `last_reply_at`（可并列；无回复主题为 NULL，索引写的是 NULLS LAST）、`sort=hot` 是"reply_count + 时间衰减"的表达式；cursor 装什么、怎么编码/加版本、"到底"怎么判定（next_cursor 为空还是 LIMIT n+1）全都没写。

**为什么是问题**：keyset 分页的正确性前提是"排序键唯一且稳定"。只带 id 就必须回查该行取排序值——并发下会漏行/重复行；并列的 last_reply_at 没有 tiebreaker 会翻页丢帖；NULL 排序值在 keyset 里没有定义；hot 是计算表达式，没有可比较的稳定键，"到底"只能靠猜。前端已按 `useInfiniteQuery + next_cursor` 写死（前端 §5.3），契约这一处含糊会直接变成信息流错乱。

**最小修法**：cursor 载荷定死为 `{v, sort, key, id}` + base64url(JSON)，所有排序列补 `(排序键, id)` 复合索引，文档给出 `LIMIT n+1` 的判到底写法；hot 要么物化成 score 列，要么从游标分页里去掉。

**置信度**：高（全库检索无任何 cursor 规格）

## M4 · major · v2 §21.1 第 1610 行、§21.2 第 1653 行、§12.2 第 1121 行、§21.4 第 1792、1794 行

**问题**：幂等只停在声明上——①发帖/回复的 `client_token` 没有表列、没有唯一索引、请求体里也没有这个字段（"可选，P2"）；②"核验已处理返回 409"没写用条件更新实现（`UPDATE ... WHERE state='pending'`），两个管理员并发核验会各自成功并双写 audit；③`PUT /topics/{id}/like` 声明"天然幂等"，错误表却给并发场景一个 `forum.duplicate_like` 409，而前端的 409 分支是"数据已变化，请刷新"。

**为什么是问题**：幂等键必须落在数据库约束上才成立；把并发冲突暴露成错误码，等于在幂等接口上给出非幂等结果（前端乐观更新后弹一个无意义错误）；审核双写会污染审计日志——而审计正是提权追溯的唯一途径。

**最小修法**：topics/posts 加 `client_token` + `(author_id, client_token)` 唯一索引，`ON CONFLICT DO NOTHING` 后返回已存在行；核验改为单条条件 UPDATE + `RowsAffected==0` → 409；点赞冲突一律当成功返回 200，删掉 `forum.duplicate_like`。

## M5 · major · v2 §7.4 第 500-557 行（尤其 550、555 行）；DB §4.10 第 349-372 行；§1 第 11 行

**问题**：四要素叠加后有三个未定义点——①带退避的任务在 pending/running 期间一直占着 `unique_key`，文档没写这期间再 Enqueue 同一个 key 是"静默丢弃"还是"报错"；②领取租约固定 5 分钟、没有续租/心跳，恢复循环会把仍在运行的慢任务（邮件、备份、导入）改回 pending 再跑一次；③两处领取 SQL 不同：v2 §7.4.1 是一步 `UPDATE … WHERE id=(SELECT … FOR UPDATE SKIP LOCKED) RETURNING *` 并宣称"不再需要两步"，DB §4.10 是"先 `SELECT … FOR UPDATE SKIP LOCKED` 再在同一事务 UPDATE"，DB §1 又说这种写法"取代两步领任务"。

**为什么是问题**：唯一键在重试窗口内被占用时，若 Enqueue 选择报错且调用方走的是 `EnqueueTx`，两次入队会把整个**业务事务**一起回滚（用户发帖失败）；若选择静默丢弃，则退避中的任务会吞掉后续同类事件——两种都必须在文档里选一个。租约短于任务时长会把"处理函数必须幂等"从保险变成唯一防线（且邮件那条链路的幂等本身就不成立，见 B2）。两段 SQL 的事务边界与锁持有时长不同，照哪一段写都像对的。

**最小修法**：明确"命中唯一键 = ON CONFLICT DO NOTHING 且返回 nil"（EnqueueTx 同）；按任务类型给租约或加 locked_until 续租；两处统一成一步 UPDATE…RETURNING。

**置信度**：高（占键期与 5 分钟租约为原文，冲突语义确实缺失）
