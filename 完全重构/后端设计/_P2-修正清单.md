# P2 实现阶段的已知修正清单（Lead 汇总）

> 来源：各施工者实测后回报的**硬事实**。P2 各域实现时照这里改，不要按旧设计文字硬写。
> 每条都有出处，不是猜测。

## 1. ent 的事务里怎么跑原生 SQL（D2 读生成代码逐条核实）

| 想做的事 | 正确写法 | 出处 |
|---|---|---|
| 事务里执行原生 SQL | `tx.ExecContext(ctx, sql, args...)` | `ent.Tx` 内嵌 `config`，config 有 `ExecContext`（`internal/ent/client.go:8315`），是**提升方法** |
| 事务里查询多行 | `rows, err := tx.QueryContext(...)` 然后 `rows.Next()/Scan` | `client.go:8327` 的提升方法 |
| **`tx.QueryRowContext`** | **不存在**，别用 | txDriver 只有 Exec / QueryContext |
| `tx.Client().Driver().QueryRowContext(...)` | **也是错的**（有人先这么建议过，已撤回） | `dialect.Driver` 上只有 Exec / Query / Tx |

`*ent.Tx` 确实实现 `queue.TxExecutor`（`app/ent_tx_assert_test.go` 的编译期断言证明），所以 `EnqueueTx` 在业务事务里可用。
**`FOR UPDATE OF u` 这类锁查询必须在同一个事务里**（§8.9 第 1 条要的就是这个），不要为了少写几行把它挪到事务外。

## 2. 事务与依赖（d1 平台层的实际接口）

| 错法 | 对法 |
|---|---|
| `s.db.WithTx(ctx, fn)` | `platformdb.WithTx(ctx, s.db, fn)` —— `ent.Client` 没有 WithTx 方法 |
| 嵌套调 WithTx | 已在事务里的私有函数直接收 `*ent.Tx` 往下传；**不支持嵌套、不模拟 savepoint** |

## 3. 类型与字段（编译期就能发现，但先说省一轮）

- `AuditEntry.TargetID` 是 **`string`**；传进去的 `target.PublicID` 是 `uuid.UUID` → 要 `.String()`。
- 认证 Service 需要 `codes` 字段（`email.go` 用 `s.codes.forget` / `s.codes.bump`），别漏。
- 会话 Resolve / LoadActor 走 `*pgxpool.Pool`（不是 `*ent.Client`）：`Service.pool` + `Deps.Pool`。
- `config.Auth` 有四个运行期参数（d1 已补默认值）：`argon2_max_concur=2`、`argon2_wait_timeout=3s`、`touch_interval=10m`、`renew_interval=24h`。
  **`argon2_max_concur < 1` 会在 Validate 里被拒绝启动** —— 配成 0 时信号量永远取不到，登录会全部挂住（这是配置错误，不是运行期降级）。
- `authz.Set` 有 `Keys() []string`（排序副本），`/me` 的 perms 与审计 before/after 要用它保证稳定顺序。

| # | 根因 | 处数 | 改法 |
|---|---|---|---|
| 1 | `tx.QueryRowContext` **不存在** | 7（account.go:701、email.go:364/385、privileges.go:98/199/268/355） | `rows, err := tx.QueryContext(ctx, sql, args...)` + `defer rows.Close()` + `rows.Next()/Scan`。**别用 `tx.Client().Driver().QueryRowContext`**（dialect.Driver 上没这方法，编译不过） |

| 4 | `newHasher` 返回值个数不匹配 | service.go:59 | `password.go:40` 的 `newHasher` 只返回 `*hasher` → 写 `h := newHasher(...)`，不是 `h, err :=` |
| 5 | `s.db.QueryRowContext` 不存在 | schema_check.go:70 | 同第 3 条：`s.pool.QueryRowContext` |
| 6 | `AuditEntry.TargetID` 是 `string`，传的是 `uuid.UUID` | 4（account.go:647/686、privileges.go:275/323） | `.String()` |
| 7 | 零散 | 2 | `privileges.go:394` 缺 `emailtoken` import；`email.go:374` ent 的 `.Exec(ctx)` **只返回 error**（不是 2 个值） |

**建议（一次改完，省 31 条里的一半）**：把「原生 SQL」统一收到一条路上——

1. `Service` 结构与 `Deps` 都带 `pool *pgxpool.Pool`；
2. **事务里的原生 SQL** 用 `tx.QueryContext` / `tx.ExecContext`；
3. **非事务的原生 SQL** 用 `s.pool.QueryRowContext` / `s.pool.Query`；
4. 两者之外**不再有别的写法**（不要 `s.db.Query*`，不要 `tx.Client().Driver()...`）。

### 6.1 一条会咬测试的坑（先修，否则单测会莫名其妙全 503）

`password.go:41-42` 的 `newHasher` 只有 `maxConcur <= 0 → 2` 的兜底，**没有 `wait <= 0` 的兜底**。
单测直接构造 Service（不走 config.Validate）时 `time.NewTimer(0)` **立刻到期** → 每次取信号量都返回 503 `auth.hash_busy`（**即使信号量是空闲的**）。
表现就是「测试莫名其妙全 503」，很难查。

→ **把 `wait <= 0 → 3s` 的兜底放在同一层**（`newHasher` 里，紧挨着 `maxConcur` 那条）。那一层的既定态度是「不让缺参变成静默失效」。

### 6.2 config.Validate 与 auth 侧兜底的分工（d1 定的）

`config.Validate` 已经拒绝四个死值（`argon2_max_concur < 1`、`argon2_wait_timeout <= 0`、`touch_interval <= 0`、`renew_interval <= 0`）。
所以从配置文件/env 进来的值一定先被挡掉；**auth 侧的兜底只在「不经过 Validate 的构造路径」（单测直接 NewService）才有用**。
**别删兜底，也不用为它写用例。**

## 7. 缺陷类型清单（**看到同类立刻停下**）

今天连着踩的 8 类缺陷有一个共同特征：**两边不一致，但不报错**——只在特定路径上表现为错误结果或运行期报错，
静态读代码几乎发现不了。**写代码时对照这张表自检；发现同类，按 完全重构/缺陷处理总纲.md §4 的四问回报。**

| # | 类型 | 实例 | 为什么难查 | 自检方法 |
|---|---|---|---|---|
| 1 | 复合主键 vs ent 单一 id | `board_acls` / `topic_images` 两个 PRIMARY KEY → PG 报 42P16 | 只在空库跑迁移时炸 | 每张表 grep `PRIMARY KEY`，只能出现一次 |
| 2 | ent 实体有 id、迁移没这列 | 16 张表：ent 读它们生成 `SELECT id` → 生产库 `column does not exist` | **写路径恰好不报**（id 为 nil 会被省略） | 真库跑迁移后比「有实体但表里没 id 列」 |
| 3 | 外键指向 `UNIQUE (hash)` 而非主键 | `users.avatar_hash` / `default_avatars.hash` / `payment_channels.image_hash` → `images(hash)` | ent 的 edge 只能指向主键；建了会在 codegen 报「mismatch field type」 | 不要给这类列建 ent 边，注释写明「走原生 SQL」 |
| 4 | 主键 int vs 外键 int64 | 46 个实体默认主键 `int`，外键全 `int64` | codegen 报的表名常不是真正出问题的那张 | 每个实体显式 `field.Int64("id")` |
| 5 | 部分索引谓词含 `now()` | 「未过期」语义 → PG 拒绝建索引（谓词必须 IMMUTABLE） | 只有跑迁移时炸 | 谓词只写列条件，时间比较留在查询里 |
| 6 | `UPDATE ... FROM unnest(...)` 同目标行匹配多次 | counter 批量写回：PG 只更新一次 → **静默丢增量** | 不报错，数据悄悄错 | 写回前在 Go 侧按 id 合并 |
| 7 | 参数类型靠 PG 推断 | 退避 SQL `$4 + interval` 在 DescribeExec 下 `$4` 被推断成 interval | 报错信息指向加法，真实原因是推断 | 参数处显式转型 `$4::timestamptz` |
| 8 | 配置/档位没落到实际使用处 | 日志打 8 个 worker、实际跑 4 | 日志与行为不一致，所有表面证据都指向正确 | **生产路径与用例共用同一个解析函数**，并做变异验证 |

### 7.1 第 8 类最值得学：怎么让它永久不复发

d1 的处理值得照抄——**光写一条「A == B」的断言没用**（那测的是你复述的逻辑，不是 `NewInfra` 真正走的那条路）。他做的三步：

1. 把解析抽成 `resolveQueue(q, profile)`，**生产路径与用例共用同一份代码**；
2. 用例断言 `got.WorkersFor("") == got.Workers` —— 即「交给 queue 的那个数，正好就是 queue 在 `Run` 里算出来的数」；
3. **变异验证**：把修复退回去，确认用例会红；还原，确认会绿。

> 不加第 3 步，「测试通过」和「测试什么都没测」长得一模一样。

### 7.2 写代码时的三条硬自检

1. **凡是「两个地方各写一遍同一个事实」**（列名、权限点、错误码、任务类型、枚举值、索引名）→ 都要问「有没有一条检查能证明两边一致」。**没有就加一条。**
2. **凡是要靠 PG 推断的东西**（参数类型、隐式转换、`SELECT` 的列）→ 显式写出来。
3. **凡是有默认值/档位/配置参与**（worker 数、超时、limit）→ 让**生产路径与测试读同一个函数**，不要各算各的。

## 8. P2c 报的冲突与定案（2026-10-13）

### 8.1 【必须统一】forum 入队的 payload 形状

**问题**：d3-forum §1625–1628 写的是 `{"post_id": id}` / `{"post_id", "user_id"}`，
而 D4（notify 侧实际实现）要的是 **`{"ref_type", "ref_id", "topic_id", "actor_id"[, "user_id"]}`**。
两边不一致 → **6 个通知任务会全部解析错**（而任务失败是进 dead，不是报错，很容易漏）。

**定案：以 D4 的形状为准**（notify 是消费方，解析逻辑在它那里）。
forum 的所有 `EnqueueTx` 入队点按这个形状写：

    { "ref_type": "post" | "topic" | "comment", "ref_id": <bigint>, "topic_id": <bigint>, "actor_id": <bigint>[ , "user_id": <bigint> ] }

**映射规则**（写死在 forum 的入队点）：
- `likes.target_type='issue_comment'` → 通知里的 `ref_type="comment"`（NotifyLike 只认 post/topic/comment 三个）；
- `ref_type` 与 `ref_id` 在**同一个**入队点算一次，不要两处各算。

### 8.2 【冲突】通知 payload 用内部 bigint，与拍板 §5.6「API 禁止自增 id」

- payload 是**任务队列内部数据**，不是 API 响应；§5.6 管的是 API。
- **定案：payload 用内部 bigint（维持 D4 实现）**。理由：任务在服务端解析，用 public_id 只是多一次转换；
  而且 dedup_key 与 payload 的 id 必须同源（d4 §1.1），混用两套 id 必然漂移。
- 若将来前端要「点通知跳到帖子」，由 API 响应用 public_id 解决（那是**出参**的事，不是 payload 的事）。

### 8.3 【定案】review 通知的 actor 可以为 NULL

d4 §9 自检第 4 条「非 system 通知必须有 actor」在 review 通知上必然破例：**AI 判定时 `topics.reviewed_by` 为空**。
**定案**：给该自检加豁免 —— `kind='review' AND review_source='ai'` 时允许 `actor_id IS NULL`。
（人判的 review 通知仍必须有人；AI 判的没有。）

### 8.4 【定案】CreateInput 的 Extra 字段：保留，但**禁止它变成万能袋子**

`Extra map[string]any` 是为了让 review 的 state/text、sanction 的 until、reward 的 amount_cents 进 payload。
**保留**，但立一条规矩：**只有「某类通知独有」的字段能进 Extra；两类以上共用的字段必须提升为显式字段**（否则它迟早变成没人知道里面有什么的袋子）。

### 8.5 【定案】通知行不带正文摘录（本轮不做）

前端 mock 的 NoticeRow 有 excerpt（被回复内容），但 payload 不放内容快照（快照会过期，d4 §1.1 已定）。
**本轮不做**：要摘录就得在通知里存一段截断文本，那是第二份真源；前端可以按 `ref_id` 再取一次。
若以后要做，正确做法是**通知列表 SQL 里 JOIN 取**（不是存快照）——写进「明确不做」备查。
