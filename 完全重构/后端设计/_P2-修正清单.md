# P2 实现阶段的已知修正清单（Lead 汇总）

> 来源：各施工者实测后回报的**硬事实**。P2 各域实现时照这里改，不要按旧设计文字硬写。
> 每条都有出处，不是猜测。

## 1. ent 的事务里怎么跑原生 SQL（D2 读生成代码逐条核实）

| 想做的事 | 正确写法 | 出处 |
|---|---|---|
| 事务里执行原生 SQL | `tx.ExecContext(ctx, sql, args...)` | `ent.Tx` 内嵌 `config`，config 有 `ExecContext`（`internal/ent/client.go:8315`），是**提升方法** |
| 事务里查询多行 | `rows, err := tx.QueryContext(...)` 然后 `rows.Next()/Scan` | `client.go:8327` 的提升方法 |
| **`tx.QueryRowContext`** | **不存在**，别用 | txDriver 只有 Exec / QueryContext |
| `tx.Client().Driver().QueryRowContext(...)` | **也是错的**（有人先这么建议过，已撤回） | `dialect.Driver` 上只有 Exec / Query / Tx |

`*ent.Tx` 确实实现 `queue.TxExecutor`（`app/ent_tx_assert_test.go` 的编译期断言证明），所以 `EnqueueTx` 在业务事务里可用。
**`FOR UPDATE OF u` 这类锁查询必须在同一个事务里**（§8.9 第 1 条要的就是这个），不要为了少写几行把它挪到事务外。

## 2. 事务与依赖（d1 平台层的实际接口）

| 错法 | 对法 |
|---|---|
| `s.db.WithTx(ctx, fn)` | `platformdb.WithTx(ctx, s.db, fn)` —— `ent.Client` 没有 WithTx 方法 |
| 嵌套调 WithTx | 已在事务里的私有函数直接收 `*ent.Tx` 往下传；**不支持嵌套、不模拟 savepoint** |

## 3. 类型与字段（编译期就能发现，但先说省一轮）

- `AuditEntry.TargetID` 是 **`string`**；传进去的 `target.PublicID` 是 `uuid.UUID` → 要 `.String()`。
- 认证 Service 需要 `codes` 字段（`email.go` 用 `s.codes.forget` / `s.codes.bump`），别漏。
- 会话 Resolve / LoadActor 走 `*pgxpool.Pool`（不是 `*ent.Client`）：`Service.pool` + `Deps.Pool`。
- `config.Auth` 有四个运行期参数（d1 已补默认值）：`argon2_max_concur=2`、`argon2_wait_timeout=3s`、`touch_interval=10m`、`renew_interval=24h`。
  **`argon2_max_concur < 1` 会在 Validate 里被拒绝启动** —— 配成 0 时信号量永远取不到，登录会全部挂住（这是配置错误，不是运行期降级）。
- `authz.Set` 有 `Keys() []string`（排序副本），`/me` 的 perms 与审计 before/after 要用它保证稳定顺序。

## 6. `internal/auth` 当前 31 条编译错误的根因归并（d2-auth 实测，P2a 直接照修）

| # | 根因 | 处数 | 改法 |
|---|---|---|---|
| 1 | `tx.QueryRowContext` **不存在** | 7（account.go:701、email.go:364/385、privileges.go:98/199/268/355） | `rows, err := tx.QueryContext(ctx, sql, args...)` + `defer rows.Close()` + `rows.Next()/Scan`。**别用 `tx.Client().Driver().QueryRowContext`**（dialect.Driver 上没这方法，编译不过） |

| 4 | `newHasher` 返回值个数不匹配 | service.go:59 | `password.go:40` 的 `newHasher` 只返回 `*hasher` → 写 `h := newHasher(...)`，不是 `h, err :=` |
| 5 | `s.db.QueryRowContext` 不存在 | schema_check.go:70 | 同第 3 条：`s.pool.QueryRowContext` |
| 6 | `AuditEntry.TargetID` 是 `string`，传的是 `uuid.UUID` | 4（account.go:647/686、privileges.go:275/323） | `.String()` |
| 7 | 零散 | 2 | `privileges.go:394` 缺 `emailtoken` import；`email.go:374` ent 的 `.Exec(ctx)` **只返回 error**（不是 2 个值） |

**建议（一次改完，省 31 条里的一半）**：把「原生 SQL」统一收到一条路上——

1. `Service` 结构与 `Deps` 都带 `pool *pgxpool.Pool`；
2. **事务里的原生 SQL** 用 `tx.QueryContext` / `tx.ExecContext`；
3. **非事务的原生 SQL** 用 `s.pool.QueryRowContext` / `s.pool.Query`；
4. 两者之外**不再有别的写法**（不要 `s.db.Query*`，不要 `tx.Client().Driver()...`）。

### 6.1 一条会咬测试的坑（先修，否则单测会莫名其妙全 503）

`password.go:41-42` 的 `newHasher` 只有 `maxConcur <= 0 → 2` 的兜底，**没有 `wait <= 0` 的兜底**。
单测直接构造 Service（不走 config.Validate）时 `time.NewTimer(0)` **立刻到期** → 每次取信号量都返回 503 `auth.hash_busy`（**即使信号量是空闲的**）。
表现就是「测试莫名其妙全 503」，很难查。

→ **把 `wait <= 0 → 3s` 的兜底放在同一层**（`newHasher` 里，紧挨着 `maxConcur` 那条）。那一层的既定态度是「不让缺参变成静默失效」。

### 6.2 config.Validate 与 auth 侧兜底的分工（d1 定的）

`config.Validate` 已经拒绝四个死值（`argon2_max_concur < 1`、`argon2_wait_timeout <= 0`、`touch_interval <= 0`、`renew_interval <= 0`）。
所以从配置文件/env 进来的值一定先被挡掉；**auth 侧的兜底只在「不经过 Validate 的构造路径」（单测直接 NewService）才有用**。
**别删兜底，也不用为它写用例。**
