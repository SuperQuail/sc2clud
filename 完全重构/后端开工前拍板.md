## 0. 一句话总纲

**写正确工作的代码，不写防御性代码。** 具体到本项目：

- 不做「以后可能要」的抽象、不写没人调的导出、不为不可能的分支加兜底；
- 校验只做**信任边界**上的（HTTP 入参、外部 URL、上传字节），内部调用之间不加防御；
- 不为了通过验收而写代码：验收命令是用来**发现错误**的，不是用来「满足」的；
- 发现设计不对就推倒重来，现在还在开发阶段，没有兼容包袱。

### 1.4 「一人多角色」作废，**一人一个基线角色**

- 真源：`users.role_id`（单值外键，`ON DELETE RESTRICT`）。
- **不存在 `user_roles` 表**；`数据库设计-postgresql.md` §4.1 里若还写着「一人多角色、授权取并集」，那句话作废。
- 追加权限走 `user_permissions`（点对点，每行必须有 `reason`，`expires_at` 必填）。
- 分配角色的端点：`PATCH /api/v1/admin/users/{id}/role`，body `{ role_id }`。旧的复数 `POST/DELETE /admin/users/{id}/roles` 作废。
- 权限集合 = 基线角色的权限 ∪ 未过期的追加。**角色之间永不并集**。

### 1.5 D6 判定顺序改写

原 D6 写「**任一**角色命中 deny → 拒绝」——那是旧站「一人多组」的残留，单基线角色下没有意义。改写为：

    判定发言权（service 层，不在中间件）：
      1. actor.IsSuper                              → 放行
      2. 命中未过期 Sanction（board_id = 0 或该分区）→ 拒绝（403 forum.sanctioned，带 until）
      3. boards.acl_enabled = false                 → 放行（回到「登录即可发言」）
      4. 该用户基线角色那一行 deny_post / deny_reply → 拒绝   ← 禁止优先
      5. 同一行 can_post / can_reply                 → 放行
      6. 该分区没有任何该角色的行                     → 拒绝（白名单制）

## 2. 帖子类型与审核状态（补 20.2 的空白）

### 2.1 帖子三类

    topics.kind text CHECK (kind IN ('discussion','resource','repost'))

老站就是这个三分法（功能清单 2.2），20.2 第 1 条也写了要保。`resource` 才能挂 `topic_sources`。

### 2.2 审核状态：**必须补，否则老站的审核队列没办法对标**

20.2 只说「M5 只有 normal/locked/hidden/deleted」——那是**可见性**，不是**审核态**。老站有完整的 pending/approved/rejected + 待审修改，13.3 的管理屏也已按它做完。

    topics.visibility text CHECK (visibility IN ('normal','hidden','deleted'))   -- 可见性，默认 normal
    topics.review_state text CHECK (review_state IN ('pending','approved','rejected'))  -- 审核态，默认 approved
    topics.review_note text          -- 「请求修改」给作者看的话
    topics.reviewed_by bigint        -- 审核人（可空）
    topics.reviewed_at timestamptz   -- 审核时间（可空）

规则（service 层）：

1. 是否进审核队列由 `users.trusted` + 分区要求决定：`trusted = true` 或持有 `post.review` → 直接 `approved`；
2. `review_state IN ('pending','rejected')` 的主题**只有作者本人与持 `post.review` 的人可见**（列表与详情都要过滤，搜索也要——见 7.6 的「必须 JOIN topics 过滤 status」）；
3. 主题被回复的可见性**跟随主题**：主题不可见时它的楼层一并对游客不可见（不要在 posts 上再存一份审核态，那是第二份真源）。

## 3. 投票（点赞 / 点踩）契约：**两个计数 + 我的投票**

契约原写 `PUT /posts/{id}/vote` body `{ value: 1 | -1 }`（单值）。但 `@/ui/comment` 是已经验证并登记过的控件，它要 `likes` / `dislikes` / `liked` / `disliked` 四个字段——只给 `value` 前端算不出「12 赞 3 踩」。

**定案**：写接口不变（幂等 PUT/DELETE），**读接口改字段**：

    // 回复 / issue 评论的响应里
    like_count: int      // value = 1 的行数
    dislike_count: int   // value = -1 的行数
    my_vote: -1 | 0 | 1  // 当前登录者的投票；游客恒为 0

理由：改 dto.go 只动后端；改控件要动 4 个文件 + 重出图。主题列表的 `like_count` 也按这个口径（主题只有赞，没有踩——`my_vote` 只有 0/1）。

## 5. 跨域约定（所有模块共用，**唯一一处定义**）

### 5.1 分页：**游标，永远带 id 兜底**

    请求  ?limit=20&cursor=<base64url(JSON{k,id})>       limit 默认 20、上限 100（超出按 100）
    响应  { data: [...], next_cursor: string | null }    next_cursor 为 null 表示到底

- 查询条件恒为「`(k, id) < (?, ?)`」的行序比较（降序用 `<`），**排序键永远带 id 兜底**——否则并列或 NULL 会跨页重复/漏项。
- 常见排序键：`sort=latest` → `(last_reply_at DESC NULLS LAST, id DESC)`；`new` → `(created_at DESC, id DESC)`。**v1 不做 `sort=hot`**（没有物化分数列就没有稳定游标）。
- 复合索引必须与排序键同序，否则每个游标都在排序整个表。
- **禁止 page/offset**。

### 5.2 错误：一个类型 + 一个映射表

    // internal/platform/apperr
    type Error struct { Code string; Status int; Msg string; Fields map[string]string }
    func (e *Error) Error() string
    func New(code string, status int, msg string) *Error
    func Invalid(fields map[string]string) *Error   // common.invalid_input + fields

- 错误码总表见后端方案 §21.4；`Code` 是前后端唯一约定，**handler 不许自己造码**。
- handler 只做一件事：`httpx.Fail(c, err)`。它按 `errors.As(*apperr.Error)` 取 status/code，取不到就 500 + `common.internal`（细节进日志，响应里只说这句话 + request_id）。
- service 返回 `*apperr.Error`；platform 层返回**包了上下文的原始错误**（`fmt.Errorf("...: %w")`），不要 import apperr——那是业务概念。

### 5.3 Principal 传递：**显式入参，不从 context 取**

    service 方法签名：func (s *Service) CreateTopic(ctx context.Context, actor *authz.Actor, in CreateTopicInput) (*Topic, error)
    handler 里：      actor, ok := auth.FromGin(c); if !ok { 401 }

- `authz.Actor` 只带判定需要的东西：`UserID int64` / `PublicID string` / `Perms authz.Set` / `BoardIDs []int64` / `IsSuper bool` / `EmailVerified bool` / `Status string`。
- handler 解出 actor 后**显式传给 service**。禁止 `ctx.Value` 到处捞、禁止 service 里再 `PrincipalFrom(ctx)`。
- 需要登录的 handler 用 `auth.RequireLogin()` 中间件；service 里对危险写操作再 `authz.Require(actor, perm)` 兜底一次（队列/cron/CLI 不走路由）。

### 5.4 事务：`WithTx` 一个入口

    func WithTx(ctx context.Context, c *ent.Client, fn func(tx *ent.Tx) error) error

- **禁止在事务里**：发 HTTP、发邮件、图片落盘、`Queue.Enqueue`（要用 `EnqueueTx`）。
- 事务里只做数据库读写 + `EnqueueTx`。
- 事务函数不要返回 ent 实体再在外面用（实体绑着 tx）；需要返回就在事务内转成 DTO。

### 5.5 时间：一律 `clock.Clock`，一律 UTC

    // internal/platform/clock
    type Clock interface { Now() time.Time }
    type Real struct{}; type Fake struct{ T time.Time }

- 业务代码**禁止直接 `time.Now()`**（测试要能控制时间；`grep -rn 'time.Now()' internal --include=*.go` 除 clock 包外必须为空）。
- 入库一律 `timestamptz`（UTC），出参 RFC3339 UTC，字段名 `_at` 结尾。

### 5.6 对外 ID：`public_id` 一处生成

- 写库前用 `idgen.NewPublicID()`（UUID v7）；**DB 不设默认值**。
- API 响应里只出现 `public_id`（JSON 字段名就叫 `id`），**禁止把自增 bigint 返给前端**；内部外键用 bigint。
- `parsePublicID(s string) (int64, error)` 放各模块共用的一个小 helper（`platform/idgen`），**不要每个 service 各写一遍**。

### 5.7 队列任务：类型常量一处定义，payload 只放 id

- 常量集中在 `internal/platform/queue/types.go`；任务的 payload 是 `{ "id": <bigint> }` 这种最小形状，**不放业务快照**（快照会过期）。
- 处理函数必须**幂等**（先查状态，已是目标态就返回 nil），失败靠退避重试；不可重试的返回 `queue.ErrSkipRetry`。

### 5.8 测试：真 PG，独立 schema

- 集成测试用 `embedded-postgres`（**显式随机端口**，不要用默认 5432）或 CI 的 service container。
- 每个用例 `CREATE SCHEMA test_xxx; SET search_path`，结束 `DROP SCHEMA ... CASCADE`；不要一个用例建一个库。
- 允许在测试里 `client.Schema.Create`；**另有一组走嵌入迁移的测试**（空库 → 全部迁移 → 基本读写），保证迁移文件本身可用。

## 5.9 索引规则（**踩过就会返工的那几条，先写死**）

1. **部分索引的谓词必须是 IMMUTABLE**。PG 会拒绝 `CREATE INDEX ... WHERE ... now()`：

       -- ❌ 建不出来（function in index predicate must be marked IMMUTABLE）
       CREATE INDEX idx_banners_live ON banners (starts_at) WHERE enabled AND now() BETWEEN starts_at AND ends_at;
       -- ✅ 只保留不随时间变化的那一半条件，时间窗口留到查询里
       CREATE INDEX idx_banners_live ON banners (starts_at, ends_at) WHERE enabled;

   所以「生效中的横幅 / 未过期的禁言 / 未过期的追加权限」这类索引，**谓词里只能放列**，时间比较放进 WHERE 查询。
   （`deleted_at IS NULL`、`status = 'pending'`、`read_at IS NULL` 这些是合法的——它们只引用列。）

2. **表达式索引的表达式必须与查询逐字一致**才走索引：`lower(username)` 索引 ↔ `WHERE lower(username) = lower($1)`；
   `date_trunc(...)`、`(a || b)` 同理。**文档里写查询的地方要连写法一起写出来**，否则实现时一定漂。

3. **生成列只能用 IMMUTABLE 表达式**。`tsvector` 生成列可以（`to_tsvector('simple', coalesce(title,'') || ' ' || coalesce(bigram_text,''))` 这类），
   `now()`、`random()`、子查询不行。

4. **复合索引的列序必须与游标排序同序**（拍板 §5.1）：查询是 `(last_reply_at DESC NULLS LAST, id DESC)`，索引就得是 `(last_reply_at DESC NULLS LAST, id DESC)`；
   索引方向写反了 PG 还能反向扫，但 `NULLS LAST` 写错就一定排序整表。

5. **多态表（likes / reports）没有外键**，`target_id` 上的索引要自己建，孤儿行由数据库文档 §12 第 7 条的检查 SQL 兜。

6. **外键列必须显式建索引**（PG 不自动建）。复合主键的第二列不算已索引——`bookmarks.topic_id`、`board_moderators.user_id`、
   `topic_images.topic_id` 这些是**级联删除的真实路径**，要么补单列索引，要么在自检里放负例证明会红。

7. **别建重复索引**（`pg_index` 自比较，数据库文档 §12 第 10 条）。「先建了再说」的结果就是写放大 + 内存浪费。

## 6. 明确不做的（写下来是为了以后不要再讨论）

| 不做 | 理由 |
|---|---|
| `user_roles` 多角色表 | 见 §1.4，单一基线角色 |
| `moderator` 内置角色 | 见 §1.3，作用域用 board_moderators |
| `post_revisions`（待审修改的独立版本表） | 「请求修改」用 `topics.review_note` + 作者自行编辑；独立版本表是为「编辑也要审」设计的，本社区没有这个需求 |
| `sort=hot` | 没有稳定游标，见 §5.1 |

| 网盘 / 文件字节 / 缩略图 | 已定案 |
| Redis 做队列 | `EnqueueTx` 与业务同事务是核心性质 |
| **关注分区**（`board_members` / `boards.member_count` / `joined`） | 2026-10-12 定案：全站只有「收藏主题」一套关注语义，不再加第二套；界面右栏的「关注分区」按钮与「成员」统计格一并从设计里去掉（前端的 mock 保留不动，上线时删） |

## 9. 注册激活（用户 2026-10-12 定的需求，终局）

### 9.1 需求原话

> 「没有做登录页面；一并做了，并且确认设计，打开自动激活则等于使用验证码发邮件，如果验证码机爆了回退到手动激活，但是用户可再次请求，如果发码机又有额度了可以单独给未激活账号验证码激活」

### 9.2 状态机（**两条激活路，互不阻塞**）

注册时创建 user：status='active'，email_verified_at = NULL，activated_at = NULL。

    注册
     └─ 立刻投递「验证邮件」任务（mail:send，idempotency_key = verify:<user_id>:<token_id>）
          ├─ 有账号 + 有额度 → 任务入队 → activation_pending = 'email'
          └─ 一个发信账号都没有，或当天额度全满 → **不再重试**（ErrSkipRetry，避免死循环占队列）
                                         → activation_pending = 'manual'

    路径 A（邮件）
     ├─ 用户收到信 → 点链接 POST /api/v1/auth/email/verify { token }
     │    → email_verified_at = now()，activated_at = now()，activation_pending = NULL，该 token 作废
     └─ 用户没收到 → 「重新发送」POST /api/v1/auth/email/resend（**限流 1/分钟、5/天**）
          → 新 token + 新任务；成功则 activation_pending 回到 'email'（从 manual 也能回来）

    路径 B（管理员手动）
     └─ 后台「激活账号」按钮 → activated_at = now()，activation_pending = NULL
          → **email_verified_at 保持 NULL**（手动激活不等于邮箱验证；两件事不要合并）

    任意时刻：email_verified_at IS NULL 时，该账号都允许再次请求验证码（不限阶段）。

### 9.3 新增字段与状态机落点

    users.activation_pending text NULL CHECK (activation_pending IN ('email','manual'))

| 值 | 含义 | 谁能改 |
|---|---|---|
| `email` | 已入队一封验证邮件，等用户点链接 | 用户「重新发送」/ 邮件任务成功 |
| `manual` | 发不出去（无账号 / 额度满），等管理员手动激活 | 管理员激活 / 用户重新发送成功后回到 `email` |
| NULL | 已激活 | — |

**为什么用一列而不是三列布尔**：它是**一个**互斥状态（email / manual / 已激活），三列布尔会出现「既 email 又 manual」这种要靠约定排除的组合。

### 9.4 与三根状态轴的关系（不要混）

| 轴 | 列 | 判定 |
|---|---|---|
| 封禁 | status ∈ active/banned/deleted | 封号一票否决，任何写操作 401 |
| 激活 | activated_at IS NOT NULL | 能登录、能读；**未激活时写操作 403 auth.not_activated** |
| 邮箱验证 | email_verified_at IS NOT NULL | 目前**只做展示与实际验证动作**，不额外挡功能（20.2 第 22 条那条「未验证只能读」**先不启用**，因为激活已经把写权限管住了；启用会让「手动激活的用户」又不能写，与本次需求冲突） |

> 这一条是对 20.2 第 22 条的**修改**：原文「未验证用户可读不可写」作废，改为「**未激活**用户可读不可写」。回写时同步改 20.2 与 §9.8。

### 9.5 错误码

| code | status | 场景 |
|---|---|---|
| `auth.not_activated` | 403 | 未激活用户的写操作（读不受限） |
| `auth.mail_unavailable` | 503 | 「重新发送」时确认一个发信账号都没有（额度满不算：额度会恢复，属于可重试） |
| `auth.token_invalid` | 400 | 验证 / 重置令牌无效或过期（既有） |
| `auth.too_many_requests` | 429 | 重新发送超限（带 Retry-After） |

「额度满」在发送时**不报错给用户**（用户等了也白等），只把 activation_pending 置 manual 并在登录页提示「等待管理员激活」。

### 9.6 登录页必须覆盖的 7 种情形（前端按这张表做分支）

| # | 情形 | 界面 |
|---|---|---|
| 1 | 正常 | 用户名 + 密码 + 可选验证码（captcha.mode 非 off 时） |
| 2 | 失败 | **统一「账号或密码错误」**，不区分用户不存在/密码错 |
| 3 | 封禁 | 403「账号已被封禁」 |
| 4 | 未激活 + pending=email | 「我们给你发了验证邮件」+ 重新发送 + 改邮箱（改邮箱本轮不做） |
| 5 | 未激活 + pending=manual | 「邮件暂时发不出去，已通知管理员激活，你也可以稍后再点重新发送」 |
| 6 | 限流 429 | 按钮倒计时禁用，显示剩余秒数（读 Retry-After） |
| 7 | 需要验证码 | 出现验证码图（GET /api/v1/captcha） |

**登录成功后**：未激活也允许登录（能读、能重新发送），只是写操作会被 403；不要在登录时就拦死——否则用户连「重新发送」都点不到。

### 9.7 迁移顺序（幂等）

    1. users 加列 activation_pending（可空）；
    2. 已有用户一律置 NULL（他们都已激活：旧站迁进来的按 activated_at 判定）；
    3. 「自动/手动」不是一个配置开关——**它由发信能力自动决定**（有账号有额度就发，没有就 manual）。
       所以**不引入 auth.registration.require_activation 这类开关**（旧站有，新设计不需要：模式是推出来的，不是配的）。

### 9.8 验收（必须能红）

1. 把 mail_accounts 清空 → 注册 → `activation_pending='manual'` 且任务**没有**反复重试（jobs 里该任务是 done 或 dead，不是 pending 堆积）；
2. 恢复一个账号 → 该用户点「重新发送」→ 收到信 → 点链接 → `email_verified_at` 与 `activated_at` 都非空、`activation_pending` 为 NULL；
3. 清空账号 → 注册 → 管理员手动激活 → `activated_at` 非空、`email_verified_at` **仍为 NULL**、`activation_pending` 为 NULL；
4. 未激活用户发帖 → 403 `auth.not_activated`；读帖子 → 200；
5. 「重新发送」第 2 次在 1 分钟内 → 429 + Retry-After。

### 9.10 U19 那条是全局规则的又一例（记下来）

`WHERE ... expires_at > now()` 这类谓词**在任何索引里都不合法**（now() 不是 IMMUTABLE）。
本设计里凡是「未过期」的语义，谓词只能写「未消费 / 未删除 / 状态为 X」，时间比较一律留在查询的 WHERE 里。
涉及：`uq_email_tokens_live`、`user_permissions` 的未过期追加、`sanctions` 的未过期禁言、`banners` 的生效中。**实现时逐条检查这四处。**

## 11. 邮箱激活改成「验证码」而不是「链接」（用户 2026-10-12 定案）

### 11.1 为什么改（不是口味问题，是三个真实故障）

| 链接方案的问题 | 验证码方案 |
|---|---|
| **跨设备必然断**：在 PC 上注册、邮件在手机上看，点链接是在手机浏览器里打开——手机没有那个会话，用户看到的是一脸茫然 | 用户把 6 位码抄回注册页，**在哪台设备注册就在哪台设备激活** |
| **邮箱客户端会拦/改写链接**：QQ 邮箱、企业邮件网关、微信内置浏览器都会做链接安全检测，轻则警告页，重则打不开 | 纯文本的 6 位数字没有任何可拦的东西 |
| **链接是 GET**：容易被预取/安全扫描器**提前消费**（有些企业邮箱会预取链接做检查，用户点的时候已经失效） | 码必须由人输入，不存在被自动消费 |

### 11.2 定案：**只做验证码，不做链接**

- 邮件正文里给一个 **6 位数字码**（有效期 10 分钟），不发链接；
- 注册后的落地页是**「输入验证码」页**，不是「验证成功」页；
- 「重新发送」生成新码，**请求新码时旧码立刻失效**（同 (user_id, purpose) 只留一条活跃记录）。

### 11.3 不新增表、不新增端点（复用既有结构）

email_tokens 原样复用，token_hash 里存**码的 sha256**（与 session token 同一套做法：库里不存明文）：

    -- 既有表，只补两列
    ALTER TABLE email_tokens ADD COLUMN attempt_count smallint NOT NULL DEFAULT 0;   -- 校验失败次数，防爆破
    ALTER TABLE email_tokens ADD COLUMN last_attempt_at ts NULL;
    -- 既有约束 uq_email_tokens_live (user_id, purpose) WHERE used_at IS NULL 继续用：重发即失效旧码

端点**沿用** POST /api/v1/auth/email/verify，body 从 {token} 改成：

    { "username": "...", "code": "123456" }

（用 username 而不是 email：注册后用户手上最确定的是自己刚填的登录名；也允许传 email 二选一。）

### 11.4 爆破防护（6 位数字必须配这个，不能省）

| 措施 | 值 |
|---|---|
| 码长度与字符集 | 6 位数字（crypto/rand，**不用 math/rand**） |
| 有效期 | **10 分钟** |
| 单个码最多试错 | **5 次**——第 5 次失败后该码作废（used_at 置为现在），用户必须重新发送 |
| 重发频率 | 1 次/分钟、5 次/天（既有规则不变） |
| 按账号限流 | 15 分钟内累计 10 次校验失败 → 429（auth.too_many_requests，带 Retry-After） |
| 失败响应 | **统一「验证码不正确或已过期」**，不区分「码错了」与「码过期了」——区分就等于告诉攻击者「码还存在」 |
| 成功响应 | 置 email_verified_at + activated_at，activation_pending = NULL，该码 used_at 置为现在 |

**6 位数字 + 5 次尝试 + 10 分钟 = 单码被猜中概率 5/1,000,000**，再加按账号限流，够用。
（对比：4 位数字加不限次就是可爆破的——长度与次数上限必须一起定。）

### 11.5 「提示码」不做

「提示码」（邮件里写「以 12 开头」这类）只在超长码（8 位以上）时才划算，6 位码没有可用空间，而且它会削弱有效熵。**不做。**

### 11.6 与另外两个「验证码」的区分（写下来免得混）

本站有三样东西都被叫「验证码」，它们是**三套独立机制**：

| 名字 | 干什么 | 存哪 | 谁发给谁 |
|---|---|---|---|
| **邮箱验证码**（本文） | 激活账号 / 找回密码 | email_tokens.token_hash（sha256） | 站点 → 用户邮箱 |
| **图形验证码**（captcha） | 防机器人刷注册/登录 | Redis captcha:&lt;id&gt;，TTL 5 分钟 | 站点 → 用户屏幕 |
| **会话 token** | 登录态 | sessions.token_hash | 站点 → 用户 Cookie |

三者的有效期、失败计数、存储位置都不同，**不要合并实现**。

### 11.7 前端要改的地方（F3 正在做的登录/注册页）

- 注册成功后的落地视图：**「输入 6 位验证码」**（6 格输入或一个 6 位输入框 + 大字号），带「没收到？重新发送（倒计时）」；
- 验证码输入框要 inputmode="numeric"、autocomplete="one-time-code"（手机能自动填）；
- 失败文案统一「验证码不正确或已过期」，**不要**写「还剩 3 次」——那等于告诉攻击者还剩几次；
- 找回密码同理：**输入验证码 → 设新密码**，两步一页，不再有「点邮件里的链接」；
- 原来的「邮箱验证结果页（verify 视图）」改成**「输入验证码」页**；成功后就地显示「已激活，去登录」。

### 11.8 验收（必须能红）

1. 注册 → 收到的邮件正文里**没有链接**，只有 6 位数字码与有效期说明；
2. 输入正确码 → email_verified_at 与 activated_at 都非空、activation_pending 为 NULL；
3. 输错 5 次 → 该码作废，第 6 次即使输对也失败（必须先重新发送）；
4. 重新发送后**旧码立刻失效**（用旧码校验返回同一个统一错误）；
5. 15 分钟内累计 10 次失败 → 429 + Retry-After；
6. 请求新码频率超 1 次/分钟 → 429（既有规则）；
7. 整个流程里**没有任何一步需要点邮件里的链接**（换设备也能完成激活）。

**定案：加一个布尔字段 `review_pending_human`**（含义是「这篇在等人工」，不是「谁判的」）。

| 状态 | 文案 |
|---|---|
| pending + 未转人工 | 「正在自动检查，通常几十秒内完成」 |
| pending + `review_pending_human=true` | 「已转人工审核，通常 1 个工作日内有结果」 |
| rejected | 「未通过审核」+ 理由 + 「你可以修改后重新提交」+ 「申请人工复核」 |

它不下发 `review_source`（不暴露 AI/人工/免审），只说「在不在等人」——与 §10.3 的边界一致。

**4. `?review=` 这个演示开关只存在于 DevRoom**，真实页面由后端 `review_state` 决定——W2 已在代码里标注，正确。
