### D1｜blocker｜数据库设计 §4.1 L99-101/L107-113、§10.2 L536、§11 L581

- **问题**：同一条「旧站未激活」的映射在三处互斥：§4.1 把「激活」定为独立第三轴（`activated_at`，NULL = 可登录不可写），§10.2 写「旧『未激活』不是 status，而是 `email_verified_at = NULL`」，§11 写「旧表的『激活』语义映射到 `email_verified_at IS NOT NULL`，不再是一个独立列」。
- **为什么是问题**：导入是一次不可逆的数据写入，按哪一条写决定这批用户「能不能登录」还是「能登录不能发帖」——两种结果都是线上事故（全员锁死，或未激活用户获得写权限）。三轴模型是 §4.1 花了一段专门论证的设计，§10.2/§11 是没跟上的旧结论，但导入程序作者更可能照 §10 的映射表写。
- **最小修法**：在 §10.2 加一行「旧未激活 → `activated_at IS NULL`（`email_verified_at` 只由旧 `email_codes` 的 consumed verify 判定）」，并把 §11 第 4 条改成同一句话；或反过来删掉 `activated_at` 轴——三处必须只剩一个答案。
- **置信度**：高（三处原文逐行比对；`旧站用户表提取.md` L9 证实旧库是 SQLite、L163 证实实际用户数未知）

### D2｜blocker｜数据库设计 §5 L429-448、§4.2 L182

- **问题**：`topic_search` 没有 status 列，§5 给出的查询只有 `WHERE tsv @@ plainto_tsquery('simple', $1)`；而 §4.2 规定 `topics.status` 的 `pending`/`rejected` 只有作者与管理员可见，`hidden`/`deleted` 是软删。
- **为什么是问题**：搜索是一条**绕过内容可见性**的读路径：未过审内容会被对全体访客（含游客）公开，软删内容继续可搜。这既是越权披露，也让「软删」承诺失效；`search:index` 是否在主题删除/隐藏时删索引行，文档一字未提，等于把安全性交给实现者记忆。排序还要用 `last_reply_at`，说明查询本来就得连 `topics`，却仍没写过滤。
- **最小修法**：查询改为 `FROM topic_search s JOIN topics t ON t.id = s.topic_id WHERE s.tsv @@ ... AND t.status = 'normal'`；`search:index` 任务对 `status <> 'normal'` 的主题删索引行，并把这条写进 §12 自检。
- **置信度**：高（读文档即可判定；四份文档全文无「搜索过滤 status」相关表述）

### D3｜blocker｜后端方案 §17 M7 L1440-1443 vs §12 L1090-1094、§15 L1371；同文档 §9.6 L876、§9.8 L940

- **问题**：M7 仍要求交付 `RewardOrder`/`Wallet`/`LedgerEntry`、`payment.Gateway`、创建订单/回调/对账/超时关闭，验收标准是「同一回调重复 10 次只入账一次；流水总和等于余额」；而 §12 开头明确「Gateway/回调/对账/Wallet/LedgerEntry/余额全部不需要，不要再实现」，§15 第 12 条禁止余额与流水，数据库 §4.6 也确认没有钱包表。残留在同一份文档里的还有 §9.6 为「支付回调」留的 64KB 体限、§9.8 里对应已放弃网盘的 `PermUserQuotaSet = "user.quota_set"`。
- **为什么是问题**：§17 是执行者的排期真源，照它写会造出一整个被禁止、且没有表可落的模块（工期与代码全废）；一旦「余额」真的落库，就重新引入资金不变量与对账债务，正是本项目要摆脱的东西。残留权限点让「代码常量集合 == permissions 表」的启动自检长期带污点（表里有、代码没有只能 Warn），久而久之没人再看这条告警。
- **最小修法**：M7 整段改成 §4.6 的人工核验流（`donation_records` + `reward.verify` + `audit_logs` 留痕 + 撤回/改判规则），删掉 §9.6 的支付回调一行与 §9.8 的 `user.quota_set` 常量及对应迁移行。
- **置信度**：高（四处原文逐行核对）

### D4｜major｜数据库设计 §7 L482-489；后端方案 §9.6 L879-890

- **问题**：2GB 机器的内存总账只算了 Go 进程的一半和 `shared_buffers`，结论却已按「放得下」使用；账里最大的一项（gse 词典 ≤80MB）与依赖实测不符。
- **为什么是问题**：逐项核算（文档口径 → 实际口径）：
  1. Go 基线 80MB（保留）；进程内缓存 + 限流 ≤60MB（保留）；argon2 峰值 2×32MB=64MB（与 §9.1 参数一致，保留）。
  2. **gse 词典：文档 ≤80MB，实测下限已超**。gse v1.1.0 的词典结构是 cedar 双数组 trie + `Dictionary.Tokens []Token`（逐词条），`Token` 字段 `text []Text(24) + freq float64(8) + pos string(16) + distance float32(4) + inverseFreq float64(8) + segments []*Segment(24)` = 对齐后 **88B/词条**；zh 词典 `s_1.txt` 实测 **352,280 行** + `t_1.txt` **236,755 行** ≈ 589,035 词条 ⇒ 仅 Tokens 切片就 **≈49MiB**，再加每词条的 `words` 子切片（CJK 逐字切片，实测 `SplitTextToWords` 每字一个 `Text`）实际量级 **120MB+**。这条预算必须按实测重写。
  3. → Go 侧真实区间 **≈330–450MB**，而不是 284MB；文档自己的「RSS 目标 ≤400MB」只有在词典取小值时才成立。
  4. **PG 侧漏了三大项**：`autovacuum_work_mem` 默认 −1 ⇒ 用 `maintenance_work_mem`（默认 64MB），而 `autovacuum_max_workers` 默认 3（官方文档明确提示「最多会同时分配 3 倍」）⇒ **最多 192MB 完全没进账**；每条连接对应的后端进程本身约 5–10MB（池 16 + autovacuum 3 + pg_dump/psql ≈ 20 个 ≈ 100–200MB）也没算；`work_mem` 被写成「每连接 4MB」，而官方定义是**每个排序/哈希节点**各 4MB（复杂查询与并行 worker 会成倍），实际 64–192MB；再加 WAL 缓冲（shared_buffers/32 = 8MB）。
  5. PG 侧现实区间 **≈430–710MB**；OS + nginx + sshd + 文件缓存 **150–300MB**。
  6. **结论：单实例合计 ≈1.0–1.6GB / 2GB，纸面不超但已无余量**（一次 2MB×N 的图片上传并发、一次 argon2 峰值、一次 autovacuum 风暴都可能压过线）；**若 dev 实例与 prod 同机，再加一个完整 Go 进程 ⇒ ≈1.5–2.1GB，必被 OOM killer 杀掉**。而「dev 是否同机」在两份文档里读不出答案：部署 §3.2 把 prod/dev 两套 systemd unit 与两个库并列在同一份目录结构里，施工计划 L181 又说 dev 用开发机上的 embedded-postgres、「生产机另装」。
  7. 另外，「硬上限 GOMEMLIMIT=600MiB」的措辞不成立：GOMEMLIMIT 是运行时的 GC 目标（软限），活对象本身超限时运行时只能继续增长，它也不约束 Go 运行时之外的内存；全文没有 cgroup/systemd `MemoryMax`（已核实三份文档零命中）。
- **最小修法**：把 §7/§9.6 的预算表改成可核算的四段式「Go（实测 RSS）+ PG（shared_buffers + WAL + 后端数×5-10MB + autovacuum_work_mem×workers + work_mem×节点数）+ nginx/OS」，并显式设 `autovacuum_work_mem=16MB`、`work_mem=4MB`、`max_parallel_workers_per_gather` 上限；gse 一栏启动后打一次 `runtime.ReadMemStats`/pprof 写入日志作为实测值；同时把「dev 必须与 prod 分机」或「dev 与 prod 同机时的进程内存上限」写成一句硬约束（systemd `MemoryHigh/MemoryMax`），并删掉「硬上限」的说法。
- **置信度**：高（词典规模与 `Token` 布局来自模块缓存实测/逐字段核对；PG 默认值取自官方文档；「无 cgroup/无 MemoryMax」为全文 grep 核实；唯一未实测的是 gse 加载后的真实 RSS，故给区间并注明取证方法）

### D5｜major｜数据库设计 §7 L471-489；后端方案 §9.2 L776、L802-811

- **问题**：连接数余量本身够（`max_connections=50` 减默认 `superuser_reserved_connections=3` ⇒ 可用 47；应用池 16 + 队列 4 worker + cron + pg_dump + psql/论坛 check ≈ 22，即使 dev 共用同一集群（部署 §3.2 的 `forum_dev`）也就 ~38），但全文没有任何语句级超时，且 §9.2 仍写着「写库只有 1 个连接」。
- **为什么是问题**：真正会打死服务的是**长事务与卡住的查询**，不是连接总数：pgxpool 没有排队上限，`Acquire` 会一直等到 ctx 超时，HTTP 与队列 worker 共用同一个 16 条连接的池，一条缺 `statement_timeout` 的慢查询就能把池啃掉一块；`lock_timeout` 缺失会让一个锁等待无限期挂住；`idle_in_transaction_session_timeout` 缺失会让「忘了提交」的事务永久占住连接并顶住 vacuum（与 D8 的膨胀叠加）。§10.3 的 `import-users`「全程单事务」与每小时 `pg_dump` 是两个已知的长事务/长快照来源，后者在其整个运行期间持有 xmin，使**所有表**的死元组都不能回收。§9.2 L776 的「写库只有 1 个连接」是 SQLite 时代残留（与 §1「单池取代读写双池」、§7 的 16 连接冲突），会误导实现者继续把写路径当单写者来设计或过度节流。
- **最小修法**：在 pgxpool 的 `RuntimeParams` 里设 `statement_timeout`（如 5s，长任务单独放宽）、`lock_timeout=2s`、`idle_in_transaction_session_timeout=30s`；把 `import-users`/备份这类长事务走独立连接配置并计入池上限；把 §9.2 那句改成「连接池 16 条共享，写路径仍需节流」。
- **置信度**：高（`statement_timeout|lock_timeout|idle_in_transaction` 在三份文档中零命中，已 grep）

### D6｜major｜数据库设计 §12 第 1 条 L591-602

- **问题**：这条「未索引外键」自检只看「某索引的前 n 个键列是否包含外键列」，不看 `indisvalid`、`indpred`、索引方法。反例：`CREATE INDEX ON posts (topic_id) WHERE status = 'normal'` 与 `posts.topic_id → topics.id` 同时存在时，检查会判定「已索引」，而 PG 的 RI 子表查找（`WHERE topic_id = $1 FOR KEY SHARE`）谓词里没有 `status`，用不了这个部分索引 ⇒ 删父行仍全表扫；`CREATE INDEX CONCURRENTLY` 失败留下的 invalid 索引同理。
- **为什么是问题**：自检的全部价值是「能红」。一条把真实缺失判为通过的规则比没有规则更坏（虚假安全感），而部分索引恰恰是本设计 §2.15 鼓励的常规武器，撞车概率很高。
- **最小修法**：`NOT EXISTS` 子查询加 `AND i.indisvalid AND i.indpred IS NULL`；并在 CI 里放一个负例夹具（把某外键的索引换成部分索引后自检必须失败），否则无法证明这条检查会红。
- **顺带核实（对「切片与 @> 是否真的对」的回答）**：**是对的**。`indkey` 是 0 基（PG 核心开发者 Tom Lane 在 pgsql-general 原帖中明确说明，且 `int2vectorin/recv` 的 `lbound1=0`），而 `int2vector::int2[]` 在 PG 里**没有 `pg_cast` 条目**（已核实 `pg_cast.dat` 全文无 int2vector），因此走 `find_coercion_pathway` 的数组分支（该分支注释专门点名 int2vector）生成 `ArrayCoerceExpr`，保留原数组下标 ⇒ `[0:n-1]` 恰好取前 n 个键列；`@>` 的「前 n 列任意顺序包含」对全等值连接的外键查找是正确且更宽松的语义（复合外键不会误报）。表达式索引不会造成误报：其 `indkey` 位置是 0，而 `conkey` 是 ≥1 的 attnum。
- **置信度**：高（PG 源码：`pg_cast.dat`（无 int2vector 条目）、`find_coercion_pathway` 的 oidvector/int2vector 注释分支、`int2vectorout/in` 的 lbound1=0；部分索引不可用于无谓词的 RI 查询为 PG 既定行为。未在真库复现，本机无 PG/Docker）

### D7｜major｜数据库设计 §12 L587-613、§6 L461-463、§2.9 L25

- **问题**：多条自检在 CI 的默认数据规模下恒真或恒假，等于没有门禁：
  - #9「空库跑迁移的结果 vs ent schema snapshot（Atlas diff）」：§2.9 自己承认 ent 声明不了表达式索引、`lower()` 唯一索引「Atlas diff 会想 DROP 它」，扩展/生成列/CHECK 同理 ⇒ 两条 DDL 路径**不可能一致**，这条检查永远红（除非实现者把差异项做成白名单或直接删掉检查，那就是它消失）。
  - #11「没有 Seq Scan 出现在 topics/posts/notifications 上（表小于 1000 行时豁免）」：CI 空库/小库上所有表都豁免 ⇒ 恒绿。
  - #1 在空库上恒返回 0 行，而 M0 的验收恰好是「外键索引自检 SQL 在空库上跑通」——只证明语法没错。
  - #4「用 pg_constraint 解析 CHECK 表达式比对」不可直接执行：PG 把 `col IN ('a','b')` 规范化成 `col = ANY (ARRAY['a'::text, 'b'::text])`，要按这种受控形式解析；且「某个 text+CHECK 列 ↔ 哪一组 Go 常量」的映射规则没定义（§4 里这样的列有十几处）。
- **为什么是问题**：门禁的可信度取决于「在真实形状的数据上能红」；这四条要么恒红（让人学会忽略红），要么恒绿（零保护），而队列表、外键索引这些正是「只写在文档里等于没有」的典型。评审/CI 的认知负担会从「看结果」退化为「猜这条为什么又红了」。
- **最小修法**：#9 改为「迁移目录 → ent 快照」的 Atlas diff + 一份手写对象白名单文件（生成列/CHECK/表达式索引/部分索引），或退化为只比对表与列集合；#11 的夹具先灌 ≥1000 行真实形状数据再断言；#4 明确按 `pg_get_constraintdef` 的 `= ANY (ARRAY[...])` 形式解析并在文档里给出样例。
- **置信度**：高（§2.9/§6/§12 原文互斥；ent v0.14.6 模块缓存内只有 `IndexWhere`、无表达式索引 API，已 grep 核实；`IN`→`= ANY(ARRAY[])` 是 PG 既定重写行为）

### D8｜major｜数据库设计 §4.1 L130、§4.2 L189、§4.7 L325、§4.10 L342-372；后端方案 §7.5 L561-566

- **问题**：设计主动制造了三处持续更新：`sessions.last_seen_at` 批量刷、`topics.view_count`/`release_assets.download_count` 每 15 秒回写、`jobs` 每次领取/完成改 `status`；但全篇没有一处 per-table autovacuum 参数、没有 fillfactor、没有膨胀或事务年龄检查。
- **为什么是问题**：PG 默认 `autovacuum_vacuum_scale_factor=0.2`（表级 20%，加 `autovacuum_naptime=1min`、`autovacuum_max_workers=3`）是按批量装载型表调优的；对「小热区 + 大表」的更新型负载，死元组在很长一段时间内回收不掉，膨胀随行数增长而增长，最后只能停机 `VACUUM FULL`——磁盘、内存、扫描成本三者一起涨，且没有任何指标会提前告诉你（见 D9）。`jobs` 的 `status` 同时出现在两个部分索引里，状态翻转大概率使 HOT 失效，churn 直接落到索引上。
- **最小修法**：给 `sessions`/`topics`/`release_assets`/`jobs`/`mail_quota` 写 `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_threshold = 1000)`（放进手写迁移）；在 `forum check` 里加死元组比例与 `age(relfrozenxid)` 的阈值检查。
- **置信度**：高（默认值取自 PG 官方文档；三处热更新路径为原文；「无 per-table 设置/无膨胀检查」为全文 grep 核实）

### D9｜major｜数据库设计 §8 L493-499、§12 L587-613；后端方案 §9.6 L874-891、§16 L1390-1394

- **问题**：运行期可观测性为零。慢查询、锁等待、连接池耗尽、队列积压、备份新鲜度、PG 事务年龄/膨胀，六项没有一项有采集或告警定义：没有 `pg_stat_statements`、没有 `log_min_duration_statement`/`log_lock_waits`；没有指标端点（`pgxpool.Stat`、`jobs` 的 pending 数与最老 `run_at` 都是现成数据却没接出来）；备份失败只「记 Warn」；唯一的「慢查询闸门」是 CI 里的 EXPLAIN，管不到生产。
- **为什么是问题**：单机自建的故障几乎都是缓慢劣化型（膨胀、连接泄漏、队列堆积、cron 静默停止），没有指标就只能等用户投诉，而且 D5/D8/D10 的修法全都无法验收。四份文档里「监控/告警」相关词零命中（已 grep），说明这不是遗漏一处而是整章缺失。
- **最小修法**：`postgresql.conf` 打开 `log_min_duration_statement=500ms`、`log_lock_waits=on`、`shared_preload_libraries=pg_stat_statements`；给 `/healthz`（或 `/​readyz`）附 `{pool_acquired, pool_total, jobs_pending, oldest_pending_age, last_backup_age, db_size, dead_tuple_ratio}`；备份失败写 ERROR 并让健康检查失败，从而触发部署脚本既有的自动回滚/告警路径。
- **置信度**：高（全文 grep 核实；健康检查端点清单见后端 §17 M0 只有 `/healthz`、`/readyz`）

### D10｜major｜数据库设计 §8 L493-499；后端方案 §16 L1390-1394；施工计划 L164、L171

- **问题**：备份策略与「RPO = 1 小时」不匹配：`pg_dump -Fc` 落在**本机**（图片目录也在本机，dump 不含图片），没有任何异地/站外副本；dump 无校验（无 sha256、无 `pg_restore --list` 抽查）；恢复演练只出现在 S8 一次性切换检查单（施工计划 L171「试恢复过一次」），运行期没有定期演练；磁盘不足时「跳过本次并记 Warn」，而 Warn 没人看；备份由进程内 cron 驱动 ⇒ 进程不跑就没有备份。
- **为什么是问题**：主机/磁盘故障时同盘备份的 RPO 是无穷大，对「打赏申报、发帖」这类**不可重建的用户输入**没有兜底；「备份存在」必须由恢复演练来证明，而一次性演练会随时间腐烂（迁移版本、扩展、角色、目录权限都会变）。`pg_dump` 对在线库只拿 ACCESS SHARE 锁、不阻塞读写（这点文档没错），但它持有整段快照，dump 期间所有表的死元组都不能回收，与 D8 的膨胀叠加——文档没给 dump 的时长预算或「跑完后确认 autovacuum 跟得上」的动作。
- **最小修法**：把施工计划 L164/L171 的两条升级为常态要求写进 §8：每次 dump 后记录 sha256 并 `pg_restore --list` 校验，每周自动恢复到临时库跑一次 `forum check`，把「最后一次成功备份的时间」暴露成指标（D9）并在超期时让健康检查变红；异地副本先用 `deploy.ps1` 已验证过的传输路径。
- **置信度**：高（原文；「站外」二字只出现在一次性切换清单里）

### D11｜major｜数据库设计 §8 L499、§4.8 L329；部署与开发流程 §3.4 L80-84、§3.2 L57-58、L61

- **问题**：dump 里含 `mail_accounts.secret_cipher`/`secret_nonce`（发信凭据密文），而 `deploy.ps1 sync` 会把生产 dump 复制到 dev；§8 的论断「备份不含主密钥，所以快照泄露 ≠ 凭据泄露」只在 dev 使用**另一把** `FORUM_SECRET_MAIL_KEY` 时才成立，文档对 dev 用哪把密钥没有任何规定（§3.2 只说「两个库、两个角色」）。
- **为什么是问题**：只要有人把 `prod.env` 照抄成 `dev.env`，生产的 SMTP/Resend 凭据就随 dump 落到防护更弱的机器上，「凭据在库里加密存储」的收益归零，而且这种配置漂移不会触发任何报错（dev 能正常发信，看起来是「配好了」）。这正是 §8 想避免的那类泄露，却把它交给了一条没写下来的约定。
- **最小修法**：在 §8 与 §3.4 各写死一句「dev 使用独立的 `FORUM_SECRET_MAIL_KEY`」，并要求 sync 之后把 dev 库里的 `secret_cipher`/`secret_nonce` 置空、由 dev 重新录入测试发信账号（或直接禁用 dev 发信）。
- **置信度**：中高（文档确实未规定；需要作者确认是否有意共用主密钥）

### D12｜major｜数据库设计 §7 L471-489、§4.1 L151-163；后端方案 §9.8 L980-986、§15 L1385；部署与开发流程 §3.2 L61

- **问题**：全项目没有数据库权限模型。唯一的角色描述是部署 §3.2 的「两个库、两个角色」（一库一角色），也就是迁移与运行同角色 ⇒ 应用进程在运行期可以 `DROP`/`ALTER` 任何对象；没有一条 GRANT/REVOKE；`pg_trgm` 谁创建、迁移用哪个角色跑（§5 L446 只说「数据库属主可自行创建」）都没有落点；`audit_logs` 对应用可 UPDATE/DELETE，审计行是否与业务变更同事务没写（§9.8 只列了要审计的动作），提权类操作里 `forum create-admin`（授予 superadmin）与自定义角色删除都不在清单里；`sessions.ip`/`user_agent`、`mail_logs`（收件人地址）、`email_tokens`、`audit_logs` 没有留存期与清理任务。`audit_logs`/`audit_log` 两种表名在 §9.8 L982 与 §12 L1106/§4.1 之间也不一致。
- **为什么是问题**：最小权限决定「应用被拿下/被注入」时的损失上限——同角色意味着一个 SQL 注入就能改 schema、改历史；可改写的审计表等于没有审计（提权类操作事后无从追查，这正是 §9.8 自己给审计写的理由）。敏感字段无留存策略则与「数据最小化」直接冲突，且这些表都是只增不减的（`mail_logs` 每封邮件一行、审计每动作一行）。
- **最小修法**：定义两个角色：owner（跑 `forum migrate` 与 `CREATE EXTENSION`）与 `forum_app`（仅表级 SELECT/INSERT/UPDATE/DELETE + sequence USAGE，无 DDL），`REVOKE UPDATE, DELETE ON audit_logs FROM forum_app`；审计写入与业务变更放在同一个 `WithTx` 里；把「`create-admin`、角色删除、封禁、发信凭据变更」补进审计动作清单；给 ip/user_agent/mail_logs/email_tokens/审计各定一个保留期并落成清理任务（见 D15）。
- **置信度**：高（三份文档 grep 无 GRANT/REVOKE/角色定义；「role/权限」相关表述仅部署 §3.2 一句）

### D13｜major｜数据库设计 §5 L429-448、§13 G6 L627；后端方案 §7.6 L568-574、§2 L64、§15 L1366

- **问题**：两件事都靠约定：
  1. **写入放大**：`topic_search` 一行里同时存 `title`、`body_text`（1 楼正文纯文本副本）、`tokens`（切词后再一份）、生成列 `tsv`（再一份索引副本），外加 `gin(title gin_trgm_ops)`，等于每帖 3–4 份文本副本和两个 GIN 索引的写成本；刷新策略在 §13 仍是「待确认 G6」（发帖即入队 vs 定时全量），而 §7.6 已假定「不在发帖请求里同步执行」——触发时机、改帖/删帖如何重建都没有定。
  2. **分词一致性没有机器保证**：查询侧（HTTP handler）与写入侧（`search:index` 后台任务）各自调用 gse，两处只能靠「必须用同一套分词」这句话；分词器配置（词典、`AlphaNum`、停用词）只要有一侧不同，症状是**悄悄搜不到**，没有任何测试或类型约束会发现。
- **为什么是问题**：这是本项目唯一「错了也测不出来」的失败模式，而设计通篇在反对「靠约定」（§12 开头：「只写在文档里的规则等于没有规则」）。§15 L1366 又写着「禁止使用数据库私有语法；tsvector 相关的原生 SQL 只允许出现在 `platform/search/pgsql` 包与手写迁移里」——队列的领取 SQL（§4.10/§7.4）与 §12 的自检 SQL 同样是原生 SQL，却不在这个例外清单内，说明「唯一允许原生 SQL 的地方」这个口径也没有被维护（好在这些语句不含用户输入、搜索用 `$1` 参数化，注入面本身很小）。
- **最小修法**：只暴露一个 `search.Tokenize(string) string`（Segmenter 实例藏在包内、外部构造不出第二个），索引与查询都只能经它；加一个表驱动测试对同一语料断言两侧输出逐字节相同；在 §5 写死刷新触发（发帖/改帖/删帖入队 `search:index`，`unique_key = topic:<id>`）并关掉 G6；`body_text` 若只为检索存在，考虑不落库（或明确它是可重建的派生数据）。
- **置信度**：高（`topic_search` 列定义与查询写法为原文；「无跨侧一致性测试」为文档确认；原生 SQL 例外清单与队列实现冲突可逐条对照）

### D14｜major｜数据库设计 §10.2 L534、§10.3 L543-548；施工计划 L165-166

- **问题**：迁移的判据不可执行、幂等性没有定义验证方法：
  - 施工计划 S8 要求「`forum import-users` **dry-run** 报告已核对（用户数、冲突、需重置口令、头像数）」，但 §10.3 没有 `--dry-run` 旗标，报告列只有 `old_id, username, email, 冲突原因, 处理结果`，产不出这四个计数。
  - §10.3 同时给出「默认单事务」和「`--batch 500` 分批 + 记录断点」两条互斥路径，且没写选择规则；分批模式下「`lower(username)` 已存在则跳过」**不收敛**：进程死在「用户行已写、头衔/经验/头像还没写」之间，重跑会整条跳过该用户，永远缺数据。
  - 头像步骤「复制字节 → 写 `images` 行 → 回填两列」没有原子边界与对账：事务提交后复制失败 ⇒ 坏引用（页面裂图）；复制成功但事务回滚 ⇒ 磁盘上留下**永远不会被回收**的孤儿文件（`image:gc` 只扫 `refcount=0` 的**行**）。§12 也没有「`images` 行 ↔ 磁盘文件」的对账项。
  - 施工计划 L166 的验收「`import_map` 行数与旧库用户数一致」与 §10.2 的邮箱/用户名去重（同一邮箱多账号只保留最早的一个）互相矛盾——去重后行数必然小于旧用户数。
- **为什么是问题**：迁移是唯一「做错就得手工修数据」的环节，它的验收必须是可执行的计数；这里「幂等」被定义成「跳过已存在」，那只保证不重复写，不保证收敛到目标状态。报告在单事务里生成、回滚后仍留在磁盘上也是一种「看似成功」的误报源。
- **最小修法**：定义 `--dry-run`（只读、不写库、输出固定字段：总数/新建/跳过/冲突/需重置口令/头像缺失）并让正式导入复用它；只保留单事务这一条路径（若要分批，改为按 `old_id` 断点 + 每用户级关系表 upsert，并把「半迁移」纳入幂等定义）；头像改成「先落文件 → 再写库 → 最后按 `images` 行对账」，对账计数进 §12；把 `import_map` 的验收改成「`import_map` 行数 = 新建用户数」并与冲突报告互相对账。
- **置信度**：高（两份文档原文冲突已逐行比对；孤儿文件的 GC 语义见 §4.4/`image:gc`）
