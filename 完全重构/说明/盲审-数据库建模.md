## B1 | blocker | 后端方案 §21.2/§21.3（行 1640–1746）× 数据库设计 §3/§4.2/§4.7/§5

**问题**：§21 端点逐条对照后，有 7 处找不到匹配的列或索引：
1. `GET /api/v1/boards`（行 1650）要求返回 `topic_count`：boards 表（§4.2）没有该列，也没有任何计数维护路径。
2. `GET /api/v1/topics?board=X&sort=new`（行 1652）：没有 `(board_id, created_at DESC)`；`idx_topics_board_kind (board_id, kind, created_at DESC)` 的 kind 在中间，无 kind 时无法为 created_at 排序。
3. `sort=hot`（行 1605，按 reply_count + 时间衰减）：无任何索引，且用计算表达式做游标 → 翻页时分数变化，跨页重复/漏项。
4. §21.3 列表项有 `cover`（行 1758）：topics 无 cover 列；topic_images 只有主键 `(topic_id, image_hash)`，无 `(topic_id, sort)` 索引，sort 也无唯一约束。
5. `GET /api/v1/users/search?q=`（行 1641，§20.2#7 要求 nickname 前缀）：users 只有 `lower(username)`/`lower(email)` 与 created_at；nickname 无索引，唯一的 trgm 索引建在 topic_search.title 上。
6. `GET /api/v1/launcher/latest` / `/launcher/releases`（行 1705–1706）：releases 只有 version UNIQUE（§4.7），查 status/channel/published_at 的排序无索引。
7. `POST /api/v1/posts/{id}/images`（每帖 ≤ 9）与 `DELETE /api/v1/posts/{id}/images/{hash}`（行 1674–1675）：topic_images 的键是 topic_id，没有 post_id —— "每帖 ≤9" 与按楼层解引用都无法实现（同一个 `posts` 段在 `PATCH /posts/{id}` 行 1667 里指的是楼层）。
8. `GET /api/v1/notifications?kind=`（行 1689）：列名是 `type`，notification_mutes 却用 `kind`；`idx_notifications_inbox (user_id, created_at DESC)` 不含 type，按类别过滤只能堆上做。

**为什么**：§21 自称"前端唯一依据"，缺列 = 端点写不出来，缺索引 = 上线即全表扫/Sort（§12 第 11 条只禁 Seq Scan，Sort 会漏过），type/kind 漂移 = DTO 与查询各写一遍名。

**最小修法**：boards 加 topic_count（或把 §21 改成计数查询）；补 `(board_id, created_at DESC)`、`(status, channel, published_at DESC)`、`(topic_id, sort)` 与 nickname 前缀/trgm 索引；hot 改成 `(created_at, id)` 固定窗口游标；topic_images 加 post_id 或把端点改成 topic 维度；notifications 列名统一。

**置信度**：高（已核实：逐条读 §21.2/§21.3 与 §3/§4 列清单；grep 全目录确认 `topic_count` 仅出现在 §21.2、`cover` 无列、users 无 nickname 索引）。

## B2 | blocker | 数据库设计 §2.10 与 §12.1（行 591–602），涉及 §4.1–§4.11 各表

**问题**：§12 第 1 条"外键索引自检"（S0 验收项、施工计划行 38）按本设计建表后**必然返回结果**。该 SQL 只比较索引的**前 N 列**与 FK 列，于是复合主键的第二个 FK 列不算"已索引"：user_roles.role_id、role_permissions.permission_id、board_acls.role_id、board_moderators.user_id、topic_images.image_hash、banner_dismissals.user_id、user_titles.title_id、bookmarks.topic_id。另外这些 FK 压根没有索引：email_tokens.user_id、reports.reporter_id/handled_by、sanctions.created_by、announcements.created_by、mail_logs.quota_account_id、images.owner_id、notifications.actor_id、post_issues.closed_by、issue_comments.author_id、donation_records.post_id、users.avatar_hash/avatar_small_hash/equipped_title_id。
该 SQL 也不排除部分索引：messages.high_id 会被 `idx_messages_unread (high_id) WHERE read_at IS NULL AND deleted_by_high=false` 判为"已索引"，但该索引服务不了级联删除与一般查询。

**为什么**：空库上 pg_constraint 已有全部外键 → 检查一开跑就是红的，团队只会做两件事之一：真加索引，或把检查放宽（假绿，从此 §2.10 这条规则失效）。而真实代价就在这些列上：删主题时 bookmarks.topic_id 全表扫、每次 /me 取 board_ids 时 board_moderators.user_id 全表扫（主键前导是 board_id）。

**最小修法**：按上面清单补子表侧索引（小关联表至少补 role_id/user_id/image_hash/title_id/topic_id 单列索引）；检查 SQL 加 `AND i.indpred IS NULL`。

**置信度**：高（已核实：读 §12.1 原文 SQL 与 pg_index/pg_constraint 语义；列与索引逐表对照 §4）。

## B3 | blocker | 数据库设计 §4.11（行 376–396）

**问题**：`read_at` 定义为"**收件人**已读时间"，但未读部分索引是 `high_id WHERE read_at IS NULL AND deleted_by_high=false`（low 对称）——sender 恰好是 high 的消息（high 发给 low、low 未读）同样落在 high 的未读集里 → **自己发的消息计入自己的未读角标**。另缺 `(high_id, low_id, id DESC)`：用户作为 high 一侧时会话列表 `WHERE low_id=$me OR high_id=$me` 只能全表扫（两个部分索引都带 read_at/deleted 谓词，服务不了列表）。附带：没有会话表，per-conversation 的静音/举报/归档/未读清除/彻底删除都无处落；`deleted_by_low/high` 是 bool，没有删除时间 → 无法做保留期与恢复。

**为什么**：未读角标是 S6 验收项（施工计划行 104"未读角标正确"），30 秒全局轮询会把错误计数与全表扫一起放大；会话列表是私信模块的主查询。

**最小修法**：两个部分索引的谓词改为 `sender_id = low_id AND read_at IS NULL AND deleted_by_high = false`（及对称），并补 `(high_id, low_id, id DESC)`；若不打算做按会话的操作，就在文档里明确写"不做"，别留一条读不出来的会话列表。

**置信度**：高（谓词语义由 §4.11 行 384/389 两处定义直接推出，无外部假设）。

## B4 | blocker | 数据库设计 §4.1（行 99–113）/§10.2（行 536）/§11（行 581）× 后端方案 §20.2#22（行 1521）/§21.4（行 1782）× 施工计划 S1–S2

**问题**：激活轴四处互相矛盾，且迁移映射缺列：
- §4.1：`activated_at` 是**独立第三轴**，NULL → 写操作 403 `auth.not_activated`；
- §10.2：旧"未激活"映射成 `email_verified_at=NULL`（不是 activated_at）；
- §11.4（行 581）："旧表的激活语义映射到 `email_verified_at IS NOT NULL`，**不再是一个独立列**"；

而 §10.2 的逐字段映射表**没有 `activated_at`、没有 `trusted` 两行** → 导入程序不会写这两列：activated_at 保持 NULL（按 §4.1，全部老用户不能发帖），trusted 保持 false（全部老用户发帖进 pending，而 §21 没有任何审核端点，§4.2 只说 pending 对作者与管理员可见）。

**最小修法**：二选一定案并只保留一处表述（建议保留 `activated_at`，删掉 §11.4 的说法），§10.2 补 `activated_at`/`trusted` 两行与判定规则，§21.4 补 `auth.not_activated`。

**置信度**：高（已核实：四份文档原句对照；§10.2 表逐行读过并确认缺这两行）。

## B5 | blocker | 后端方案 §12.2（行 1115/1119）vs §21.2（行 1714）× 数据库设计 §4.6（行 292–318）

**问题**：同一个 `POST /api/v1/rewards` 在两章里 body 不同：§12.2 是 `{to_handle, post_id?, amount_cents, txn_id, note?}`，§21.2 是 `{to_handle, post_id?, amount_cents, channel_id, note?}`（无 txn_id）。而 donation_records 表（§4.6）**没有 channel_id 列**，`post_id` 也没有索引；`post_id bigint NULL fk topics` 的名字指向 topics（真要挂楼层就无处放）。`user_donation_settings` 的列在全套文档里**从未定义**：§4.6（行 318）说"两个展示开关"，§12.2 说"三个开关（show_channels/records_public/notice_visible）+ notice_text"，施工计划 S2（行 60）要求迁"打赏三个开关与提示文案"。

**最小修法**：donation_records 加 channel_id（FK payment_channels）与 post_id 索引；txn_id 写回 §21.2；三处统一成"三开关 + notice_text"并给出 user_donation_settings 的列清单。

**置信度**：高（已核实：grep 确认 `channel_id` 全目录只出现在 §21.2；`user_donation_settings` 除主键提示外无任何列定义）。

## B6 | blocker | 数据库设计 §2.6（行 22）/§2.9（行 25）/§6（行 452–464）/§12.9（行 611）+ 施工计划 DoD3（行 152）

**问题**：两条硬要求互斥：
(a) §2.6/§2.9/§6 明确 CHECK、`lower()` 表达式唯一索引、部分索引、生成列、pg_trgm 扩展"**ent 生成不了、只能手写**"，而 §6/§12 第 9 条要求"空库跑迁移的结果 == ent schema snapshot"（CI 必跑）——手写对象在 Atlas diff 里必然是多余项，diff 永远非空；
(b) §2.9 自己承认"Atlas diff 会想 DROP 它"，却没有任何机制阻止它被 DROP（自检第 1 条只查外键索引，§12 也没有"必需表达式索引存在"的断言）。

**为什么**：要么 CI 常态红然后被关掉，要么有人把 `DROP INDEX` 当"对齐 snapshot"提交 —— 而这两个索引是 username/email 唯一性的唯一保证（§2 删掉了 *_normalized 列）。

**最小修法**：CI 加一条"必需索引存在且定义匹配"的 pg_indexes 断言（`uq_users_username_lower`、`uq_users_email_lower`、`uq_likes_target`、`uq_jobs_unique_key` 白名单）；Atlas diff 对这些对象用 `--exclude`，禁止整份 diff 直接采纳。

**置信度**：高（矛盾出自两份文档原文；已核实 ent 行为：本机 `ent@v0.14.6/dialect/sql/schema/postgres.go:141-144` 的 TypeEnum 分支写死 varchar、无 CHECK）。

## M1 | major | 数据库设计 §4.2/§4.3/§4.7/§4.11/§5 + §12（行 591–613）+ §10.3/§10.4

**问题**：8 个派生量与真源之间只有 2 条自检（level↔exp、images.refcount），其余无校验，且软删口径没定义：reply_count 是否含 `status='deleted'` 的楼层与 1 楼？like_count 是否含 value=-1（topics 无 dislike_count，posts 有）？view_count/download_count 是 15 秒内存缓冲（v2 §7.5），崩溃丢窗口且无对账；boards.topic_count 缺列（见 B1）。users.exp / users.level / exp_events 三份真源，§12 只查 level↔exp，不查 exp↔SUM(delta)；exp_events 无 `(user_id,reason,ref)` 幂等键，而队列重试是常规路径（v2 §7.4 第 5 条）。images.refcount 同样：同 hash 二次上传（v2 §10.3 去重）没写 `ON CONFLICT ... refcount+1`，而默认值是 1 —— "上传成功"与"被引用一次"被混为一谈。

**为什么**：派生列一旦漂移就没有权威值可回滚，且漂移是静默的；改"删除回复"的人不会知道要同步 reply_count 口径。refcount 的两种失败都是真损失：少了会误删仍在用的图，多了会永久占盘（GC 只扫 refcount=0）。

**最小修法**：口径写成一句话（如 reply_count = 未软删且 floor>1 的楼层数）并各配一条可红 SQL；exp_events 加 `UNIQUE (user_id,reason,ref) WHERE ref <> ''` + `users.exp = COALESCE(SUM(delta),0)` 自检；images 写入统一走 `INSERT ... ON CONFLICT (hash) DO UPDATE SET refcount = images.refcount + 1`；不需要排序的计数改成读时聚合。

**置信度**：高（§12 十一条逐条对照；v2 §7.5/§10.3–§10.4 原文）。

## M2 | major | 数据库设计 §4.1–§4.9 各表定义（示例：行 167/182/211/243/245/322/329/331）

**问题**：状态/枚举列大面积缺 NOT NULL：topics.kind、topics.status（`DEFAULT 'normal'` 不等于 NOT NULL）、posts.status、issue_comments.status、post_issues.kind/status、reports.target_type/reason/status、sanctions.action/reason、boards.status（连默认值都没有）、banners.kind、releases.channel/status、mail_logs.status、notifications.type。布尔也漏：board_acls.can_post/can_reply（§2.7 要求 `boolean NOT NULL DEFAULT false`）、mail_accounts.enabled（只有 `DEFAULT true`）。`mail_logs.idempotency_key varchar(128) UNIQUE` 可空 → NULL 行不受唯一约束，幂等静默失效。

**为什么**：SQL 里 CHECK 对 NULL 恒为真 → §12 第 4 条"枚举值域自检"永远看不见 NULL 行；`WHERE status='active'` 会静默漏掉 NULL 行；board_acls.can_post 为 NULL 时"任一角色 can 则放行"判否 → 用户被静默拒绝且无从排查（v2 的选型核实 §195 自己写了"ent 的 optional 在 PG 才是真 NULL"）。

**最小修法**：状态/枚举/开关列一律 `text NOT NULL DEFAULT ...` / `boolean NOT NULL DEFAULT false`，`idempotency_key` 加 NOT NULL；§12 第 4 条顺带断言 `attnotnull`。

**置信度**：高（逐表读列定义；NULL 通过 CHECK 与 ent optional→NULL 均为既有语义）。

## M3 | major | 数据库设计 §2.9（行 25）/§4.1（行 106）/§4.2（行 167–168）

**问题**：软删与唯一键没有一起设计：
(a) `uq_users_username_lower`/`uq_users_email_lower` 没有 `WHERE status <> 'deleted'` 谓词 → 账号一旦 deleted，handle 与邮箱**永久占用**（换绑、重新注册都不行），而文档没写这条策略；
(b) boards.slug 是普通 `UNIQUE`（区分大小写），却直接做 URL（`/api/v1/boards/{slug}`）→ `Mod` 与 `mod` 可共存、`/boards/mod` 404，与 username/email 的处理方式不一致；
(c) §2.9 要求查询必须写成 `lower(col)=lower($1)` 才走索引，但没有任何机制保证：ent 生成代码写不出这种谓词，也没有对应自检（自检里没有"表达式索引存在"这一条）。

**为什么**：唯一键是最难回收的资源（释放要改索引 + 处理历史行）；URL 大小写规则不定会变成"分享出去的链接打不开"；表达式索引写不进迁移或查询不按写法来，两种失败都是静默的。

**最小修法**：明确"handle/邮箱是否可回收"，要回收就加部分唯一谓词；slug 统一 `lower(slug)` 唯一 + 字符集 CHECK；把 lower() 查询封装成共享 helper，并加一条表达式索引存在性断言（同 B6）。

**置信度**：高（列定义原句 + PG 部分索引语义）。

## M4 | major | 数据库设计 §4.2（行 182/192–197）/§4.6（行 303）/§4.10（行 344–372）+ §12.6（行 608）

**问题**：三个状态机都没有兜底：
- topics.status 一列塞了三根轴（审核 pending/rejected、可见性 normal/hidden/deleted、互动 locked），非法组合无人拦（如 rejected 且 pinned_at 非 NULL），且 §21 没有审核端点 → pending 只能靠手工 SQL 出队；
- donation_records"改判必须留痕"只落成 §12 第 6 条自检（approved/rejected 必须有 verified_by），不是 CHECK；withdrawn→approved 也合法；该表会变却没有 updated_at；
- jobs 无终态约束（done↔finished_at、dead↔attempts/max_retry 无关）；崩溃恢复（`locked_until < now()`）与 7/30 天清理（`finished_at`）的扫描列都没有索引，`idx_jobs_claim` 是 `WHERE status='pending'` 的部分索引，帮不上。
附带（中置信度）：`uq_posts_topic_floor` 意味着 floor 要用 MAX+1 分配，并发回复会撞唯一键，文档既没写 `SELECT ... FOR UPDATE`（已开 sql/lock）也没写 23505 重试。

**为什么**：状态机写在 service 里，队列、CLI、导入脚本都能绕过；自检是事后扣分不是阻止写入；队列的恢复与清理是每天都会跑的路径。

**最小修法**：topics 拆成 `status` + `review_status` 两列各带 CHECK；§12 第 6 条改写成同义 CHECK；jobs 加终态 CHECK 与 `(locked_until) WHERE status='running'`、`(finished_at) WHERE status IN ('done','dead')` 两个部分索引；回复事务里对 topic 行加 FOR UPDATE。

**置信度**：高（列定义与端点对照；并发一条为中）。

## M5 | major | 数据库设计 §4.3（行 230/243）与 §4.11（行 425）+ §12.7（行 609）

**问题**：
(a) likes 的 CHECK 在同一份文档里有两个版本：§4.3 `ck ('topic','post')`、§4.11"扩展为 `('topic','post','issue','issue_comment')`"，而 §20.2#27 与施工计划 S6 验收要求 issue 投票 —— 照 §4.3 写就拒掉该功能；
(b) likes/reports 无外键的代价只记了"应用在事务里清理 + §12 第 7 条数孤儿行"：没有清理任务、没有保留期，reports 连 target 是否存在都无法校验；
(c) 同一概念 `target_id` 有三种编码：likes/reports 是 bigint 内部 id、audit_logs.target_id 是 varchar(64) 的 public_id/key、§21 请求体一律传 public_id。

**为什么**：孤儿行会永久留在点赞列表与计数里（点进去 404），而 §12 只报数量不清理；三种编码让"按目标查一切"要写三套 SQL，也让多态行与 audit_logs 对不上。

**最小修法**：只留一份 likes CHECK（含四种 target_type）；reports 补 public_id；投票/举报的 target 统一成 public_id 编码，或至少加一条"孤儿行 > 0 即失败"并配 `vote:gc` 队列类型。

**置信度**：高（两份定义原文对照；编码差异逐表读过）。

## M6 | major | 后端方案 §21.1（行 1606）/§21.2（行 1629/1692/1724/1644/1741/1734/1731）× 数据库设计 §2.3（行 19）

**问题**：`{id}` 端点里有 7 类实体**没有 public_id 列**：sessions、notifications、banners（`POST /banners/{id}/dismiss`）、payment_channels、reports（`PATCH /admin/reports/{id}`）、roles（`PATCH /admin/roles/{id}/permissions`）、mail_accounts（`/admin/mail/accounts/{id}`）。而 §2.3 与 §21.1 同时禁止"把自增 id 返回给前端/出现在 URL 与 API"。

**为什么**：实现者只剩两条路 —— 返回自增 bigint（违反硬规则，可枚举、泄露全局行数）或临时发明不透明 id；契约测试 21.6 只检查响应能被 zod 解析，发现不了这个差异。

**最小修法**：给这 7 张表补 public_id（或明确它们用 hash/name/token 作对外标识），并在 §21.2 的路径说明里写清 `{id}` 是什么。

**置信度**：高（已核实：grep `public_id` 的全部出现位置 + §21.2 路径逐条比对）。

## M7 | major | 数据库设计 §2.6（行 22）/§2.7（行 23）/§2.12（行 31）+ §12.4（行 606）+ §4.4/§4.6/§4.9

**问题**：类型约定有例外，且例外不受自检覆盖：
(a) images.visibility 用 `smallint ck in (0,1,2)`、likes.value 用 smallint —— §2.6 规定枚举一律 `text + CHECK`，§12 第 4 条又只遍历"text + CHECK"列 → 这两列的值域永远不被比对；
(b) 真枚举却写成无 CHECK 的 varchar：notifications.type、jobs.type、audit_logs.action、mail_logs.template/provider、notification_mutes.kind、titles.key；
(c) 计数/大小同一概念混用 int 与 bigint（reply_count/like_count/mail_quota.count 是 int；view_count/download_count/size 是 bigint）；
(d) 会变却缺 updated_at：donation_records、reports、post_issues、banners、announcements、jobs —— 与 §2.12 自己的规则冲突；
(e) hash 列用 `char(64)`（images.hash 及各引用列），bpchar 的补空格比较与 length() 语义与 hex 摘要并不等价，无必要。

**为什么**：例外不受自检保护 = 静默漂移；缺 updated_at 会让"这条申报/举报什么时候被改过"无法回答，缓存失效也没有依据。

**最小修法**：visibility/value 改 text+CHECK（或把 §12 第 4 条扩成"所有小整数枚举列"）；6 个 varchar 枚举列补 CHECK；可变表补 updated_at；hash 列统一 varchar(64)。金额（_cents bigint）与时间（timestamptz）本身没有例外，问题只在上面的枚举与计数类型。

**置信度**：高（列定义逐条读；自检范围按 §12 第 4 条原文判定）。

## M8 | major | 数据库设计 §6（行 452–464）/§9（行 503–510）× 部署与开发流程 §3.4（行 80）× 施工计划 S1（行 45）

**问题**：迁移演进只规定了"一次建齐 45 张、已提交不许改"，没有锁与停机规则：golang-migrate 默认把每个迁移包在事务里，而对热表加索引、加 CHECK（要全表校验）、`SET NOT NULL` 都要 ACCESS EXCLUSIVE；文档既没写 `lock_timeout`/`statement_timeout`，也没写 CONCURRENTLY 与"加列 → 回填 → SET NOT NULL"的顺序 —— 而 §12 想把更多自检写成 CHECK，正好都是锁表操作。另：内置角色/权限点"由迁移幂等插入"（行 146、v2 §9.8），而 §2.12 规定 created_at 由 ent mixin 在应用层写、DDL 默认值必须用 `entsql.DefaultExpr` —— 迁移里的裸 INSERT 必须自己给 created_at，文档没写。`deploy.ps1 sync` 把生产 dump `--clean` 恢复到 dev 后直接起服，会撞上"迁移版本不一致拒绝启动"（§6），流程里没有 restore → migrate 这一步。

**为什么**：这些只在生产上暴露（迁移卡在长事务后面 → 全站写阻塞），而 S1 一次性交付 45 张表意味着后续所有演进都在同一套规则下做。

**最小修法**：迁移模板加 `SET lock_timeout='3s'; SET statement_timeout='30s'`；写明"热表新索引用 CONCURRENTLY（放在不包事务的迁移里）"与三步加列法；seed 迁移显式写 created_at；sync 流程补一步 `forum migrate`。

**置信度**：中高（PG/golang-migrate 行为是既有事实；sync 后果由两份文档的规则直接推出）。
