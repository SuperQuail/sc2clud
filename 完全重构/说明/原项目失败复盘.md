# 原项目失败复盘（SC2clud 旧站）

> 只读调查结论；证据取自主库 `site/`（HEAD = dev-side，262 次提交，Rust 24k 行 / HTML 2.8k 行 / 迁移 36 个）。
> 目的：给“完全重构”一份可评审的对照表 —— **为什么烂**（根因）、**禁止再做什么**（黑名单）、**最容易无意识复刻什么**（遗留陷阱）。
> 不列 bug 清单，不给补丁。

## 1. 一句话结论

**失败的本质是“一切都是就地手工拼的”：每个业务概念在代码里没有唯一归属。**
因此每加一个功能，就要把同一套规则在“枚举、SQL、处理器、模板、前端脚本、nginx 配置、迁移”里各写一遍；
每改一个需求，就要同步 N 处；漏掉一处不会报错，只会静默错——于是缺陷永远修不完，
只能靠“再补一个脚本、再写一条注释、再加一次兜底”往前爬。文档里写的架构其实是对的，**但它没有被代码强制执行**。

## 2. 根因清单（按严重度排序）

### 根因 1｜业务事务在请求层“就地拼”，没有领域边界
- 现象：写操作由 handler 顺序 `await` 若干仓储函数拼成，中途失败留下半成品；改一个流程要通读整个 handler。
- 证据：
  - `crates/sc2clud-web/src/pages_posts.rs`：第 787 行起的保存流程 **449 行 / 19 次仓储调用 / 26 次 await**；发帖 `new_post_submit` 209 行 / 6 次仓储调用；帖子详情 `build_post_page` 423 行 / 15 次仓储调用。
  - `crates/sc2clud-db/src/repo.rs` 自述“多语句写操作一律放事务句柄”，但全库 `begin()` 仅 12 处（对应 382 条 SQL），`repo.rs` 254 个 `pub fn` 中的写操作大多无事务。
  - `repo::ensure_super_admin`（repo.rs 第 55 行起）跨 users 表两次写入无事务。
- 根因：**领域规则只存在于“这次请求怎么走”的散文里**，没有被建模成一个原子的用例；数据库层只提供裸 SQL，不提供“操作”。
- 新架构对策：必须做到——每个业务动作（发帖、审批、打赏入账）是一个**用例单元**，其全部写操作在同一事务内提交，失败整体回滚；禁止在 HTTP 处理器里直接编排多步写入。

### 根因 2｜同一个领域概念有 2–4 份独立实现（真源分裂）
- 现象：同一份查询/规则被复制粘贴；改一处漏一处，同类缺陷反复复发。
- 证据：
  - `repo.rs` 中帖子列表 SELECT 出现 3 次、`comments/post_likes/post_bookmarks` 计数子查询各 4 次、`UPDATE blobs SET refcount = refcount - 1` 3 次。
  - `crates/sc2clud-core/src/resource.rs` 分区 key→展示名→权限 三张表（第 14/38/48/75 行）随枚举同增；权限门槛又分散在 `auth.rs::min_role()`、`session::guard`、`ensure_section_action`、模板判断。
  - `AGENTS.md` 自述“改权限必须同时改三处”——写下这句话，等于承认没有单一真源。
- 根因：**没有“唯一真源 + 派生”的结构**，只有并列的副本；耦合不是类型上的，而是“你得记得改哪里”的。
- 新架构对策：必须做到——一个领域概念只允许一处权威定义，其余全部由它派生（生成/查询/编译期校验）；发现第二份实现必须当场合并。禁止复制 SQL、复制权限判断、复制展示名映射表。

### 根因 3｜列表在循环里逐行查库（N+1），把延迟和一致性风险一起放大
- 现象：一个页面要几十到几百次串行查询；页面各区块互相看不见对方的数据版本。
- 证据：
  - `crates/sc2clud-web/src/pages_admin.rs` 第 88–122 行：单次渲染先 `admin_list_users(200)` + `count_users` + `list_pending_posts` + `quota_totals` + `list_sections`，随后 **`for row in &rows` 内每行调一次 `active_sanctions`**，再对每个用户组循环 `list_group_members`；第 190–193 行再来一遍。
  - 同样的“先主查询再逐行补数据”散落在 `pages_posts.rs`、`pages_profile.rs`、`pages_messages.rs`。
- 根因：**仓储 API 是“单行取数”形状，页面却需要“聚合视图”**；缺一个能一次取全所需字段的读模型，于是把组装推给了调用者。
- 新架构对策：必须做到——列表/详情由**专用读查询（一次 JOIN + 聚合）**产出完整视图；禁止在渲染循环里发查询；性能门禁上按“每请求查询条数上限”量化验收。

### 根因 4｜“模式常量”与“声明的事实”一致靠人记，不一致时静默
- 现象：加了数据，页面不显示；改了配置，运行期行为没变——都不报错。
- 证据：
  - 分区 key 写死为枚举 `PostSection`（`resource.rs:14`），而 `crates/sc2clud-web/src/routes.rs:892-911` 的 `ordered_sections` 用 `PostSection::parse(&key)` 过滤，**未知 key 被 `if let Ok` 静默丢弃**；同处 `list_sections(...).unwrap_or_default()` 把“查库失败”变成“空列表”。实测手写 SQL 插入的分区“数据库有行、首页不显示”。
  - 模板与开关漂移：`crates/sc2clud-web/templates/admin.html:22` 无条件渲染“自检面板”链接，而路由只在 `debug_pages=true` 时注册（`crates/sc2clud-web/src/lib.rs:118`）→ 生产点它必 404（用户实测过）。
  - 配置与边缘同义反复：nginx 侧要跟应用对齐 `BASE_URL / DOWNLOAD_PREFIX / INTERNAL_PREFIX / DOWNLOAD_MODE / COOKIE_NAME`（`crates/sc2clud-core/src/config.rs` 才有完整 14 个键，而 `.env.example` 9 个、`secrets/env/production.env.example` 仅 5 个），没有一处校验两侧一致。
- 根因：**数据/配置是“真相”，代码里却另存一份“事实”，两侧只靠人维持同步**，且不同步被设计成“继续跑”。
- 新架构对策：必须做到——枚举式清单必须由数据生成，或启动时校验并**拒绝启动**；页面渲染前校验声明与数据一致（宁可 500，不要静默漏）；跨进程契约（nginx↔应用）要有单一生成源 + 启动自检。

### 根因 5｜有副作用的操作被“吞错”，可观测性被自己写没
- 现象：操作看起来成功，审计/通知/落库实际没发生；故障无迹可查，只能靠人工 curl + 看库推。
- 证据：
  - `unwrap_or_default()` 在 `crates/sc2clud-web/src/` 出现 **58 次**，`let _ = ` 出现 **56 次**；典型：`admin_ai.rs:230/244` 丢弃 AI 审核落库与状态回填，`admin_users.rs:209` 丢弃会话清理，`admin_posts.rs:117/149`、`admin_titles.rs:75/161`、`admin_content.rs:200/387` 丢弃审计写入——**审计链路整体不可靠**。
  - `pages_posts.rs:1908` 通知写入失败直接忽略；`pages_posts.rs:1932-1934` 处罚查询失败按“无处罚”继续。
- 根因：**写路径与读路径共用一个“容错”习惯**；容错只该属于“读不到还能更好降级”，被误用到“写入必须成功”的地方，等于删掉证据。
- 新架构对策：必须做到——类型上区分“可降级的读”与“必须成功的写”：写失败必须回滚并影响响应（或进可查询的补偿队列并告警）；禁止 `let _ = ` 吞掉有副作用的调用；每个用例记录可检索的结构化事件（谁、什么、结果）。

### 根因 6｜HTTP 契约与前端数据协议是手写双份
- 现象：前端发的内容类型/字段名与后端提取器不一致 → 422；同一页面里的链接前缀在 dev 与生产不同 → 请求打错环境。
- 证据：
  - `AGENTS.md` §9 记录：编辑用户保存 422（“提取器拒绝请求体”），本月同类已出现两次（“社区开关缺 enabled 字段”、“inbox 内联脚本语法错”）。
  - `web/src/` 根目录并列 10 个手写模块（auth/admin/avatar/account/home-reader/home-urls/auth-urls/post-images/theme），其中 `auth.ts:1`、`admin.ts`、`avatar.ts`、`account.ts`、`home-reader.ts` 各自 `fetch`；而规范声称“全站只有 lib/ 允许 fetch”——根目录模块成了影子数据层。
  - 路径前缀问题修过多次（提交 689cb5c“评论头像/帖子编辑链接/issue 链接改走 appUrl”），说明前缀是散在模板与脚本里的字符串。
- 根因：**契约不是可检查的产物**，后端出参（模板字段名 + `data-*` + JSON）与前端入参（手写 fetch）是两份手抄本，靠“记得同步”。
- 新架构对策：必须做到——请求/响应用**单一协议定义**（schema/类型）在两侧生成；禁止手写 URL 与字段名；URL 构造只允许一个入口；端到端契约测试覆盖每个写端点。

### 根因 7｜UI 逻辑被挤进模板与全局脚本，前端没有“入口/边界”
- 现象：同一个交互在两处实现；改一处另一处坏；页面体积与预算失控。
- 证据：
  - `crates/sc2clud-web/templates/inbox.html` 第 158–286 行是 **128 行手写 DOM + SSE + 轮询脚本**；模板全站统计：16/30 个模板含 `<script>` 或 `<style>`，`inbox.html` 有 5 处内联事件处理器。
  - `templates/base.html`：第 6–19 行内联主题脚本、第 89 行起内联 fab/未读徽标脚本，且**第 29–31 行的 CSS `<link>` 写在 `</head>` 之后**（无效位置，靠浏览器容错）。
  - 产物与预算口径脱节：`static/islands/postform.js` **474 KB**（压缩后约 164 KB）对上限 200 KB 的“具名豁免”；`index.js` 143 KB、`select.js` 87 KB；`docs/BUDGETS.md` 另记 66.6 KB（口径不同）。
- 根因：**没有“一个页面一个入口”的约束**，模板被当作可以放任何东西的地方；交互逻辑没有归属，就在“就近”的位置写第二次。
- 新架构对策：必须做到——模板只输出结构与数据（含挂载点）；一切交互属于明确的前端模块；全局脚本只允许一个外壳入口；体积预算进 CI 且口径唯一（原始/压缩只准选一个并写进门禁）。

### 根因 8｜迁移只前进且不还债，历史状态永远留在库里
- 现象：新代码要同时兼容“旧列/新列两种真实”；权限从布尔改档位后，语义靠注释表达。
- 证据：
  - 36 个迁移中至少 14 个是纯加列/改列（0004、0006、0007、0010、0015、0017、0019、0021、0023、0025、0026、0027、0034、0035）；`0034_blob_visibility.sql` → `0035_blob_visibility_levels.sql` 把布尔升级成三档，旧列语义仍留在库里。
  - 敏感信息曾经直接入库：`0029/0030/0031/0036` 建有 `ai_secrets`、`smtp_accounts`、`mail_accounts` 等含密钥列的表。
- 根因：**“只加不删”被当成安全策略**，实质是没人负责收尾；模式演进的历史沉积成了永久兼容负担。
- 新架构对策：必须做到——每次结构演进必须成对交付“新语义 + 旧状态迁移/清理”；禁止保留语义已废的列或表；密钥类数据禁止进业务库（只存引用，密钥在专用密钥存储）。

### 根因 9｜生产即测试环境，验证不可复现、不可审计
- 现象：验证靠“对生产站 curl + 直接查库”，验证完再手工把生产改回去；没有可重复的回归。
- 证据：
  - 仓库外层根目录 70+ 个一次性脚本（social_test.sh、admin_test.sh、feature_test.sh、flow.ps1…），每个自带 `BASE=http://191.40.41.97`、`DB=/srv/sc2clud/data/sc2clud.sqlite3`，启动即 `set-password tangtian <口令>` 改生产账户口令，`sqlite3` 直插/直删生产数据，测试尾部再把口令改成随机值。
  - 明文口令留在脚本里：`admin_test.sh:18`（password=hello-miyin-2026）、`admin_edit_test.sh:7/28`、`admin_ui_test.sh:7` 等十余处；`secrets/ssh/id_ed25519_deploy`（私钥）与 `server_data/pin.txt` 明文存放（未入库，但工作区里就是明文）。
  - 站点长期无域名无证书，用 IP + http 验证；也因此无法验证 Secure/SameSite 等 Cookie 行为（`部署记录.md` 待办第 1 条）。
- 根因：**没有“测试环境”这个一等公民**，测试不是代码库的一部分而是操作者的临时命令行；反馈回路不可重复，也就不能积累。
- 新架构对策：必须做到——本地/CI 一键起完整栈（含 nginx 或等价边缘模拟）跑端到端；测试不得依赖生产凭据，不得改生产数据；凭据只从密钥存储读取；CI 日志与产物可追溯。

### 根因 10｜构建产物的流转是一条跨机器手工接力
- 现象：新前端产物上线后 404；“改了没生效”反复出现，排查成本高。
- 证据：
  - 前端产物目录 `crates/sc2clud-web/static/islands/` 被 `site/.gitignore` 忽略，服务器无 Node（`部署记录.md`），因此链路是：本机 `pnpm -C web build` → `deploy/islands-push.ps1` scp 到 `/srv/sc2clud-dev/islands-upload` → `deploy/dev.sh` 拷回仓库再编译 → `deploy/promote.sh` 推生产。
  - 该顺序写死在注释里（deploy/dev.sh：“必须在构建之前把开发者上传的产物放进仓库 static/islands，否则运行期 404”），并注明“2026-10 踩过一次：新面板的岛全 404”；提交 cf3930d、0b8b602（后被 fcdf3f3 revert）都在补这条链。静态资源是**编译期嵌入**二进制的，运行目录只做兜底。
- 根因：**产物没有单一来源和可复现的构建入口**，谁在什么机器上构建、是否先于编译同步，全靠人按顺序操作。
- 新架构对策：必须做到——一条命令从干净检出产出可部署物（含前端），产物由 CI 产出并带版本号；禁止“本地构建 + scp + 服务器再编译”这种跨机接力；部署前后各跑一次自检（资产存在性 + 版本号一致性）。

### 根因 11｜门禁与开发主线脱节，规则写完就没人执行
- 现象：文档里的硬预算与规则持续被突破，却没有红灯。
- 证据：
  - `.github/workflows/ci.yml` 只对 `main` 的 push 与 PR 触发；而日常开发分支 `dev-side` 领先进 193 个提交（`git rev-list --left-right --count main...HEAD` → `0  193`），CI 覆盖不到实际被改的代码。
  - 该 CI 只跑 fmt / clippy / test / smoke / 前端 typecheck+build+check-budgets.mjs；**`scripts/check-size.mjs`（文件体量）与 `scripts/check-path-prefix.mjs`（路径前缀）都没进 CI**——而这两条恰恰是过往反复踩的坑。
  - 结果：`postform.js` 474 KB 与 200 KB 豁免并存；`repo.rs` 5044 行 / `pages_posts.rs` 2031 行长期挂在“待重构清单”。
- 根因：**规则以自然语言存在，执行以人工习惯存在**；门禁位置（分支、时机）与实际工作流不一致。
- 新架构对策：必须做到——每条架构规则都有对应可执行门禁，且门禁跑在**实际会合入的分支与 CI 上**；规则文档只解释“为什么”，数字与阈值由门禁持有；逾期豁免必须带截止条件，不允许无限续期。

### 根因 12｜反馈回路失效的代价被“就地打补丁”吸收，缺陷因此常驻
- 现象：同一个问题以不同形态复发；文档里积累的缺陷条目越来越多（`AGENTS.md` §9 已记 10+ 条），每次都靠“下一轮再修”。
- 证据：
  - 262 个提交里存在大量“修一处→坏一处→再修”的序列：提交 2dae55e（补 import、补 tsconfig、删死岛、改探针）、09217ac（DOM 嵌套错位、页高 23541px）、71751e9（模板内联脚本语法错）都属同一类——改动边界没有类型或测试托底，只能事后发现。
  - 同一形态的问题在 `AGENTS.md` §9 里并列出现：“自定义分区看不到”“自检面板链接 404”“编辑用户 422”“收款码 404”——分属不同功能，却都是根因 2/4/6 的不同投影。
- 根因：缺少“改动必须触及的清单”这一层结构（callers/tests/fixtures/契约），只能靠人临场回忆边界。
- 新架构对策：必须做到——每个改动以测试与契约清单圈定范围；新增/修改行为必须有对应验证；重复出现的缺陷形态必须上溯到结构（合并真源、加门禁），禁止只补症状。

## 3. 反模式黑名单（重写时明确禁止，可检查）

| # | 禁止 | 可检查规则 |
| --- | --- | --- |
| 1 | HTTP 处理器里直接编排多步写库 | handler 中不得出现两次以上写仓储调用；写操作必须经由用例层 |
| 2 | 多语句写操作不开事务 | 写仓储函数体若含 ≥2 条写 SQL，必须出现事务边界 |
| 3 | 同一 SQL / 同一规则复制第二份 | SQL 文本与权限判断的重复片段检测，重复即失败 |
| 4 | 渲染循环内查询 | 渲染/视图函数体内不得出现数据库调用（应在读模型里） |
| 5 | 枚举/常量清单与数据并列维护 | 新增分区/类型必须零代码改动；启动时校验，不一致拒绝启动 |
| 6 | 静默丢弃未知值、静默降级失败写 | 禁止 `if let Ok` / `unwrap_or_default` / `let _ = ` 包裹写操作；未知 key 必须报错 |
| 7 | 手写 URL、手写请求字段名 | fetch 与 URL 构造只允许出现在协议层；其余位置出现即失败 |
| 8 | 模板内业务 JS、内联样式、内联事件 | 模板不得含 `<script>`（外壳单入口除外）、`<style>`、`on*` 属性 |
| 9 | 页面级“具名豁免”式预算放宽 | 豁免必须有到期条件与负责人；超限即失败 |
| 10 | 密钥/口令进库、进脚本、进仓库 | 脚本与迁移中不得出现字面口令；密钥只从密钥存储读取 |
| 11 | 测试改生产数据、依赖生产凭据 | 端到端测试只对本地/CI 环境；脚本中不得出现生产 IP 与主机路径 |
| 12 | 跨机器手工接力部署 | 部署物由 CI 产出；本地构建产物不得作为部署输入 |
| 13 | 只在非开发分支跑门禁 | CI 必须覆盖实际开发分支；体量/预算/前缀门禁全部在 CI 内 |
| 14 | 语义废弃的列/表长期保留 | 结构演进必须成对交付清理迁移；发现无引用列即失败 |

## 4. 遗留陷阱（重写时最容易无意识复刻）

1. **把 SQL 搬过去、交互模式照旧**：新后端沿用“单行取数 + 处理器拼装”，N+1 与半成品状态会原样复刻。→ 验收看“每请求查询条数”和“用例事务边界”，不是看语言。
2. **实体字段镜像成手写 DTO**：旧站把 DTO / 视图模型 / 模板结构体混在一处（`crates/sc2clud-web/src/templates.rs`：67 个结构体 / 24 个模板），照抄则字段漂移会回来。→ 协议由 schema 生成。
3. **“先跑起来再说”的枚举**：把分区、类型、权限位再写成常量数组，下一个需求出现时又变成根因 4。→ 第一次就表驱动。
4. **边缘配置继续手抄两份**：nginx 与应用各写一份前缀/TTL/模式，靠 install.sh 打补丁同步。→ 生成或启动自检。
5. **容错习惯照搬**：新代码继续 `unwrap_or_default` 兜住写失败，等于把旧站最难查的一类故障带过去。→ 类型上分离读降级与写必成。
6. **“验证靠人点”照搬**：没有可一键起停的端到端环境，就会继续“改一处坏一处、上线后才发现”。→ 环境是代码。
7. **文档先行、门禁缺位**：重写最容易产出更漂亮的架构文档而不产出对应的失败门禁；旧站文档质量并不差，差的是执行。→ 每条规则配一个会红的检查。
8. **预算口径混用**：旧站同一份产物同时用“原始/压缩”两个口径陈述（474 KB vs 164 KB vs 200 KB），预算永远说不清。→ 一个口径、一个数字、一个门禁。

## 5. 给新架构的最小验收线（与根因一一对应）

1. 用例层存在且写路径原子（根因 1）；
2. 任一领域概念只有一处定义，且可机器验证（根因 2、12）；
3. 每请求查询条数有上限并被度量（根因 3）；
4. 数据与代码清单一致性由启动校验或生成保证（根因 4）；
5. 写失败必定可见、可回滚、可追溯（根因 5）；
6. 请求/响应契约由单一协议定义生成，端到端契约测试通过（根因 6）；
7. 模板无脚本、前端有单一入口、体积门禁在 CI（根因 7、11）；
8. 结构演进带清理，密钥不进业务库（根因 8）；
9. 端到端测试可一键在本地/CI 复现，且不碰生产（根因 9）；
10. 部署物由 CI 产出，一条命令可部署并自检（根因 10）。
