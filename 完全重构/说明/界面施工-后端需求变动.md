## 1. 口径冲突（先解决这个，否则后面每条都要重写）

### 1.1 【已确认】权限点命名有两套：`post.*` 与 `topic.*`

| 出处 | 用的名字 |
|---|---|
| `论坛后端技术方案-v2.md` §21.2 端点表 | `post.create` / `post.update_own` / `post.delete_own` / `post.delete_any` / `post.lock` / `post.pin` |
| `RBAC权限树设计.md` §3 角色矩阵（**权限的唯一真源**） | `topic.create` / `topic.edit.own` / `topic.delete.own` / `topic.delete.any` / `topic.lock` / `topic.pin` / `topic.feature` / `topic.move` |
| `论坛后端技术方案-v2.md` §20.2 第 15 条 | 「权限点无」……同章其它条又用 `post.create` |

**为什么必须现在定**：RBAC 文档自称「权限的唯一真源」，且 §6 有一条启动自检「`permissions.key` 集合 == 代码常量集合」。
两套名字并存时，这条自检要么红、要么被迫放水——而 旧站根因 11 说的就是「规则没有落点于是没人执行」。
另外前端 `/api/v1/me` 返回的 `perms: string[]` 是界面**显示与否**的依据，名字不定就会在按钮上写错。

**建议**：以 RBAC 文档为准，把 21.2 全表统一成 `topic.*` / `reply.*`，并补两条现在只有一半的：
`reply.create`（§21.2 用的是 `post.create` 管回复）、`topic.edit.own`（§21.2 写作 `post.update_own`）。

### 1.2 【已确认】四个权限点被用了但没进常量表（启动自检必红）

§21.2 的端点表里出现了 `post.review`、`report.handle`、`title.manage`、`board.moderate`，
而 §9.8 的权限点常量表里**一个都没有**；`RBAC权限树设计.md` §6 第 6 条要求「`permissions.key` 集合 == 代码常量集合」。
按现状写迁移，这条自检第一次跑就会红。需要：常量表补这 4 个 → 迁移插 `permissions` 行 → 按角色矩阵写穿。

### 1.3 【已确认】`user_roles`（多角色并集）与 RBAC 的「单一基线角色」矛盾

| 出处 | 说的是 |
|---|---|
| `数据库设计-postgresql.md` §4.1 | 角色关系走 `user_roles`，**一人多角色、授权取并集** |
| `RBAC权限树设计.md` §1 / §2 | 一人**只有一个基线角色**（`users.role_id`），追加权限走 `user_permissions`，**角色之间永不并集** |
| `论坛后端技术方案-v2.md` §21.2 | `POST/DELETE /api/v1/admin/users/{id}/roles`（复数语义 = 多角色） |

W5 按 RBAC 文档实现（单一基线 + 点对点追加，界面上是「改角色」而不是「加角色」）。
**必须二选一**，因为它决定 `users.role_id` 还是 `user_roles` 表——迁移写下去就改不动了。建议以 RBAC 文档为准：
`PATCH /api/v1/admin/users/{id}/role { role_id }`，并把数据库文档 §4.1 与 §21.2 的复数端点一并改掉。

### 1.4 【待拍板】内置角色名单：`moderator` 到底在不在

§9.8 的角色里有 `moderator`，`RBAC权限树设计.md` §3 的四个内置角色（user / creator / admin / superadmin）里没有。
W5 把 moderator 做成**可删的自定义角色**（`is_system=false`）。若它应是内置角色，需要补第 5 行权限矩阵并说明与 `board.moderate` 的关系。

### 1.5 【已确认】数据库文档的两处缺漏

1. **没有 `reports` 表**：§21.2 已有 `POST /api/v1/reports` 与 `GET/PATCH /api/v1/admin/reports`，但表设计里找不到它（功能清单 A7 也只说「方案零提及」）。至少要：
   `reports(id, public_id, target_type, target_id, reason, detail, reporter_id, state, handler_id, handled_at, handle_note, created_at)` + 索引 `(state, created_at DESC)`，并考虑「同一人对同一对象重复举报」的约束。
2. **`topics` 缺 `created_at`**：同节的索引 `idx_topics_author (author_id, created_at DESC)` 与 §21.3 的响应示例都在用它，列清单里却没有。

### 1.6 【待拍板】D6 的判定顺序是旧站「一人多组」的残留

§20.4 D6 写的是「**任一**角色命中 deny → 拒绝」。那是旧站用户组模型的说法；
在「一人一个基线角色」下，这句话没有意义（只有一行）——应改为「**该用户基线角色那一行**命中 deny → 拒绝」。
W5 在分区管理屏上按新口径实现并把这个疑问写在界面上，等这里拍板后要同步改 D6 正文。

## 2. 帖子详情页（W2）

### 2.1 【待拍板】Issue 未关闭计数（W2 与 W3 各自独立提出，口径一致）

- 需求：帖子页顶部「帖子内容 / Issue」两个大按钮里，Issue 按钮要显示**未关闭**条数（仿 GitHub 仓库页）。
- 现状：`GET /api/v1/topics/{id}/issues` 只有游标分页，没有计数；`topic` 详情响应里也没有 issue 统计。
- 建议：`GET /api/v1/topics/{id}` 的响应加 `issue_open_count: int`（一次查询顺带，不新增端点，列表页也不用为此多发一个请求）。
  为什么不做成独立计数端点：详情页已经要拉 topic，再发一次请求会撞上前端方案 §9.1「首屏请求数 ≤ 10」的口径。
- 权限点：无（游客可读）。

### 2.2 【待拍板】资源帖的「下载来源」：字段形状 + 转链端点

- 需求：资源帖正文下方要展示下载来源列表（网盘 / GitHub + 提取码 + 转链按钮 + 维护状态）。
- 现状：`GET /api/v1/topics/{id}` 说「详情含 sources[]」，但**没有任何字段形状**；
  §20.2 第 4 条定的表是 `TopicSource(topic_id, label, url, code, sort)` + `Topic.resource_status`。
- 建议（W2 按界面逐项反推的最小集）：

      sources: [{
        id: string,
        provider: 'netdisk' | 'github',   // 决定用哪个图标与文案
        label: string,                    // 「第三章整合包（含 18 张地图 + 完整语音）」
        extraction_code: string | null,   // 网盘提取码；GitHub 源为 null
        size_text: string,                // 展示用「2.4 GB」，后端格式化，前端不做单位换算
        verified_at: RFC3339,
        upkeep: 'active' | 'archived'     // 维护状态：仍跟进 / 已归档
      }]

  `upkeep` 必须是独立字段：它回答「还有没有人维护」，**不能从 `verified_at` 推断**（链接昨天验过、作者已弃坑，是常见组合）。
- **转链端点**：`GET /api/v1/topics/{topicId}/sources/{sourceId}/go` → 302，计数进 counter（第 11 章的口径）。
  §21.2 现在只有 `GET /api/v1/launcher/assets/{id}/go`，资源帖用不了。
  为什么必须走后端转链而不是前端直链：网盘直链会失效、会被爬，且失效后需要一个统一的地方改。
- 权限点：无（游客可点）；但**要限流**，否则它就是一个免费的跳板。写路径 `topic.edit.own`。

### 2.3 【已确认】主题详情补 `updated_at` 与 `viewer`

- `updated_at`：页面要显示「最后编辑 今天 11:04」，§21.2 的详情只列了 `created_at` / `last_reply_at`。
- `viewer: { liked, bookmarked }`：点赞/收藏的**初始态**靠它；§21.3 的列表例子里有 `viewer`，详情段没写明。
  没有它，详情页只能先渲染「未点赞」，等用户点了才发现是已点赞——这是「刷新后状态不对」那类缺陷的来源。
- 权限点：无。

### 2.4 【待拍板】评论的赞踩：契约的「单值投票」与界面的「两个计数」对不上

| 侧 | 现状 |
|---|---|
| 契约 §21.2 | `PUT /api/v1/posts/{id}/vote`，body `{ value: 1 | -1 }` —— 一个用户一个值，语义是**净投票** |
| 界面 `@/ui/comment` 的 `CommentData` | `likes` / `dislikes` / `liked` / `disliked` —— **赞数与踩数各一个** |

这两个不能同时成立：只给 `value`，前端算不出「12 赞 3 踩」。二选一（Lead 建议第 ① 条）：

1. **（建议）** 保留 `likes` 表按 `value` 分别计数，但响应改成三个字段：`like_count: int`、`dislike_count: int`、`my_vote: -1 | 0 | 1`。
   写接口 `PUT /api/v1/posts/{id}/vote` 的 body 不变（幂等，同值重提不改计数）。选它的理由：`@/ui/comment` 是**已经验证过并登记过的控件**，改契约只动 dto.go；改控件要动 4 个文件 + 重出图。
2. 契约不动，界面改成显示「净分」。代价：赞踩分开是社区里公认的表达，改成净分等于少一个信息维度。

- 同一处还有 issue 评论：`PUT /api/v1/issue-comments/{id}/vote` 应当与回复用同一套字段（§20.2 第 27 条已要求「投票复用 likes」）。
- 权限点：无（登录即可投）。

### 2.5 【已确认】发帖者卡片要的等级 / 经验 / 统计字段

`GET /api/v1/users/{handle}`（§21.2 只说「资料 + 统计 + 最近主题 + 头衔」）需要显式给出：

      level: int, exp: int, exp_max: int,        // 等级与「本级已得 / 升下一级所需」
      topic_count: int, like_received: int, joined_at: RFC3339

- `exp_max` 必须由后端给：不变量是 `level = ⌊√(exp/100)⌋ + 1`，把这个公式抄到前端就是第二份实现（前端方案 §13.2 禁止第 3 条）。
- 权限点：无。

### 2.6 【待确认】`reply_count` 是否含楼中楼

- 界面头部「评论 128」直接显示 `topic.reply_count`。含楼中楼与不含楼中楼是两个数，显示哪个由这个口径决定。
- 建议：`reply_count` **含**楼中楼（用户眼里的「评论数」就是全部回复），另给 `top_level_count` 用于「N 条回复 / 展开 M 条」。
- 权限点：无。

## 3. Issue 页（W3）

### 3.1 【待拍板】Issue 列表的检索与筛选参数

- 需求：仿 GitHub 的列表页要支持「关键字 + 状态 + 类型 + 作者 + 标签」组合筛选，还有排序（最新 / 评论最多 / 最早）。
- 现状：§21.2 只有 `GET /api/v1/topics/{id}/issues?status=open|closed`。
- 建议：扩成 `?q=&status=&kind=&author=&label=&sort=&limit=&cursor=`：
  - `q`：标题 + 正文，复用 PG 侧的检索能力（中文两字词要能命中，M8 验收项）；
  - `kind`：`bug|feature|difficulty|other`；
  - `author`：handle；
  - `label`：GitHub 式标签（**当前数据模型里没有 issue 标签表**，若要做需要新表 `issue_labels` + `issue_label_links`，这条优先级最低，可以整块后置）；
  - `sort`：`new|old|comments`。
- 权限点：无（游客可读）。

### 3.1.1 【待拍板】需要一个跨主题的聚合列表端点

W3 做的是**全站 Issue 视图**（GitHub 的 Issues 页），而现有 `GET /api/v1/topics/{id}/issues` 只能按单个主题取。
建议新增（读：游客可访问；发 Issue 仍 `post.create`）：

    GET /api/v1/issues?q=&status=open|closed&kind=&label=&author=&assignee=me&sort=updated|comments|created&limit=&cursor=

权限点：读无；`assignee=me` 需要登录（`me` 之外的值由后端拒绝，别让它变成别人的筛选器）。

### 3.1.2 【待拍板】Issue 的三个新字段（列表要显示与筛选）

| 字段 | 类型 | 用途 | 代价 |
|---|---|---|---|
| `labels` | `string[]` | 列表标签徽标 + 标签筛选 | 需要 `issue_labels` + 关联表（**可以后置**，四类 kind 已覆盖本社区的主要分类） |
| `assignee` | `user \| null` | 「指派给我」筛选 + 详情指派位 | `post_issues.assignee_id` 一列 |
| `comment_count` | int | 列表行尾评论数 | 与 §3.3 同一条，热路径上要么冗余列要么子查询 |

详情一屏要能渲染：`body_md` + `body_html` + `labels[]` + `assignee` + `comments[]`。

### 3.1.3 【已确认】评论排序与「我的投票」

- `GET /api/v1/issues/{id}/comments` 建议支持 `?sort=hot|latest`（界面上就是「最热 / 最新」两个按钮，现在只有本地排序）。
- 评论列表响应必须带 viewer 的 `liked` / `disliked`（与 §2.4 同一处口径）：**只有票数没有我的投票，刷新后按钮状态就是错的**。

### 3.2 【待拍板】Issue 类型的取值域

- 需求：四个醒目入口「Bug 汇报 / 功能建议 / 难度建议 / 其他」。
- 现状：§20.2 第 27 条写的是 `bug/feature/other`（三项），**没有「难度建议」**。
- 建议：枚举扩为 `bug|feature|difficulty|other`。为什么值得单独列一类：本社区是战役 mod 社区，「难度建议」是作者最需要的一类反馈，混进「其他」会丢信息。
- 影响：数据库 `post_issues.kind` 的 CHECK 约束（数据库文档 §4.11）要同步。

### 3.3 【已确认】Issue 列表项必须自带的 5 个字段（W1 实测：缺一个就要多一次请求）

`GET /api/v1/topics/{id}/issues` 在 §21.2 只写了「游标分页；?status=open|closed」，没有响应示例。
IssueCard 的全部显示输入只有这五项，缺任一项前端都得再发一次请求（撞 §9.1「首屏请求数 ≤ 10」）：

| 字段 | 类型 | 用途 |
|---|---|---|
| `status` | `open` \| `closed` | 列表左侧状态图标（open 绿 / closed 紫） |
| `comment_count` | int | 行尾评论数 |
| `created_at` / `updated_at` | RFC3339 | 行尾时间，列表按 updated_at 倒序 |
| `author` | `{handle,nickname,avatar}` | 作者头像与昵称 |

- 权限点：无（游客可读）。

### 3.4 【待拍板】Issue 需要一个「给人看的编号」

- 需求：Issue 列表与详情都要显示 `#编号`（GitHub 的 #123 那种）。
- 现状：§21.1 规定响应里的 `id` 一律是 public_id 字符串；§21.3 的主题 id 形如 `0192f0…`（UUID）。
  直接拿 id 当编号显示，界面上会变成 `#0192f0ab…`——那不是编号，是一串哈希。
- 建议：`post_issues` 加一列 `number int`（**帖内自增**，用 `(topic_id, number)` 唯一约束 + 取号时按 topic 行锁），响应里同时返回 `id`（对外标识）与 `number`（展示编号）。
- 为什么不建议只给 `display_no: string`：排序与「#100 之后」这类跳转都要按数字比较，给字符串等于把这个需求推给前端。
- 权限点：无。

### 3.4.1 【已确认】前端已按 `?kind=` 深链预设类型

帖子页正文末尾与右栏各有一组**四类反馈按钮**（在帖子页上，不只是反馈页）——
理由：绝大多数用户不知道「Issue」是什么，不能只有一个黑话入口。点哪一类就带到反馈页并预设类型。

- 前端实现：`?page=13-issue&kind=bug`（产品路由上是 `/issues?kind=bug`，走 react-router 的 searchParams）。
- 后端无需新增端点：`POST /api/v1/topics/{id}/issues` 的 `kind` 本来就在 body 里；这只是一个**查询串约定**，不产生契约。
- 需要后端确认的只有一件事：§3.2 的 `kind` 枚举要包含 `difficulty`（见该条）。

### 3.5 【待拍板】谁能关 Issue

§21.2 把 `PATCH /api/v1/issues/{id}`（关/开）写成 `post.update_own`（作者或管理员）。
GitHub 式的「关闭」在社区里通常是作者 + 版主都能按。建议：作者走 `post.update_own`，非作者走 `post.lock`（该权限点已存在，语义就是「锁定/关闭讨论」）。

## 4. 主页面（W4）

### 4.1 【已确认】主题列表要能一次给出卡片视图所需的全部字段

- 需求：方卡片（16:9 封面 + 类型徽标 + 标题 + 作者 + 计数 + 时间）与横板缩略卡片同源，一行 ≥4 张。
- 现状：§21.3 的列表项已含 `cover`、`kind`、`author`、`reply_count`、`like_count`、`view_count`、`last_reply_at`、`pinned`、`featured_at`、`viewer`。
- 缺的一项：**`excerpt`（摘要）**。§21.3 的列表项没有它，而横板缩略卡片与卡片视图都要显示摘要。
- 建议：列表项补 `excerpt: string`（后端从 content_html 截断生成，**不要**让前端拿全文再截——那会把正文拉进列表响应）。
- 权限点：无。

### 4.2 【待拍板】建议给 `cover_width` / `cover_height`

- 端点：`GET /api/v1/topics`（及详情）；类型 `number | null`。
- 为什么：§21.3 有 `cover`，但**图的实际尺寸只有后端知道**。前端拿到一张 48×48 的图标当封面就会糊成一片；
  W4 现场踩到了这个（只能靠浏览器解码后量 `naturalWidth` 兜底，多一次布局判定）。后端给宽高，首屏就能决定「用图还是用占位块」，
  顺带满足前端方案 §9.1 的 CLS 硬要求（图片必须有宽高比容器）。
- 权限点：无。

## 5. 管理后台（W5）

### 5.1 【待拍板】批量操作

- 需求：审核队列、举报队列、打赏核验队列都要「勾一批 → 一次处理」，用户管理要能批量改角色 / 批量停用。
- 现状：§21.2 的 admin 段全是单条 `PATCH /admin/xxx/{id}`。
- 建议：加 `POST /api/v1/admin/{users|reports|rewards}/batch`，body `{ ids: [], action, reason? }`，**逐条返回成功/失败**（不要一个事务全成功全失败——批量核验里一条冲突就把整批回滚，管理员会疯）。
- 权限点：沿用各自的（`user.ban` / `report.handle` / `reward.verify`）。

### 5.2 【待拍板】角色 × 权限矩阵的读写

- 需求：后台要一屏「左侧角色树 + 右侧权限点分组勾选」，改完有未保存/已保存态。
- 现状：§21.2 已有 `PATCH /api/v1/admin/roles/{id}/permissions`，但**没有权限点目录的稳定读法**——§21.2 写了 `GET /admin/permissions`，
  而 RBAC 文档 §3 的权限点比它细（含 `topic.move`、`board.moderate`、`user.mute` 等），两边对不齐。
- 建议：`GET /api/v1/admin/permissions` 返回**带分组与中文名**的完整目录：`[{ key, group, name, description }]`；
  `GET /api/v1/admin/roles` 返回树形（`id,key,name,parent_id,depth,badge_color,permissions[]`）。
- 权限点：`role.edit`（§21.2）——注意 RBAC 文档里写的是 `user.role.change`，同 §1.1，需要一并统一。

### 5.3 【待拍板】BoardACL 的读写

- 需求：分区管理屏要做「角色 × 分区」的 `can_post / can_reply / deny_post / deny_reply` 四象限矩阵，并体现**禁止优先**（D6 判定顺序）。
- 现状：§21.2 有 `PUT /api/v1/admin/boards/{id}/acl`（没有任何细节），数据库文档有 BoardACL 表设计。
- 建议：明确为 `GET /api/v1/admin/boards/{id}/acl` → `[{ role_id, can_post, can_reply, deny_post, deny_reply }]`；
  `PUT` 一次替换该分区整张矩阵（矩阵是整体语义，逐格 PATCH 会把「禁止优先」的中间态暴露给正在发帖的用户）。
- 权限点：`board.manage`。

### 5.4 【待拍板】审计日志的筛选

- 需求：审计日志屏要按 actor / action / target / 时间区间筛选并分页。
- 现状：§21.2 只有 `GET /api/v1/admin/audit-logs`。
- 建议：`?actor=&action=&target_type=&from=&to=&limit=&cursor=`。
- 权限点：`audit.view`（§21.2）/ `audit.read`（RBAC 文档）——同 §1.1。

### 5.5 【已确认】举报队列与打赏队列的分页

- 现状：§21.2 只有 `GET /api/v1/admin/reports`、`GET /api/v1/admin/rewards`，没写分页参数。
- 建议：按 §21.1 的通用约定补 `?limit=&cursor=`，否则队列一长就拉全表。
- 权限点：`report.handle` / `reward.verify`。

### 5.6 【待拍板】隐私：收款码图片的读取

- 需求：打赏核验队列里管理员要看用户的收款码图片；同时收款码**不该被所有人拿到 URL 就能看**。
- 现状：旧站这里有个真实缺陷（功能清单 §12.9：收款码图片读取 404，因为 `/img/{hash}` 只认 post_images）。新方案 §10.5 有可见性三档，
  但没写「收款码图片」归哪一档。
- 建议：收款码图片固定 `visibility = 2`（仅所有者与管理员），管理端走 `/img/{hash}` 时由后端按 `reward.verify` 放行。

### 5.7 【待拍板】帖子审核队列：端点整体缺失（对照老功能 13.3）

老站有完整的审核状态机（自动审核 / pending / approved / rejected + 待审修改 `post_revisions`），新方案 M5 只有 `normal/locked/hidden/deleted`。
要把它做回来，至少需要：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/topics?state=pending\|rejected\|normal&board=&limit=&cursor=` | 队列列表，游标分页 |
| POST | `/api/v1/admin/topics/{id}/review` | body `{ action: 'approve'\|'reject'\|'request_revision', note }`，`note` 必填 |

- **「请求修改」需要有落点**：`topics.review_note`（或恢复 `post_revisions` 表）+ 通知作者。现在 DB 里没有这个字段。
- 权限点：**`post.review`**（见 §1.2，常量表里没有）。
- 审核豁免（老站「管理员及以上跳过审核」「trusted 分区」）要不要保，是产品问题——界面上按「免审作者 / 普通作者」两种作者标签做了预留。

### 5.8 【待拍板】用户管理的筛选与新端点

- `GET /api/v1/admin/users` 需要：`?q=`（登录名/昵称/邮箱）、`?status=`、`?activated=0|1`、`?email_verified=0|1`、`?role=key`、`?limit=&cursor=`；
  返回三根状态轴（封禁 / 邮箱验证 / 激活）+ `role` + `extra_permissions`。为什么：界面上是三个独立筛选器，任何一个缺失都要前端拉全量再过滤。
- **缺 `GET /api/v1/admin/users/{id}`**（§21.2 只有 PATCH）：详情要含 `sanctions[]`、`user_permissions[]`（带 reason / expires_at）、`user_titles[]`、最近审计。
- 封号接口应返回**被踢掉的会话数**（否则界面只能说「已封禁」，管理员不知道要不要再去清会话）。

### 5.9 【待拍板】点对点追加权限：完全没有端点（RBAC 的核心能力）

RBAC 文档 §1/§2 把「点对点追加权限」当成与基线角色并列的两条路之一，表也建了（`user_permissions`，每行必须有 `reason`），
但 §21.2 的 admin 段**一个端点都没有**。需要：

    POST   /api/v1/admin/users/{id}/permissions/{perm_key}   body { reason（必填）, expires_at（建议必填） }
    DELETE /api/v1/admin/users/{id}/permissions/{perm_key}

- 权限点：`role.edit`（§21.2）/ `user.role.change`（RBAC 文档）——同 §1.1 的命名统一。
- **写成功后必须主动失效该用户的 60 秒权限缓存**（RBAC §4），否则「给了权限但 60 秒内不生效」会被当成 bug 报上来。

### 5.10 【待拍板】分区管理的写操作

- `GET /api/v1/admin/boards/{id}/acl`：§21.2 只有 PUT，**读不回来**，矩阵页面打不开。
- `PUT` 的 body 定为 `{ acls: [{ role_id, can_post, can_reply, deny_post, deny_reply }] }`（**全量替换**）：
  矩阵是整体语义，逐格 PATCH 会把「禁止优先」的中间态暴露给正在发帖的用户。
- 排序：`POST /api/v1/admin/boards/reorder { ids[] }`——现在只能逐个 PATCH，拖一次排序打出 N 个请求。
- 版主任免：`GET/POST/DELETE /api/v1/admin/boards/{id}/moderators`（带 `expires_at`，写审计）。
- 分区封面：`POST /api/v1/admin/boards/{id}/cover`（走图片通道，≤512KB）。

### 5.11 【待拍板】站点设置与公告

- `PATCH /api/v1/admin/site-settings` 的 body 定为 `{ values: { key: value } }`，**未知 key 必须 400**（静默写入等于让文案表烂掉）。
- 公告与横幅：§21.2 只有 POST 创建，缺列表与下线（`GET /api/v1/admin/announcements`、`PATCH /api/v1/admin/banners/{id} { enabled }`）。
- 域名表要只读端点 `GET /api/v1/admin/site-domains`（写入另说：改主域名牵动 Cookie 与 CSRF，不能顺手做）。

### 5.12 【待拍板】审计日志导出

`GET /api/v1/admin/audit-logs/export?format=csv`（§21.2 无）。权限点建议单列 `audit.export`；
若嫌多，退一步要求 `system.settings`，但**不能默认开放**——审计日志是能一次导走全站操作痕迹的东西。
`action` 的中文标签建议后端给（或前端常量表收敛一次），`detail` 建议返回结构化 before/after，否则界面只能把 JSON 原样摊开。

### 5.13 【已确认】自检面板要能被门控住

`GET /api/v1/admin/diagnostics` 在 debug 开关关闭时，应当返回**明确的错误码**（如 `common.not_found`）而不是空 200。
空 200 会让「生产上关掉了」和「跑了但没结果」这两件事在界面上长得一样。

| 位置 | 事实 |

- `prompt`（新建帖）：与 d7 §4 的内置默认同源 —— 判「能不能公开发布」，四类拒绝、
