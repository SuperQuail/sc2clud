## 3. 密码哈希格式

- 算法：**Argon2id**，库 `argon2 = "0.5"`（`crates/sc2clud-core/Cargo.toml:10`）。
- 参数：`Argon2::default()` —— 注释写死 **m=19 MiB / t=2 / p=1**（`core/src/auth.rs:172-179`）。
- 哈希：生成时随机 salt（`SaltString::generate(&mut OsRng)`），落库是标准 **PHC 字符串**
  `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`（`to_string()`）；测试断言前缀 `$argon2`
  （`auth.rs:439`）。salt 与参数都在串内，无额外列。
- 校验：`PasswordHash::new(stored)` → `verify_password`；解析失败一律返回 false
  （不 panic、不区分「密码错」与「串损坏」）（`auth.rs:182-189`）。
- 迁移判断：**PHC 串自描述，任何标准 Argon2 实现都能原样校验，不需要重算**
  （重算需要明文密码，服务端没有）。
- 特殊值：占位哈希 `"!"` 表示「不可密码登录」，由 `ensure_super_admin` /
  `ensure_bootstrap_user` 写入（`repo.rs:105,137`）；`PasswordHash::new("!") ` 解析失败 → 永远验不过。
- 明文口令约束：8..=128 字节且不能全空白（`auth.rs:265-273`）。
- 会话令牌不是密码：32 字节随机 hex 发 Cookie，库里只存 **blake3 hex 摘要**（`sessions.id`）；
  CSRF 是 16 字节随机 hex（`auth.rs:280-294`）。

## 4. 角色与权限来源

- 4 级角色**存在 `users.role` 一列**（TEXT），取值 `member | developer | admin | super`
  （`core/src/auth.rs:29-36`；枚举 `Role` 顺序即优先级 `Member < Developer < Admin < Super`）。
- `Role::parse` 对未知值**直接报错**，不静默降级成 member（`auth.rs:48-56`）。
- 「未激活」不是角色，是独立的第二轴：`activated_at IS NULL`（`auth.rs:9-10`）。
- 权限位是**代码常量**，不是数据：`Permission` 枚举 + `min_role()` 映射表（`auth.rs:61-133`），
  唯一判定入口 `allows(role, activated, permission)`（`auth.rs:139-152`）。
  共 15 个权限位（`ViewContent` 游客可读；`ManageDomains/PublishBanner/PostAnnouncement/ManageRoles` 仅 super）。
- 相关数据侧门槛另存表：`sections.post_min_role / reply_min_role / group_check`
  （`group_check` 由代码映射成 `group_mode` 0/1/2，`repo.rs:2998`）。
- 角色分工（强制在代码里）：`docs/PERMISSIONS.md` 是文档基准，改权限要同时改
  `core::auth::min_role()`、`permission_tests` 与文档（`site/AGENTS.md` §6.5）。

## 5. 迁移时必须保住的语义（每条一句）

1. `handle` 全站唯一且不可改（登录标识，注册时校验占用 `pages_auth.rs:187`）。
2. `display_name` 非空、≤20 字符、**允许重复**，与 handle 是两回事（0004 的列注释 + `auth.rs:245-262`）。
3. 激活状态 = `activated_at IS NOT NULL`；未激活能登录但不能发帖/回复/上传/换头像（`auth.rs:139-152`）。
4. 角色 4 值 + 严格解析：非法角色必须报错，不能当 member（`auth.rs:48-56`）。
5. `trusted = 1` 时发帖只走自动审核、不进人工队列（0011 注释）。
6. 头像三件套 `avatar_hash / avatar_mime / avatar_small` 一起用：mime 决定 Content-Type，
   small 为空回落原图（0006/0025 注释）。
7. `default_avatar_hash` 是「随机分一次就固定」，不能每次刷新重算（0022 注释）。
8. `bio` 有 200 字上限并带审核态三列（`bio / bio_review_state / bio_review_note`，0019 注释）。
9. `quota_bytes` 是显式分配的额度（0007 把存量全部归零：不能有历史遗留默认量），
   `used_bytes` 是实际占用，两者都在管理页可改（`repo.rs:2257,2271`）。
10. 打赏两个开关语义不同，必须分开：`donation_visible`（展示我的收款码）≠
    `donation_records_public`（公开我的打赏记录）（0032:62-64 明确写了「复用会导致互相牵连」）。
11. `donation_notice_visible` 默认 1、`donation_notice_text` 空 = 用渠道默认（0018 注释）。
12. 头衔是「多对多 + 佩戴一个」：`user_titles` 存持有关系，`users.equipped_title_id` 存佩戴；
    注销头衔时 `equipped_title_id` 要清（`repo_titles.rs:128`）。
13. 处罚优先于角色门槛：`user_sanctions.deny` 与 `group_section_rules.deny_*` 都是「禁止优先」（0015 注释）。
14. `section` 空串 = 全局处罚，否则是分区 key（0028:11）。
15. 经验与等级：`exp` 是累计值，`level` 由 `level_for_exp`（`⌊√(exp/100)⌋+1`）反算，两者必须一致（`community.rs:94-109`）。
16. 时间一律 Unix 秒 INTEGER，不引入日期类型（0001 约定 + `models.rs:3`）。
17. 邮箱唯一但**可空**（`email TEXT UNIQUE`），注册时按小写比对（`validate_email` 返回 `to_ascii_lowercase()`）。
18. 停用/封禁的用户仍然在库：全仓库**没有 `DELETE FROM users`**，内容删除靠 `ON DELETE CASCADE` 才生效。

## 6. 不建议继承的列（含理由）

| 列 | 理由（事实） |
|---|---|
| `disabled_at` | 读侧有 4 处 `disabled_at IS NULL` 过滤，但**全仓库没有任何写入路径**——实际上永远是 NULL，「停用」是走 `activated_at = NULL`（`admin_users.rs:185,427`）。只加不删留下的死列 |
| `post_ban_until` | 0028 已把数据迁进 `user_sanctions`（全局 `kind='post'`），列本身仍在；旧的「全局禁发帖」已被「按分区 + 禁发帖/禁评论」取代，两处状态会漂移 |
| `used_bytes` | 只有 `+/- n` 两处增减，**没有配额闸门**（无 `used_bytes >= quota_bytes` 判定），也与内容寻址去重后的真实盘占用不是一回事 |
| `bio_review_note` / `bio_updated_at` | 写了但从没被读过/展示过（`bio_review_state` 也一样，写入即 `approved`）——审核机尚未接上简介 |
| `activated_by` | 只有写入，**没有任何读取/展示**；且无 FK，「谁激活的」在审计表里另有一份（`user.activate` 类 action） |
| `level` | 完全由 `exp` 推导的冗余列（`community.rs:97`）；只在 `award_exp` 里跟 `exp` 一起 UPDATE |
| `avatar_mime` | 与 `blobs` 的元信息重复；`avatar_hash` 指向的 blob 本来就带 mime（0006 注释说明了为什么当年冗余存一份） |
| `quota_bytes` 的默认值 | 0001 的默认 1 GiB 已被 0007 的 `UPDATE users SET quota_bytes = 0` 作废；建表默认值与实际语义（0 = 不分配）不一致 |

## 7. 数据规模线索

- 代码里**没有硬编码的用户数量级**。相关的只有：
  - `repo::count_users()`（`repo.rs:2889`）—— 计数器，供管理页与 debug 页展示（`pages_admin.rs:89`、`pages_debug.rs:49`）。
  - 用户数据导出写死上限 **10 000 行**：`admin_list_users(pool, "", 10_000)`（`pages_social.rs:356`）。
  - 用户搜索每次最多 50 条（`repo.rs:4202`，`limit.clamp(1, 50)`）。
  - 测试断言里的数字是测试数据：`lib.rs:539` 断言 2 个用户（非真实规模）。
- 迁移注释里的量级描述：0007「存量账号一律归零」、0028「老数据搬进来」、0036「任何部署上这里都是 0 行」——
  都只说「存量」存在，**没给数字**。
- 部署文档里的机器规格是唯一间接线索：单机 2 vCPU / 2 GB（`site/AGENTS.md` §2、`docs/BUDGETS.md`）。
- 结论：**无法确认**实际用户数。仓库内没有数据库文件（`site/**/*.sqlite*` 为空），
  数据在服务器 `/srv/sc2clud/data`；若需准数，只能查生产库或 `repo::count_users()`。
