## 1. 一句话结论

**设计的方向站得住，但"文档改了、别处没跟着改"这一类问题占了 blocker 的一大半**——这正是旧站根因 2（同一概念多份实现）在**文档层**的复发。盲审最有价值的不是挑出几个设计缺陷，而是证明：**只要没有机器检查，多份文档必然漂移**。

## 3. 其余 blocker 的裁定

| ID | 出处 | 裁定 | 修法 | 归属 |
|---|---|---|---|---|
| B1（接口）**Principal 60s 缓存 vs 封号立即生效** | 接口 | **接受**。这是真缺陷：缓存命中路径没有 JOIN，status 无从校验；且缓存键是 token 摘要、失效键是 userID，删 session 不失效 | Principal 缓存条目**必须带 status**，或把 status 校验改成"每请求一次极轻查询"；封号时按 userID 清缓存（维护二级索引） | S1 |
| B4（接口）**游标分页无规格** | 接口 | **接受**。cursor 装什么、编码、并列、hot、到底判定全空 | 定稿：cursor = base64url({k, id})，**排序键永远带 id 兜底**；**v1 砍掉 sort=hot**（它需要物化分数列才稳定，现在没有） | S1 |
| M4（接口）**幂等只有声明** | 接口 | **接受**。client_token 无列无字段、核验无 CAS、点赞并发给 409 | client_token 加列 + 唯一索引；核验用条件更新（CAS）；点赞并发返回 200 而不是 409 | S1/S3 |
| M5（接口）**队列 unique_key 语义未定义** | 接口 | **接受**。unique_key 冲突会让 EnqueueTx 回滚业务事务；租约无续租；两份文档领取 SQL 不同 | 定稿：unique_key 冲突 = **静默跳过**（ON CONFLICT DO NOTHING），绝不让它回滚业务事务；租约续租；领取 SQL 只保留数据库文档那一份 | S1 |
| M6（接口）**队列/cron/CLI 没有主体** | 接口 | **接受** | 定义系统主体（SystemActor），危险写操作在 service 层用它显式声明"这是系统调用" | S1 |
| B3（建模）**私信未读语义错 + 缺索引** | 建模 | **接受**。read_at 是收件人侧，按一侧建索引会让自己的消息进自己未读角标 | 未读用 `sender_id <> 我 AND read_at IS NULL` 的**部分索引**；补 `(high_id, low_id, id DESC)` | S1 |
| D2（运行）**搜索结果越权** | 运行 | **接受**（安全）。topic_search 无 status 列，pending/hidden/deleted 可被游客搜到 | 查询时 JOIN topics 过滤 status；**不给 topic_search 加 status 冗余列**（冗余列就是漂移源） | S7 |
| D4（运行）**内存总账不成立** | 运行 | **接受**（部分）。gse 80MB 被实测推翻（仅 Tokens 切片 49MiB）、漏 autovacuum_work_mem、无 cgroup | 重算总账写回 §9.6；**dev 与 prod 不得同机**（写进部署文档）；gse 词典大小实测后再定 | S0 |
| F01（前端）**运行期 base 未实现** | 前端 | **接受，但改决策**：路径前缀要在 4 处做运行期 plumbing（router basename / api 前缀 / 资源 URL / cookie 名），老站的头号 bug 类就是它 | **dev 改子域**（`dev.example.com`）：前缀问题、sub_filter、双 cookie 名**一次性全部消失**。一次构建、一个制品、两份部署 | S8 |
| F03（前端）**双控件基座已分裂** | 前端 | **接受**。产品里 Ring UI 只用了 1 处，文档两处结论相反 | 见 §5 待拍板 | S1 起 |
| B2（接口）**§8.1/§8.7 缺节** | 接口 | **接受**。凭据加密 AAD/轮换无规格却被 4-5 处引用 | 补回 §8.1 接口与 §8.7 加密规格（含 AAD 绑 name、轮换流程） | S7 |

## 5. 需要你拍板的（两件）

1. **dev 的形态**：路径前缀（`/dev/`，同域，需要一个运行期 base 机制）还是**子域**（`dev.example.com`，零 plumbing）。
   我的建议：**子域**。它一次性消掉前缀、sub_filter、双 cookie 名三样东西；代价是 dev 需要一个（可以自签或用同一张证书的）域名解析。
2. **双控件基座到底谁为主**：你说过"Ring UI 作为核心，都保留"，但现状是产品里 Ring UI 只用了 1 处、其余全是 shadcn。
   我的建议：**按控件类型分配并写死一张表**（Button/Input/Select/Popup/Table/Tabs/Tooltip/Avatar 用 Ring UI；Field/Label 这类 Ring UI 没有的用自建），再加一条**机检**：同一控件类型从两个来源 import 即 lint 失败。不做机检的话，这条规矩活不过两周。

## 7. 复查机制（防止再犯）

盲审证明了一件事：**多份文档必然漂移，除非有机器检查**。所以新增两条硬要求（进施工计划 DoD）：

1. **跨文档一致性检查脚本**：扫四份文档 + 代码，断言：§21 端点里出现的表名/列名在 DB 文档里都存在；权限点常量在 §9.8 与实现里都存在；任务类型常量在 §7.4 与实现里都存在；表数与清单一致。
2. **每条"必须"都要有落点**：施工计划 DoD 加一条——**新增或修改的规则，必须同时给出检查它的命令或脚本**；给不出就说明这条规则不该写进文档。
