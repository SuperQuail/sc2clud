## 根因 1｜业务事务在请求层「就地拼」，没有领域边界

| 栏 | 内容 |
|---|---|
| 旧站的病 | 写操作由 handler 顺序 `await` 若干仓储函数拼成，中途失败留下半成品；改一个流程要通读整个 handler。 |
| 新设计的堵法 | ① 事务唯一入口 `forum/internal/platform/db/tx.go` 的 `WithTx`（panic/error 都回滚，明确**不支持嵌套**）；② 逻辑在 `internal/<域>/service.go`，HTTP 层只有 bind→调 service→响应：`forum/internal/forum/handler.go:228` 的 `createTopic` 只有 20 余行，`handler.go` 全是这种薄壳；③ 审计与业务**同事务**：`forum/internal/auth/audit.go:53` 的 `writeAudit(ctx, tx *ent.Tx, e AuditEntry)` 签名上就要求传事务；④ 队列同事务：`forum/internal/forum/service.go:133` 用 `EnqueueTx`；⑤ 编译期断言 `forum/internal/app/ent_tx_assert_test.go`（`*ent.Tx` 实现 `queue.TxExecutor`）。 |
| **会红吗** | **① 有检查且能红**：`cd forum && go test ./internal/forum/... ./internal/auth/... ./internal/media/...`，红的样子是 `service_test.go:115`「事务回滚：事务内的第二次写入失败时，第一次写入必须一起消失」失败、`auth/account_test.go:136`「事务回滚：一个用户都不该留下」失败。**但**：没有任何检查禁止「handler 里编排两次写」——`完全重构/盲审-后端与接口.md:178` 点名的 depguard/导入边界 lint 至今没有载体（仓库里没有 `.golangci.yml`）。 |
| 结论 | **部分**。原子性已由「唯一事务入口 + 具体用例的回滚断言」守住；代价是**结构约束靠人**：新写一个 handler 时顺序调两个写仓储，没有任何东西会红。 |

## 根因 3｜列表在循环里逐行查库（N+1），把延迟和一致性风险一起放大

| 栏 | 内容 |
|---|---|
| 旧站的病 | 一个页面要几十到几百次串行查询；页面各区块互相看不见对方的数据版本。 |
| 新设计的堵法 | ① 读路径是专用 SQL、一次 JOIN 出完整视图：`forum/internal/forum/pgsql/topics.go:57`、`posts.go:76/107/269`、`issues.go:50/294` 都是 `JOIN users`；`internal/forum/dto.go:8` 注明「列表查询里 JOIN users 直接取，没有 N+1」；② 索引可用性闸门（EXPLAIN）：`internal/notify/pgsql/pgsql_test.go:103`（`idx_notifications_inbox`，断言不出 `Seq Scan on notifications`）、`internal/message/pgsql/pgsql_test.go:100`（会话两侧各走一条 pair 索引）。 |
| **会红吗** | **② 只有文档约定**——验收线要的那条**不存在**。全库 grep「每请求查询条数 / queryCount / 计数器」**只命中文档**（`施工计划.md:71` S3 验收写「列表页 ≤ 5 条（用日志数）」，`原项目失败复盘.md:42/161`）。代码侧最接近的东西是 `forum/internal/forum/pgsql/query.go:13` 的 `var debugSQLs = true`（注释「收尾前删掉」）——它把每条 SQL 打到 stdout，**不是计数器、也不是断言**，而且它在产品路径上。上面那三条 EXPLAIN 断言来自 d4 §8.1/§8.2（索引用没用上），**测不出「渲染/组装循环里发查询」**。 |
| 结论 | **部分**。查询形状确实换掉了（JOIN 读模型），但复盘与验收线共同要求的那把尺子（每请求查询条数上限并度量）**一毫米都没有**；「渲染循环内查询」这条反模式没有任何检查兜。 |

| 栏 | 内容 |
|---|---|
