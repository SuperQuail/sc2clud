> 审计对象：`forum/migrations/postgres/*.sql`（17 份 up + 17 份 down）与 `forum/internal/ent/schema/*.go`（46 个 ent 实体）。
> 审计时间：2026-10-13。审计方式：**静态逐行读 + 真库验证**，两者都做。
> **本报告不改任何代码或迁移**，只列结论与建议。

> 真库验证环境（本机无 PG、无 Docker，与数据库设计文档 §9 的结论一致）：

> - 探针三 `forum/internal/ent/zz_probe_migrated_readwrite_test.go`（进程内 in-package 测试，跑完自动删除；**该文件已被并行提交 224d410 收进 HEAD，审计结束后已 `git checkout` 还原，工作区无残留**）：在"真跑过迁移"的库上让 46 个实体各走一遍真实读路径与写路径，并把 24 条业务原生 SQL **逐字**送 `Prepare` 做真解析。

## 0. 一句话总结

**迁移本身是健康的**（47 张表全部建成、外键索引 0 缺失、无 serial/无时区类型/无原生 enum、部分索引谓词全部合法、down 能干净回滚）；**问题全部在"迁移与 ent/Go 两侧不一致"上**，而这些不一致只在读路径或特定 SQL 上暴露——正是"两边不一致但不报错"这一类。

上线前必须处理的 3 条：

| 排序 | 缺陷 | 后果 |
|---|---|---|
| 1 | `jobs.locked_by` 列不存在 | **整个异步队列永远领不到任务**（发信、搜索索引、图片 GC、通知全部不执行） |
| 2 | `BoardACL` 实体表名是 `board_ac_ls` | 该实体的一切读写都是 42P01 |
| 3 | `ProfileSQL` 用 `p.status`（posts 只有 `visibility`） | **每个个人主页 500** |

## 1. 缺陷清单

### D1｜`jobs.locked_by`：worker 的 5 条 SQL 全引用了一个迁移里不存在的列

- **严重度：挡住上线**（后台任务 100% 不执行，且不报错到用户可见处）。
- **在哪**：
  - `forum/internal/platform/queue/pgqueue/worker.go:23,40,51,54,58,59,63`（`claimSQL` / `doneSQL` / `retrySQL` / `deadSQL` / `recoverSQL`）
  - `forum/migrations/postgres/0015_queue.up.sql:6-26` —— `CREATE TABLE jobs` **没有 locked_by 列**；该文件只在文件头注释里出现"locked_by"这个词（`-- 与数据库文档 §4.10 的差异以 d1 §6.1 为准：locked_by / finished_at 不在……不建`）
  - `forum/internal/ent/schema/job.go:19` 同样写明"没有 locked_by"
- **现象**：进程起得来、日志正常、HTTP 正常；`jobs` 表里 pending 任务越堆越多，`max_retry` 永远不推进；`q.step()` 每次返回 error，`slot()` 里只 `q.log.Error("queue: 领取失败")` 后 break，然后等下一个 tick 再失败一次。没有任何一层把它升级成"进程该退"。
- **根因**：worker 的 5 条 SQL 与 0015 迁移各自演进，**没有任何东西把"业务 SQL 里的列名"与"迁移建出的列"对起来**。队列测试用的是一份**手写的 jobs DDL**（`queue_test.go:30-54`），而那份 DDL **有 locked_by**；唯一的"防漂移"守卫 `TestMigrationFileMatchesTestDDL`（`queue_test.go:426-437`）只断言迁移文本里**含 4 个字面子串**（`uq_jobs_unique_key` / `idx_jobs_claim` / `ck_jobs_lease` / `payload jsonb`），**没断言 locked_by**，于是"两份 DDL 漂移"的守卫恰好漏掉了唯一真的漂移了的列。
- **复现**（已跑，真库）：

  ```sql
  -- 空库按序跑 forum/migrations/postgres/*.up.sql（17/17 ok，public 表 47 张），然后：
  PREPARE probe_worker_claimSQL AS <worker.go:19-34 的 claimSQL 原文>;
  -- ERROR:  关系 "jobs" 的 "locked_by" 字段不存在  (SQLSTATE 42703)
  ```

  真库输出的 6 条失败（其余 18 条业务 SQL 全部 `SQL_OK`）：
  ```
  SQL_FAIL worker.claimSQL    错误: 关系 "jobs" 的 "locked_by" 字段不存在 (SQLSTATE 42703)
  SQL_FAIL worker.doneSQL     错误: 字段 "locked_by" 不存在 (SQLSTATE 42703)
  SQL_FAIL worker.retrySQL    错误: 字段 "locked_by" 不存在 (SQLSTATE 42703)
  SQL_FAIL worker.deadSQL     错误: 字段 "locked_by" 不存在 (SQLSTATE 42703)
  SQL_FAIL worker.recoverSQL  错误: 关系 "jobs" 的 "locked_by" 字段不存在 (SQLSTATE 42703)
  SQL_FAIL user.ProfileSQL    错误: 字段 p.status 不存在 (SQLSTATE 42703)   -- 见 D3
  ```
- **建议堵法**：
  1. **二选一落定**：要么 `ALTER TABLE jobs ADD COLUMN locked_by text NOT NULL DEFAULT ''`（0018），要么把 worker 的 5 条 SQL 里的 `locked_by` 去掉（用 `locked_until` + `id` 做租约即可，`locked_by` 只用于排查）。**当前状态是两边都没做**。
  2. **把那种守卫换成机器可验证的**：删掉 `TestMigrationFileMatchesTestDDL` 的 substring 白名单，改成"把仓库里所有原生 SQL 常量在真库上 `PREPARE` 一遍"——本次探针三的 `TestZZProbeBusinessSQL` 就是可复用的形状（24 条 SQL，6 条会红）。
  3. 在 CI 里对 `jobs` 表跑一次 `q.step()`（当前 `queue_test.go` 用的是手写 DDL，**必须改成读 0015 迁移文件建表**，否则这条永远抓不到）。

### D2｜`BoardACL` 实体的表名是 `board_ac_ls`

- **严重度：挡住上线**（该实体所有读写 42P01；目前生产读路径走原生 SQL 所以没爆，但这是个定时炸弹）。
- **在哪**：`forum/internal/ent/schema/board_acl.go:20-24`（`type BoardACL struct{ ent.Schema }`，**没有 `entsql.Annotations(entsql.Table("board_acls"))`**）；证据在生成代码 `forum/internal/ent/boardacl/boardacl.go:37` 的 `Table = "board_ac_ls"` 与 `forum/internal/ent/migrate/schema.go` 的 `board_ac_ls` 表块。
- **现象**：`client.BoardACL.Query().All(ctx)` → `关系 "board_ac_ls" 不存在 (SQLSTATE 42P01)`。ent 的默认表名是 Go 类型名的 inflect 复数，而 inflect 不认识 "ACL" 这个全大写缩写，把 `BoardACL` 拆成 `board_ac_ls`。
- **根因**：同一批 19 张"自然键降级"的表里，只有 `board_acls` 躲过了 ent 的默认命名（`topic_acls` / `user_titles` 之类都不含全大写缩写）。**没有那条闸门能红**——没有测试遍历 46 个实体的表名比对迁移，`client.Schema.Create` 反而会**新建一张错误的表**并让测试变绿。
- **复现**（已跑）：`forum/internal/ent/zz_probe_migrated_readwrite_test.go` 的读路径探针 46 条里**唯一失败的就是这条**：
  ```
  PROBE total=92 read_fail=1 write_fail=46
  READ_FAIL  BoardACL  错误: 关系 "board_ac_ls" 不存在 (SQLSTATE 42P01)
  （其余 45 个实体的读路径全部 READ_OK）
  ```
- **建议堵法**：
  1. 给 `BoardACL` 加 `func (BoardACL) Annotations() []schema.Annotation { return []schema.Annotation{entsql.Annotation{Table: "board_acls"}} }`，然后 `go generate ./internal/ent`；
  2. **加一条通不过就红的检查**：遍历 `ent/migrate.Tables` 的 `Name`，与 `information_schema.tables`（迁移跑出来的库）求差集——本次探针三的读路径循环就是它的最小版本，建议固化成 `TestEveryEntityTableExistsInMigrations`。

### D3｜`ProfileSQL` 引用 `posts.status`（posts 只有一个可见性列 `visibility`）

- **严重度：挡住上线**（`GET /users/{handle}` 必 500）。
- **在哪**：`forum/internal/user/pgsql/queries.go:35`：
  ```sql
  FROM likes l JOIN posts p ON p.id = l.target_id AND l.target_type = 'post'
   WHERE p.author_id = u.id AND p.status = 'normal'
  ```
  迁移 0004 建的是 `posts.visibility text CHECK (visibility IN ('normal','hidden','deleted'))`（`0004_forum.up.sql:130,137`），**没有 status 列**。
- **现象**：个人主页聚合查询整条失败 → handler 把它当未知错误 → 500。`like_received` 是这条 SQL 的一个 LATERAL 子查询，所以整条 ProfileSQL 一起挂。
- **根因**：`topics` 有 `visibility` + `review_state` 两根轴，`posts` 只有 `visibility` 一根（拍板 §2.2 第 3 条：楼层可见性跟随主题），**posts 上从来没有过 status**。写这条 SQL 的人按 topics 的记忆写了 `p.status`。测试没抓住它，因为 `forum/internal/user/service_test.go:39` 用的是 `client.Schema.Create(ctx)`（ent 生成的形状）而不是迁移——而 ent 的 `posts` 也没有 status 列，所以那条测试里这条 SQL 仍然会炸，**除非它根本没被调用**：`user/pgsql` 的 `Profile` 在 `forum/internal/user` 的测试里没有被任何用例走到（grep `ProfileSQL` 在测试目录只命中本次探针）。
- **复现**（已跑，见 D1 的真库输出）：`PREPARE probe_user_ProfileSQL AS <queries.go:19-37 原文>` → `ERROR: 字段 p.status 不存在 (SQLSTATE 42703)`。
- **建议堵法**：
  1. `p.status` → `p.visibility`；
  2. 该端点补一条"真库真跑"的集成测试（现状是零覆盖）；
  3. 把"所有原生 SQL 常量真库 PREPARE"做成 CI 步骤（同 D1 第 2 条）——这条和 D1 是同一道闸门缺失的两个实例。

### D4｜`release_assets` 的批量计数写回**没有按 id 去重** → 静默丢增量（第 6 类缺陷的复现）

- **严重度：数据错**（下载量少算，不报错）。
- **在哪**：`forum/internal/release/pgsql.go:259-269`（`addDownloadCounts`）：
  ```sql
  UPDATE release_assets
     SET download_count = download_count + v.n
    FROM (SELECT unnest($1::bigint[]) AS id, unnest($2::bigint[]) AS n) v
   WHERE release_assets.id = v.id
  ```
  调用方：`forum/internal/release/service.go:297`（`return addDownloadCounts(ctx, s.db, ids, counts)`）。
- **现象**：同一批 `ids` 里若某个 id 出现两次，PG 只把该行更新一次（取第一个匹配），后面的增量被**静默丢掉**——这不是报错，是把数据写错。
- **根因**：**同一类缺陷在同一个仓库里有两个实现，只有一个被修了**。`forum/internal/platform/counter/pgcounter/pgcounter.go:55-71` 显式做了去重，注释还写着原因：
  > `// 先按 id 合并：同一条 UPDATE 里若有重复 id，PG 只会更新该行一次（取第一个匹配），// 后面几笔会被静默丢掉。合并放在 Go 里，SQL 就始终是「一个 id 最多出现一次」。`

  而 release 这条路径走的是 **counter 之外的独立实现**（`flushDownloads` 自己攒 map，`service.go:297` 直接传 `ids/counts`），于是"合并"这一步整条消失。
- **复现**（静态 + 真库 PREPARE）：该 SQL 本身 `SQL_OK`（列都对），所以**PREPARE 类的闸门抓不到它**；需要用行为测试。最小复现：
  ```sql
  INSERT INTO releases (public_id, version) VALUES (gen_random_uuid(), 'v1');
  INSERT INTO release_assets (public_id, release_id, platform, arch, url, sha256)
    SELECT gen_random_uuid(), id, 'windows', 'x86_64', 'https://x', repeat('a',64) FROM releases;
  -- 同一 id 两笔：
  UPDATE release_assets SET download_count = download_count + v.n
    FROM (SELECT unnest(ARRAY[1,1]::bigint[]) AS id, unnest(ARRAY[1,1]::bigint[]) AS n) v
   WHERE release_assets.id = v.id;
  SELECT download_count FROM release_assets WHERE id = 1;  -- 得 1，期望 2
  ```
- **建议堵法**：
  1. `flushDownloads` / `addDownloadCounts` 里加与 pgcounter 同款的"按 id 合并"（或直接改成复用 `platform/counter`，它已经保证了这个不变量）；
  2. 加一条**行为**测试：同一批喂重复 id，断言 `download_count == 两笔之和`（pgcounter 已有 `pgcounter_test.go:64` 的同款断言可抄）；
  3. 把"批量 UPDATE ... FROM unnest 必须去重"写成 `开发必读` 的一条硬规则，并在 `SaveChain` 之类新增写回点时对照检查。

### D5｜`sessions.ip / audit_logs.ip`：ent 声明 `String`，库里是 `inet`（第 1 类的变体：类型不一致，写路径按值域炸）

- **严重度：隐患**（正常请求 100% 通过；一旦 ip 为空/非法就变成 500 而不是 400）。
- **在哪**：`forum/internal/ent/schema/session.go:40-41`（`field.String("ip").MaxLen(45)`）、`audit_log.go:48-50`；迁移 `0003_authz.up.sql:20` 是 `ip inet NOT NULL`。
  实体文件自己写明了这件事是有意为之（"PG 侧是 inet（0003_authz 建表写死）。ent 表达不了列类型：v0.14 的 entsql.Annotation 没有 Type 字段"）。
- **现象**：`Session.Create().SetIP("x")` → `错误: 无效的类型 inet 输入语法: "x" (SQLSTATE 22P02)`；而 ent 侧**没有任何长度/格式校验**能提前把它变成 400。真实调用链 `auth/handler.go:210 (ClientIP(c))` → `auth/session.go:102 (SetIP(ip))` → `sessions.ip inet`。
- **根因**：ent 生成的是 `varchar(45)`，迁移建的是 `inet`；**两条 DDL 路径产物不同**，而"空库跑迁移 vs ent schema snapshot 比对"这条 CI（数据库文档 §6 与 §12 第 9 条）**不存在**，所以没人发现。
  补充：**ent v0.14.6 其实有 `SchemaType`**（本仓库自己就在用：`mail_log.go:46` 用 `SchemaType(map[string]string{dialect.Postgres: "date"})`，`mail_quota.go:34` 同）。所以"ent 表达不了"这个理由**对 ip 不成立**：`field.String("ip").SchemaType(map[string]string{dialect.Postgres:"inet"})` 就能让两边一致（剩下的只是 Go 侧仍要自己校验格式）。
- **复现**（已跑）：写路径探针里 46 个实体中 `Session` 报 `无效的类型 inet 输入语法: "x" (SQLSTATE 22P02)`；其余写失败都是校验器/外键按预期拒绝假数据。
- **建议堵法**：
  1. 给两个 ip 列加 `SchemaType(pgType("inet"))`（`pgType` 已有，见 `board.go:18`），`go generate` 后两条 DDL 路径就一致了；
  2. **把数据库文档 §6/§12 第 9 条真的做出来**：空库跑迁移 → `atlas migrate diff` 与 ent schema 比对 → 有 diff 即 CI 红。这一条能一次抓掉 D2/D5 与 D12 的 28 处类型不一致。

### D6｜28 处 ent 字段类型与迁移列类型不一致（`field.Int` → bigint vs 迁移 integer 等）

- **严重度：隐患**（今天不炸；一旦"ent Schema.Create vs 迁移"这条路径被打开就会静默改列，或让 Atlas diff 永远红）。
- **在哪 / 清单**（真库 + 生成代码逐列比对，共 28 处）：

  | 迁移列 | ent 声明 → ent 会生成的类型 | 迁移实际类型 | 处数 |
  |---|---|---|---|
  | `*.sort / priority / attempts / count / delta / depth / refcount / width / height / exp / level / daily_limit / max_retry` | `field.Int` → **bigint** | **integer** | 20 |
  | `images.visibility` | `field.Int` → bigint | **smallint** | 1 |
  | `users.avatar_hash / avatar_small_hash / default_avatar_hash`、`images.hash`、`default_avatars.hash`、`payment_channels.image_hash` | `field.String` → **varchar** | **char(64)** | 6 |
  | `sessions.ip / audit_logs.ip` | `field.String` → varchar(45) | **inet** | 2 |
  | `mail_logs.quota_day / mail_quota.day` | 有 `SchemaType(date)` ✅ | date | 0（**已正确**，此处仅作对照） |

  注：`field.Int64` 与 `field.Int` 在 ent 的 PG 方言里**都映射 bigint**（已核实 `ent@v0.14.6/dialect/sql/schema/postgres.go:122` 的 `case field.TypeUint32, field.TypeInt, …, field.TypeInt64: postgres.TypeBigInt`），所以这批列是"ent 想要 bigint、迁移给了 integer"。
- **现象**：`client.Schema.Create` 会把这些列 `ALTER` 成 bigint（`forum/internal/ent/schema/image.go:21` 的注释明确说过这件事："否则 ent 的 Schema.Create 会去 ALTER 一个正在正常工作的列"）；Atlas 的 `migrate diff` 同样永远有 diff。
- **根因**：写 schema 的人用 `field.Int` 表示"这是个小整数"，但 `field.Int` 的 DDL 是 bigint，**不是 int32**。要 int32 必须写 `field.Int32`。**两条 DDL 路径从不比对**（同上：§12 第 9 条缺失）。
- **复现**：本次比对脚本的输出（28 行，见上表）；真库侧证据是 `information_schema.columns` 与 `forum/internal/ent/migrate/schema.go` 的 `Type:` 字段逐列比。
- **建议堵法**：
  1. 二选一：把 schema 侧改成 `field.Int32`（要 integer 的那些），或把迁移改成 bigint（要 int64 的那些）。**推荐前者**——20 列都是小整数，bigint 白白多 4 字节/列。
  2. `char(64)` 那 6 列：ent 侧补 `SchemaType(pgType("char(64)"))`（`board.cover_hash` 与 `topic_image.image_hash` 已经这么写了，**同一份 schema 里两种写法并存**，是这次不一致的直接来源）。
  3. 准入闸门：`atlas migrate diff --to ent://internal/ent/schema` 必须空输出（数据库文档 §6 已写，未实现）。

### D7｜零共列的 phantom 外键：ent 会生成 18 个迁移里没有的列

- **严重度：隐患**（只要有人跑 `client.Schema.Create` 就会多出 18 列 + 18 个外键；生产禁止 Schema.Create，但测试与开发会踩）。
- **在哪**：`forum/internal/ent/schema/user.go:101-116` 的 16 条"反向边"里，有 11 条**对方实体没有对应的正向边**，于是 ent 给**对方表**加了一个可空的 FK 列：
  ```
  announcements.user_announcements        banners.user_banners
  donation_records.user_donations_{sent,received,verified}
  exp_events.user_exp_events              images.user_images
  messages.user_messages_{as_low,as_high,sent}
  notifications.user_{notifications,acted_notifications}
  notification_mutes.user_notification_mutes
  payment_channels.user_payment_channels
  titles.title_equipped_by                user_titles.{title_holders,user_user_titles,user_granted_titles}
  ```
  （证据：`forum/internal/ent/migrate/schema.go` 里 `users.title_equipped_by`、`user_titles.title_holders` 等列，与真库 47 张表的列清单求差集 → 18 列）
- **现象**：**写路径恰好不报**（id 为 nil 会被省略）——正是第 2 类缺陷的镜像：这次是"ent 有列、迁移没有"，读路径才会 `SELECT` 到不存在的列。今天不炸的唯一原因是没人对 `titles` / `user_titles` / `images` 跑 `Schema.Create`（`user` 与 `auth` 的测试跑了，但恰好只碰 `Schema.Create` 建出来的形状，所以"看起来对"）。
- **根因**：反向边只能靠 `.Ref(\"名字\")` 与对方**逐字同名**，而 `user.go` 里那 16 条是"别人 .Ref() 过来的反向边"的**占位**，其中 11 条的对方还没写正向边。ent 对这种"单向 edge"的默认行为是造一个新的 FK 列，**不报错**。
- **复现**：`forum/internal/ent/migrate/schema.go` 与真库列清单的差集（本次比对脚本输出 `phantom count: 18`）。
- **建议堵法**：
  1. 那 11 条边改成对方实体的正向 `.Ref()`（现在写成 `edge.To(\"x\", T.Type)` 却不给 `.Field()` 的形态，ent 就理解为"新 FK"）；

## 附录 B：`char(64)` 那 6 处为什么是"隐患"而不是"数据错"

`users.avatar_hash` 等 6 列在库里是 `char(64)`、在 ent 里是 `varchar`（无长度）。PG 的 `bpchar` 与 `varchar` 在**定长 hex 值**上的读写行为等价（无尾空格），所以今天的读写都对；风险在两条 DDL 路径不相等：谁跑一次 `Schema.Create` / `atlas migrate apply` 就会去 `ALTER` 这 6 列（`image.go:21` 的注释已经预告过这个动作）。同一个 `schema` 包里 `board.cover_hash` 与 `topic_image.image_hash` **已经**写了 `SchemaType(pgType("char(64)"))`，所以这不是"ent 做不到"，是"漏写"。
