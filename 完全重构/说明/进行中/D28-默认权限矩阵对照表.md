## 一、24 个权限点：代码常量 = `permissions` 表 = 界面目录

| grp（库里） | 权限点 | 界面分组（mock 的 `grp`） |
|---|---|---|
| topic | `topic.create` `topic.edit.own` `topic.delete.own` `topic.delete.any` `topic.lock` `topic.pin` `topic.move` `resource.publish` | 内容 |
| board | `board.manage` `board.moderate` | 分区 |
| topic | `post.review` | 内容 |
| user | `report.handle` `reward.verify` | 运营 |
| title | `title.grant` `title.manage` | 授权 / 运营 |
| user | `role.edit` `role.assign` `permission.grant` `user.ban` `user.mute` | 授权 / 用户 |
| site | `mail.manage` `site.setting` `audit.view` `audit.export` | 系统 |

**界面上的 `grp` 是后端给的**（`GET /admin/permissions` → `PermItem.group`，真源 `authz` 常量 + 0017 的 `permissions.grp`），
不是前端那张中文表 —— `15-admin/mock/roles.ts` 里的 `PERM_GROUPS`（内容/用户/授权/分区/运营/系统）
是**房间演示**用的旧口径，产品页拿不到它，所以两者不会互相漂移。

## 二、默认矩阵：应该是什么 vs 库里原来是什么

| 角色 | 应该（拍板 §1.3） | 0017 原来种的 | 差异 |
|---|---|---|---|
| `user` | 3：`topic.create` `topic.edit.own` `topic.delete.own` | 3，逐点相同 | ✅ 无 |
| `creator` | 7：user 的 3 个 + `topic.pin` `topic.move` `topic.lock` `resource.publish` | 7，逐点相同 | ✅ 无（`lock`/`move` 是 d2-auth §8.6 的明确取舍：创作者管**自己的**帖子，归属判定在 forum） |
| `admin` | 17：`topic.*` 八个 + `board.manage` `board.moderate` `post.review` `report.handle` `reward.verify` `title.grant` `title.manage` `user.ban` `user.mute` | **16**（漏 `resource.publish`） | ❌ **改**：0052 补上 |
| `superadmin` | 24（全部） | 24（`CROSS JOIN permissions`） | ✅ 无 |

**漏 `resource.publish` 的后果不是「少一个勾」**：管理员发一篇 `kind=resource` 的帖子会被 403 拦下
（`resource.publish` 是发资源帖的额外门槛），而替创作者补发资源帖是后台最日常的动作之一。

**改法**：新迁移 `0052_admin_resource_publish`（**不改 0017** —— golang-migrate 只跑没跑过的版本，
改老迁移对已迁移的实例等于没改）。0052 只补这一个点、`WHERE NOT EXISTS` 幂等、
不碰后台改过的其他勾（0017 那条「重跑不覆盖」的纪律继续有效）。

## 三、admin 与 superadmin 的分界（不是漏配，是拍板）

下面这 7 个点**只归 superadmin**（§1.3 明文），所以 admin 的默认矩阵里没有它们**不是**缺口：

`role.edit`（改矩阵）、`role.assign`（分配角色）、`permission.grant`（点对点追加）、
`site.setting`（站点设置，AI 审核的四个端点也用它）、`audit.view`、`audit.export`、`mail.manage`。

三者的分开是硬要求（`authz/privileges.go` 的文件头）：任意两个合并都能让持有者给自己提到最高权。

## 四、界面映射：这一屏怎么显示默认值

| 界面元素 | 数据来源 | 默认值的表现 |
|---|---|---|
| 左栏角色列表 | `GET /admin/roles` 的 `RoleItem[]` | 按 `priority` 排序；`user_count` 是真实在用人数 |
| 勾选矩阵 | `RoleItem.perm_keys`（**后端算好的并集**） | 勾上的就是库里的默认值；没勾的=该角色没有 |
| 权限点目录 | `GET /admin/permissions` 的 `PermItem[]`（key/group/name/description） | 唯一真源是代码常量；后台**不能新增权限点**（没有那个端点） |
| `is_super` 角色 | `RoleItem.is_super` | 矩阵**只读**：后端在 `authz.Require` 里短路，改它只会产生一个骗人的勾 |
| `role.edit` 缺失时的账号 | `can(session, 'role.edit')` | 整张矩阵只读 + 一句 `GateNote`（真正的判定在后端） |

**「应该有而没有」的那一栏在这个屏上是看不见的**：`GET /admin/roles` 只回「这个角色有什么」，
不回「按规范它该有什么」—— 所以规范与默认值的一致性由 `role_permissions_test.go` 守，
不能指望管理员用眼睛在勾选矩阵里发现（漏一个点与「本来就不该有」长得一模一样）。
