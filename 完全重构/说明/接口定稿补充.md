# 接口定稿补充（P2 提的 7 条缺口 + 1 条门禁，Lead 拍板）

> 来源：P2 前端产品壳的回报（§5 依赖端点与缺口）。这些不定，P1 与 P2 会各自发明形状。
> **总原则**：一个概念只有一份真源；字段名要说实话（名与内容不符的名字，就是下一轮的 bug）。

## 1. 权限点命名：**以代码为准**（`forum/internal/authz/authz.go` 的 24 个常量）

两套命名并存（§21.2 的 `post.review`/`role.edit`/`site.setting`/`audit.view` vs RBAC 树文档的 `topic.*`/`system.settings`/`audit.read`）——
**定稿：权威是 `forum/internal/authz/authz.go`**，因为：① 拍板 §10.9 已冻结 24 个；② 迁移 0017 的 seed 就照它写；③ 代码里已经在用。
**前端**：把那套「任一套命中即放行」的兼容表删掉，改成单一常量表（从 authz.go 抄一遍，加一行注释指向它）。
**后端**：启动自检 `CheckPermissions` 已经在对比代码常量与 `permissions` 表 —— 它一旦接进 `forum check`（P4），这套命名就有了机器保证。

## 2. 免登录申诉端点：**建**（这是被封者唯一的闭环）

    POST /api/v1/appeals
    { type: 'ban'|'review_reject'|'report_result'|'other', username, email, ref?, title, details, contact?, captcha }
    -> 202 { no, eta }

理由：§21.2 只有「帖子作者申诉」（`POST /topics/{id}/review/appeal`），而**被封的人登不进来**，那条路走不到（盲审合并结论 §7）。
**必须免登录**，用「用户名 + 邮箱 + 图形验证码」作身份确认（前端已按这个形状实现）。
速率限制：按 IP + 按邮箱双限（对齐 §11 的验证码口径）。
**联系**：与 §21.2 的作者申诉是两件事，**不要合并**（一个是内容复核，一个是账号处罚），但两者都写进 `review_events`/申诉表，管理端同一队列。

## 3. `topics.board_id`：**改名为 `board`，值是 slug**

现状矛盾：§21.2 字段名带 `_id`，而全站句柄是 slug（`/b/:slug`、`?board=`）—— **名与内容不符**，正是我们一直在清的那类问题。
定稿：
- 请求参数用 `board`（字符串 slug）；
- 响应里若要给分区标识，给 `board: { slug, name }` 这类**对象**，**不要**再出现一个叫 `board_id` 却装 slug 的字段；
- 内部整型 id 留在数据库与 ent 层，**不出 API**（拍板 §5.6：自增 id 不出 API）。

## 4. `content_md` 里装什么：**必须是 Markdown**（编辑器负责导出）

现状矛盾：编辑器（Lexical）的存储是 EditorState JSON，而契约字段叫 `content_md`。
定稿：**`content_md` 就是 Markdown**，理由：后端用 goldmark 渲染 + bluemonday 清洗，那条管线的前提是 Markdown；
若改成 JSON，**渲染与清洗都要重做**（还要防 JSON 里的富文本注入）—— 代价远大于前端加一次导出。

**前端要做的**：编辑器提交前用 `@lexical/markdown` 的 transformers 导出 Markdown（库里已有这个包的能力）。
**风险（如实记）**：导出会**丢失 Lexical 特有的节点**（自定义节点、某些装饰器）。所以：
- 本轮**只支持 Markdown 能表达的内容**（加粗/斜体/标题/列表/引用/代码/链接/图片），**编辑器工具栏也只放这些**（现在已经是这样）；
- 若将来要保留富节点，正确的做法是**另加一个字段**（例如 `content_rich` + `content_format`），**不要让 `content_md` 装 JSON**。

## 5. `posts[].dislike_count`：**加上**

评论区 UI 有赞/踩，而 `Like.value=±1` 在 v2 §12 第 6 条已经定了。契约只写「点赞数」是漏的。
响应里给 `like_count` 与 `dislike_count`；缺省 0，**不假装踩过**。

## 6. `excerpt`：**后端补**（列表项需要摘要）

卡片与紧凑列表都要摘要，而 §21.3 的列表项没有它。已挂在 `界面施工-后端需求变动.md` §4.1，这里确认：
**由后端生成**（渲染后的纯文本前 N 字），**前端不要拉全文再截断**（那是 N+1 之外又多一次全量读）。

## 7. 分区内导航（精华 / 公告）：**两个不同的东西，别塞进同一个参数**

- **精华**是主题的一个布尔属性 → 用 `featured=1`（或响应里带 `featured`，列表支持按它筛）；
- **公告**更像一种**主题类型**（kind），用 `kind=announcement`；
两者语义不同（一个是加权标记，一个内容类别），**共用一个参数会立刻产生「既精华又公告的怎么传」这种问题**。

## 8. `gate:budget` 的最大路由 chunk 超标（97.5/60）：**让门禁实现它自己的文档**

P2 没有改（那两处是 Lead 专属），我来看。事实：
- 超标的是**富文本编辑器 chunk**（Lexical 自身 gzip 约 101KB），**任何包含它的分块都必然超 60KB**；
- 而前端方案 §9.1 **本来就写了例外**（「单个懒加载路由 chunk 60 KB，管理后台允许 90 KB」）——
  **也就是门禁脚本一直没有实现自己的文档**（现在是一刀切 60KB）。

**定稿**：改 `scripts/check-budget.ts`，把额度做成**具名例外表**（chunk 匹配 → 额度 + 理由），先补两条：

| chunk | 额度 | 理由 |
|---|---|---|
| 管理后台（`admin*`） | 90 KB | 前端方案 §9.1 原文 |
| 编辑器（`markdown-editor*` / 含 Lexical 的块） | 120 KB | **懒加载**，不进首屏；Lexical 是第三方编辑器，拆它要靠构建配置且收益只在网络差的场景 |

**这不是「让门禁闭嘴」**：① 额度是**具名 + 带理由**的；② 首屏预算（150KB）仍然一刀切；③ 例外表本身就是文档化的政策，
而我修的是「脚本没实现文档」这个缺口。**真正的解法**（把 Lexical 拆成 ≤60KB 的若干块）留给后续优化，记在待办里。
