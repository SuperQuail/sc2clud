# 技术栈与取舍

> 本文记录**为什么是这些技术**，以及**明确不采用什么**。
> 结论由硬约束推导，不是偏好；换机器规格时请连同本文一起重新推导。

## 1. 约束前提

| 约束 | 数值 | 对技术栈的强制影响 |
| --- | --- | --- |
| 服务器规格 | 2 vCPU / 2 GB RAM | 应用常驻内存必须 ≤ 150 MB；排除 JVM 级重运行时 |
| 端口带宽 | 10 Mbps 上/下行 ≈ 1.25 MB/s（全站共享） | 网络是唯一瓶颈；**文件字节一律不得经过应用进程**；前端体积纳入硬预算 |
| 磁盘 | 单机块存储 | 吞吐比带宽富余两个数量级，可放心做预压缩、多档缩略图、多副本 |
| CPU | 2 核、长期空闲（< 10%） | 定位为「用 CPU 换带宽」的资源池 |
| 业务范围 | 社区（帖/评论/用户/通知）+ 文件上传下载 | 需处理并发长连接、路径安全、配额、限速、断点续传 |
| 部署 | 单机、无编排 | 单二进制 + systemd；不引入容器编排 |

**核心判断**：网络比磁盘慢约两个数量级，因此语言性能不构成选型依据。
选型的真实依据依次是：① 常驻内存；② 部署与运维复杂度；③ 文件路径安全性；④ 团队开发效率。

## 2. 选型总览

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | Rust（edition 2024，1.94 固定） | 单静态二进制、常驻 20–80 MB；若团队更熟 Go 可等价替换 |
| 异步运行时 | tokio | 文件 IO 走流式异步，不阻塞 reactor |
| Web 框架 | axum 0.8 | 与 hyper / tower 生态一致；限流、鉴权、日志用 tower 组合 |
| 模板 | askama | 编译期模板，零运行时模板开销 |
| 序列化 | serde + serde_json | — |
| 哈希 | blake3 | 单核 GB/s 量级；去重 / 秒传 / 完整性校验共用 |
| 元数据库 | SQLite（WAL） | 无独立进程，与文件缓存共享 page cache；预留 PostgreSQL 迁移路径 |
| 数据库访问 | sqlx | 从 SQLite 切 PG 只改连接串与少量方言（当前用运行时查询，schema 稳定后切 `query!`） |
| 文件存储 | 本地内容寻址（主）+ S3 兼容（可切换） | `StorageBackend` trait 抽象，两个实现 |
| 反向代理 | nginx | sendfile 零拷贝直出、secure_link、limit_rate / limit_conn、brotli_static |
| 前端 | SSR 模板 + 渐进增强 | 交互密集处局部挂 Vue 3 + TypeScript + Vite |
| 进程管理 | systemd | 单 unit + `MemoryHigh` / `MemoryMax` / `OOMScoreAdjust` |
| 观测 | tracing + 异步落盘日志 | 日志批量刷盘，严禁每请求 fsync |
| 错误处理 | thiserror（领域）+ anyhow（边界） | — |

## 3. 关键分层理由

### 3.1 语言与运行时

选 Rust 的理由**不是性能**，而是：① 单二进制免运行时依赖；② 常驻内存低，把 2 GB 留给数据库与文件缓存；
③ 路径安全（`..`、符号链接越界、TOCTOU）在类型与显式校验下更易保证；④ 团队既有 Rust 能力。

**明确排除 JVM 系**（Spring Boot 等）：空转基线 300–600 MB，在 2 GB 上不可接受。

### 3.2 文件传输路径（本项目最关键的设计约束）

| 方向 | 实现 |
| --- | --- |
| 下载 | 应用只签发带 TTL 的签名 URL；nginx `secure_link` 自行校验签名与过期时间，`sendfile` 直出磁盘。应用在下载链路的 CPU 占用为 0 |
| 上传 | 应用流式接收（固定 64 KiB 缓冲），边收边算 blake3，直写目标文件；全程恒定内存，禁止一次性读入 `Vec<u8>` |
| 秒传 | 客户端先报 blake3，服务端核对**磁盘上确实存在该内容**后直接建引用，0 字节传输 |
| 断点续传 | 下载：nginx 原生 Range（免开发）；上传：分片 + 服务端记录已完成分片（表已就绪，接口待接） |
| 限速 | 下载用 nginx `limit_rate_after` + `limit_rate`；上传用应用层令牌桶（stock nginx 无上传限速指令） |

### 3.3 数据存储

- **主库 SQLite + WAL**：无独立进程、无专属缓冲池，省下的内存全部转化为文件缓存；单实例下并发完全够用。
- **写并发约束**：SQLite 单写者。写热点（计数、浏览数）走内存聚合 + 定时批量落库，禁止每请求 `UPDATE`。
- **不引入 Redis（初期）**：单实例应用用进程内聚合即可，省 20–50 MB；仅在需要跨进程共享会话/队列时再引入。
- **迁移路径**：出现多实例部署需求或写并发瓶颈时切 PostgreSQL；sqlx 使此迁移成本可控。

### 3.4 前端

在 1.25 MB/s 的链路上，前端 bundle 体积直接等于用户等待时间：SSR 页面（20–50 KB）与 SPA 首屏（300 KB+ JS）
的差距是 2.4 秒纯传输，且尚未计入解析执行。因此：

- 默认：askama 编译期模板输出 HTML；
- 例外：交互密集模块（上传进度、实时通知、富文本）局部挂载 Vue 3 + TS + Vite；
- 禁止：整站 SPA、CSS-in-JS 运行时、大型 UI 组件库全量引入；
- 强制：静态资源 brotli 预压缩（`brotli_static`），图片输出 WebP 多档尺寸。

## 4. 明确不采用

| 技术 | 原因 |
| --- | --- |
| Spring Boot / JVM 系 | 空转基线 300–600 MB，2 GB 上性价比不成立 |
| PHP-FPM 处理文件传输 | 一请求一进程，慢速上传长期占用 worker；并发受 `max_children` 硬限 |
| MinIO | 相对 2 GB 规格偏重；改用 Garage（Rust）或直接用对象存储 |
| Redis（初期） | 单实例下进程内聚合足够，省 20–50 MB |
| Elasticsearch | 单独即需 1 GB+ |
| 整站 SPA / Next.js SSR 全家桶 | 前端体积与带宽预算直接冲突 |
| 应用进程搬运文件字节 | 一律交给 nginx `sendfile` 零拷贝 |
| 同机 CI runner / 容器编排 | 与业务争抢本就紧张的内存与 CPU |
| 请求路径内的同步图片转码 | 2 核上会瞬间打满 CPU，必须异步化 |

## 5. 与现实的偏差记录

原始约束里写的是「HMAC 签名」。**stock nginx 只有 MD5**（`secure_link_md5`，无 SHA-256 变体），
所以实现是「把密钥拼进被哈希表达式」的带密钥 MAC（keyed MD5），语义上等价于短 TTL 场景下的 HMAC。
若确实需要 HMAC-SHA256，可换用第三方模块 `ngx_http_hmac_secure_link_module`。详见 `sign.rs` 顶部注释。
