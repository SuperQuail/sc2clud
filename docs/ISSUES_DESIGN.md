# 资源帖 Issue（报告 Bug / 功能建议）—— 设计与规划

> 面向 AI 代理与协作者。核心字段仍叫 issue；**对用户一律不出现 issue 这个词**。

## 1. 现状盘点（写之前先看这段，别重复造）

| 层 | 现状 |
| --- | --- |
| 表 | `post_issues`（`kind: bug\|feature\|other`、`state: open\|closed`、`closed_at/closed_by`、`created_at/updated_at`）、`issue_comments`（软删 `deleted_at`）—— 迁移 0014 |
| 领域 | `core::community::IssueKind`（bug / 功能建议 / 其它，带中文标签）、`IssueState`（开着 / 已关闭）、经验值动作 `IssueCreated` / `IssueClosed` |
| 仓储 | `list_issues`、`get_issue`、`set_issue_state`、`count_open_issues`、`add_issue_comment`、`list_issue_comments` |
| 路由 | `POST /p/{id}/issues`、`POST /p/{id}/issues/{issue_id}/state`、`POST /p/{id}/issues/{issue_id}/comments`、`GET /api/v1/posts/{id}/issues`、`GET /api/v1/posts/{id}/issues/{issue_id}` |
| 页面 | **完全没有**（模板里 0 处 issue）—— 今天只有 API，没人能用 |

结论：**后端基本齐了，这活是「做页面 + 补权限细节」**，不是从零开始。

## 2. 命名与文案（最重要的一条）

用户看到的词：

| 位置 | 文案 |
| --- | --- |
| 入口按钮 | **报告 Bug / 功能建议** |
| 类型选项 | `报告 Bug` · `功能建议` · `其它问题`（三选一，必选） |
| 列表标题 | 「XX 的反馈」/「XX 的问题与建议」 |
| 空态 | 「还没有人反馈问题。发现问题就点右上角『报告 Bug』」 |

代码内部继续用 `issue` / `kind`，不改成 report 之类（仓储与表已经这样了）。

## 3. 数据模型要补的（都很小）

1. `post_issues.deleted_at INTEGER`（软删除，列表查询排除；管理员可见已删除）；
2. `post_issues.edited_at INTEGER` + `editor_id INTEGER`（谁改的，用于「由作者/管理员编辑过」提示）——
   是否要留编辑历史（像帖子修订那样）先不做，写在这里备查；
3. 索引已在（`idx_post_issues_post`），补一个 `(post_id, kind, state)` 便于筛选。

`kind` 与 `state` 的取值集合已在 core 里定死并有往返单测，**不要新增取值**；
要加就在 `IssueKind` 里加，并同步其 `label()`。

## 4. 权限矩阵（你给的规则 + 我要跟你确认的两处 ⚠️）

| 动作 | 游客 | 登录用户 | issue 作者 | **帖子发布者** | 管理员及以上 |
| --- | --- | --- | --- | --- | --- |
| 浏览列表/详情 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 提交 | ❌ | ✅ | — | ✅ | ✅ |
| 编辑内容 | ❌ | ❌ | ⚠️ 见下 | ✅ | ✅ |
| 关闭 / 重新打开 | ❌ | ❌ | ⚠️ 见下 | ✅ | ✅ |
| 删除（软删） | ❌ | ❌ | ❌ | ✅ | ✅ |
| 评论 | ❌ | ✅ | ✅ | ✅ | ✅ |
| 删除他人评论 | ❌ | ❌ | ❌ | ❌ | ✅ |

**已定（GitHub 式，2026-10-10）：提建议的人可以编辑与关闭自己的 issue** —— 上表 ⚠️ 两格改成 ✅：

| 动作 | 游客 | 普通用户 | **issue 作者** | **帖子发布者** | 管理员及以上 |
| --- | --- | --- | --- | --- | --- |
| 编辑内容 | ❌ | ❌ | ✅ | ✅ | ✅ |
| 关闭 / 重新打开 | ❌ | ❌ | ✅ | ✅ | ✅ |

补充约定：
1. 删除（软删）不开放给 issue 作者 —— 与 GitHub 一致（提的人可以关，但不能抹掉记录），发布者与管理员可删；
2. **评论作者可以删自己的评论**（软删），发布者与管理员可删任何评论；
3. 「发布者」= 资源帖作者（`posts.author_id`）；平台没有「协作作者」概念，先只认作者本人。

## 5. 交互设计

**列表页 `/p/{id}/issues`**：
1. 顶部一行筛选：`全部 / 待处理 / 已关闭` + 类型筛选 `全部 / Bug / 建议 / 其它`（同一行芯片，默认「待处理 + 全部类型」）；
2. 每条：类型徽章（Bug 用红、建议用蓝、其它用灰）+ 标题 + 作者 + 时间 + 评论数 + 状态；
3. 右上角：**报告 Bug**（主按钮）+ **功能建议**（次按钮）—— 两个入口分别预选类型；
4. 空态文案见 §2。

**新建 / 编辑（同一表单）**：类型是三选一**必选**（默认按你点的入口预选），标题（≤ 80 字）、正文（支持现有帖子编辑器的最小版）、
提交后回到列表并高亮新条目。

**详情**：整页（`/p/{id}/issues/{issue_id}`），左侧正文、右侧元信息（类型、状态、作者、时间、所属资源帖链接）；
底部评论（复用评论区的样式与 @ 机制）；右侧按钮按权限显示：`编辑` / `关闭` / `重新打开` / `删除`（删除要二次确认，措辞「删除后不可恢复，但管理员仍可查看」）。

**与资源帖的关系**：帖子页（`/p/{id}`）在下载区下方放一条入口：「**问题与建议 · 待处理 3**」→ 点进列表；
不把 issue 列表嵌进帖子页正文（帖子页已经很长）。

## 6. 三版布局（按 §11 规矩，先出图再定）

| 版本 | 列表形态 | 取舍 |
| --- | --- | --- |
| **1 · 列表式（对齐 GitHub Issues）** | 一行一条，左侧状态点 + 类型徽章 + 标题 + 右侧评论数/时间；筛选在顶部 | 信息密度最高，仓库式站点的用户最眼熟；但「报告 Bug / 功能建议」两个入口需要单独一行按钮 |
| **2 · 卡片式（对齐 B 站动态）** | 每条一张卡，类型徽章做成一整块彩色标签，正文摘要直接显示 | 对非技术用户最友好，一眼看懂「这是别人提的问题」；列表更长，扫读慢 |
| **3 · 双栏式（左列表右详情，同页切换）** | 左窄栏列表，右侧即时显示详情 | 不用跳页，翻看多个 issue 最快；窄屏要退化成整页，实现复杂 |

实现时用 `?ivi=1|2|3`（仅开发实例）出三张图，你选一版后再写进 `AGENTS.md` §11 的定版表。
